> 文档版本：v0.9  
> 需求 ID：PRD-20260821-SECURITY-ANALYSIS  
> 所属产品：YunLogin PC 端  
> 文档状态：评审稿  
> 最后更新：2026-08-21

## 0. 文档目的与核心结论

本文用于回答三个问题：YunLogin 为什么需要安全策略、首期应解决什么问题、竞品能力应如何取舍。本文是《02-YunLogin安全策略产品设计方案.md》和《03-YunLogin安全策略业务流程.md》的上位依据。

**核心结论：**YunLogin 当前的环境授权解决“谁能打开哪个浏览器环境”，日志解决“事后发生过什么”，但尚未解决“成员进入已授权环境后，哪些网页和高危动作仍然不能做”。安全策略应补齐这一运行时控制层，形成以下闭环：

```text
身份与环境授权（能否进入）
  -> 运行时访问策略（进入后能访问/操作什么）
  -> 临时审批（业务例外如何受控放行）
  -> 安全日志（命中、放行、拦截是否可追溯）
```

首期不建议复制紫鸟全部监控能力。应先把“敏感网页拦截 + 临时审批 + 不可篡改日志”做成可靠闭环，再逐步扩展复制、上传、下载、打印、开发者工具、页面元素和风险告警。

## 2. YunLogin 当前安全能力与缺口

### 2.1 已有能力

1. 团队创建者、管理员、部门、角色及自定义权限矩阵；
2. 环境授权，可限制成员能查看、启动或管理的浏览器环境；
3. 凭据锁定，可控制账号密码等凭据的可见和编辑范围；
4. 登录请求审批，可结合成员、终端、MAC 和网络判断是否允许登录；
5. 登录日志、操作日志、权限日志，且既有 PRD 已要求日志只读、敏感值脱敏、历史成员快照保留；
6. 设置中心存在“环境安全监控”和“高风险操作提醒”的概念入口，但业务规则未明确。

### 2.2 核心缺口

| 编号 | 缺口 | 业务后果 |
|---|---|---|
| G-01 | 环境授权只能决定能否进入环境 | 运营人员为完成上架必须进入 Amazon 店铺，但同时能进入付款、提现、收款账户等不属于其职责的页面 |
| G-02 | 凭据隐藏不能限制已登录会话内的高危页面 | 成员无需知道密码，也可能利用现成登录态执行提现、换绑或新增子账号 |
| G-03 | 现有日志偏事后审计，没有命中策略的专用语义 | 管理员难以区分正常浏览、被阻断操作、临时授权放行和技术失败 |
| G-04 | 缺少临时业务例外 | 一刀切拦截会迫使团队线下共享高权限账号，反而削弱管控 |
| G-05 | 缺少页面资源和匹配测试 | 管理员难以持续维护不同平台、站点、语言和 URL 变化 |
| G-06 | 缺少策略版本、发布和客户端生效证明 | 管理端显示“已开启”不代表成员浏览器实际执行了策略 |
| G-07 | 现有“环境安全策略”实际是代理换绑筛选偏好 | 名称冲突会让用户误以为已经具备网页安全策略 |

### 2.3 目标用户与关键任务

| 角色 | 关键任务 | 最关注的问题 |
|---|---|---|
| 团队创建者 | 建立全团队安全基线、处理重大例外 | 高危操作能否真正被阻断，管理员是否也受审计 |
| 安全管理员 | 创建策略、维护资源、调查事件 | 策略覆盖谁、在哪些环境生效、为何命中 |
| 财务负责人 | 管理资金相关页面和临时授权 | 非财务成员能否被阻断，放行是否有期限与理由 |
| 部门管理员 | 管理本部门成员的策略和申请 | 是否会越权操作其他部门资产 |
| 运营成员 | 完成日常店铺操作 | 被拦截时能否理解原因、申请必要的临时访问 |
| 安全审计员 | 只读查询、导出和关联调查 | 日志是否完整、不可删除、能否还原当时策略版本 |

## 3. 重点风险场景

### 3.1 资金与账户控制

| 风险场景 | 示例 | 推荐控制 |
|---|---|---|
| 非财务成员访问提现/打款页 | Amazon Payments、TikTok Shop 结算提现 | 整页拦截；允许发起限时审批；命中即记录 |
| 修改收款账户 | 新增/替换银行卡、第三方收款账号 | 首期整页拦截；后续增加按钮/表单操作拦截 |
| 查看账单或交易明细 | 资金报表、交易明细 | 可按职责设置“允许并记录”或拦截，避免把查看和提现混为同一风险等级 |
| 新增高权限子账号 | 平台用户与权限管理 | 拦截或要求审批；记录目标环境和页面 |

### 3.2 凭据与会话泄露

| 风险场景 | 推荐控制 |
|---|---|
| 查看浏览器密码管理器明文 | 通用策略按成员/角色禁止查看，并记录尝试 |
| 使用开发者工具读取 Cookie、Token 或表单 | 禁用开发者工具或记录开启尝试；旧客户端不得静默降级 |
| 下载敏感文件、打印或复制财务信息 | P1 增加下载/打印/复制规则，默认不记录文件正文 |
| 通过扩展或自动化接口绕过界面 | 扩展安装、API、RPA 和无头模式分别受权限与策略约束 |

### 3.3 误操作与内部滥用

- 非促销负责人进入折扣、优惠券、库存处置页面；
- 外包成员在合同期外或非工作时段访问环境；
- 成员通过新窗口、重定向或修改 URL 进入受限页面；
- 同一成员同时命中部门、角色和个人策略，结果不可预测；
- 客户端离线、版本过旧或策略同步失败时仍继续运行。

## 4. 竞品深度分析

### 4.1 网易跨境通：轻量访问控制

已核实的模型是“成员 × 店铺 × 预设网页”：

- 固定黑名单模式，可禁止整页访问，也可限制预设网页中的元素/操作；
- 可配置访问行为记录；整页命中时展示“暂无此网页访问权限”，操作命中时拦截指定动作；
- 访问审批通过的优先级高于黑名单；
- 通用策略覆盖屏幕水印、密码框、开发者工具和打印；
- 超级管理员与团队创建者可查看命中策略日志；
- 依赖客户端版本，且截图仅确认从预设网页中添加规则。

**优点：**配置路径短，适合从零启用；成员和店铺范围直接贴合跨境业务。  
**不足：**预设资源限制扩展性；冲突、版本、回滚、日志保留和客户端未生效处理不够透明；“Boss 默认排除”会形成治理盲区。

### 4.2 紫鸟：监管与拦截双体系

紫鸟形成了两条相对独立的产品线：

1. **安全监管：**按平台账号或成员记录浏览行为，配置预设/自定义告警规则，支持截图、文件传输备份、多渠道通知和敏感日志遮蔽；
2. **安全拦截：**黑名单、白名单、访问特例、网页资源库、成员访问审批、访问拦截日志和审计看板。

#### 安全监管的业务逻辑

截图显示“安全监管”不是简单操作日志，而是从监管对象到告警处置的独立体系：

```text
选择按平台账号或按成员监管
  -> 配置需要记录的成员和账号
  -> 选择预设告警规则或自定义网页规则
  -> 成员在环境中访问/操作
  -> 生成行为记录、截图或文件备份
  -> 命中规则后通知指定管理员
  -> 管理员在全部记录/全部告警中调查
```

告警方案可配置方案名称、监控账号、生效成员和通知对象；成员可按全部、指定成员、部门或角色选择。预设规则覆盖价格、优惠、主图、库存处置、提现、收款账户、子账号、TikTok 结算等跨境业务动作；自定义规则可从网页资源库选择或录入 URL，并配置访问、复制、上传、下载、打印、开发者模式和元素点击等行为。部分告警可携带截图，文件传输备份可保存上传/下载原文件，但截图说明同时显示文件大小、类型和客户端版本限制。

监管日志区分“全部记录”和“全部告警”，可按时间、成员、账号、行为和网页筛选。对于资金账户等高敏感页面，紫鸟又增加日志遮蔽：预设敏感 URL 默认隐藏查看/导出，Boss 需短信验证后查看。该设计说明监控证据本身也是高风险数据，权限和二次验证不可缺失。

#### 安全拦截的业务逻辑

```text
维护网页/元素资源
  -> 创建黑名单、白名单或访问特例
  -> 配置成员、账号、时段、网页和动作
  -> 客户端实时执行
  -> 拦截或记录
  -> 成员按规则申请访问
  -> 审批后形成临时例外
  -> 审计看板和明细日志复盘
```

策略列表同时表达类型、成员、账号、网页、状态和启停；策略可按永久、日期区间、星期和每日时间段生效。网页资源可由系统预设、手工 URL、智能采集和元素采集产生。自定义 URL 支持通配符和是否保留完整查询参数，说明紫鸟把“资源定义”与“策略引用”分离，而不是让每条策略重复维护网页。

截图明确给出 `访问特例 > 白名单 > 黑名单` 的策略优先级，同一成员命中多个黑名单时限制规则优先。优点是用户可理解，但“白名单允许”覆盖黑名单拒绝可能让高危页面被误放行；YunLogin 因此不直接沿用该优先级，而把白名单定义为默认拒绝范围，高危拒绝仍可继续收紧。

#### 管理闭环和成熟度判断

| 层级 | 紫鸟可见能力 | 产品判断 |
|---|---|---|
| 组织范围 | 成员、部门、角色 | 能支撑大团队批量治理，优于逐成员配置 |
| 资产范围 | 平台账号、全部/指定账号 | 安全策略与实际店铺资产绑定，而非仅绑定设备 |
| 时间范围 | 永久、日期、星期、每日时段 | 可覆盖外包合同期、值班和非工作时段 |
| 资源层 | 系统预设、自定义 URL、智能采集、元素采集 | 易扩展，但需要持续维护资源健康 |
| 决策层 | 允许、拦截、记录、申请审批 | 形成业务例外闭环 |
| 证据层 | 截图、录像/记录、文件备份、行为日志 | 证据丰富，但隐私、存储和敏感信息风险高 |
| 运营层 | 看板、趋势、成员/账号/URL/动作排行 | 从“功能设置”上升为安全运营工作台 |
| 通知层 | 站内、微信、飞书、钉钉等 | 有利于及时处置，但需要去重和告警降噪 |

访问拦截日志还提供审计看板，按拦截 URL、拦截动作、异常账号和异常成员统计，并能从成员、平台账号、URL 和全部事件下钻。成员访问审批区分待审批、已通过和已拒绝，可配合移动端通知完成及时审批。屏幕水印可按成员和场景显示成员名、手机号后六位、MAC 后四位或自定义内容。

访问策略的可见能力包括：

- 成员可按成员、部门、角色选择；账号可选全部或指定；
- 生效时间支持永久、日期区间、星期与每日时段；
- 黑名单适合限制少量高危网页，白名单适合最小访问集合；
- 访问特例优先级高于白名单和黑名单；
- 可限制复制、上传、下载、打印、开发者工具、密码框以及指定页面元素；
- 网页资源可预设、手工填写、智能采集或元素采集；
- 拦截数据可按成员、账号、网页、动作查看趋势与排行；
- 访问申请可在移动端审批，并限制只有 Boss 审批或完全禁止申请。

**优点：**覆盖“发现—控制—例外—调查”的完整链路，资源库与策略作用域成熟。  
**不足：**概念和配置项多，学习成本高；告警、录像、截图和文件备份带来明显隐私及存储风险；元素选择器容易随平台改版失效；多客户端版本差异可能导致策略看似启用、实际未完全执行；Boss 例外不利于零信任治理。

### 4.3 其他指纹浏览器：以角色、环境和通用限制为主

公开官方资料显示，AdsPower、MoreLogin、Multilogin、GoLogin、Dolphin Anty 普遍具备：

- 成员角色与环境/文件夹/分组授权；
- 仅运行、可编辑、可共享等分级能力；
- 登录、环境打开、环境管理或代理操作日志；
- 密码、开发者工具、登录 IP、2FA 等通用安全设置。

其中 AdsPower 官方文档明确提供 URL 禁止访问；MoreLogin 明确提供按角色限制密码和开发者工具。公开资料主要强调“谁能使用哪些环境”，尚不足以证明它们都具备紫鸟式的网页元素拦截、临时访问审批和命中审计闭环。

### 4.4 能力对比与取舍

| 能力层 | 网易跨境通 | 紫鸟 | 其他公开方案 | YunLogin 决策 |
|---|---|---|---|---|
| 成员/角色/资产范围 | 有成员、店铺 | 成员/部门/角色、账号 | 普遍具备 | 复用现有组织与环境授权 |
| 整页 URL 拦截 | 有，偏预设 | 有，预设+自定义 | AdsPower 明确支持 | P0 必做 |
| 临时访问审批 | 有优先级说明 | 完整审批列表 | 公开资料不普遍 | P0 必做，避免线下绕过 |
| 操作/元素拦截 | 有预设元素 | 较完整 | 通常是通用权限 | P1，先做稳定动作再做元素 |
| 监控/告警 | 访问行为记录 | 录像、截图、告警、文件备份 | 操作日志为主 | P2；首期避免过度监控 |
| 冲突规则 | 审批高于黑名单 | 特例 > 白名单 > 黑名单 | 多为角色继承 | YunLogin 采用硬拦截优先、例外显式放行 |
| 审计解释 | 基础日志 | 看板+多维日志 | 多为操作日志 | P0 记录决策链和策略版本 |
| 管理员例外 | Boss 排除 | Boss 排除较多 | Owner 权限最高 | 不静默排除；采用紧急解锁机制 |

## 5. YunLogin 产品定位与设计原则

### 5.1 一句话定位

让团队管理者在不回收成员日常环境权限的前提下，对资金、账号控制权和敏感数据相关网页实施可解释、可审批、可审计的运行时限制。

### 5.2 设计原则

1. **环境授权与安全策略分层：**环境授权决定能否进入，访问策略决定进入后能做什么。
2. **高危拒绝优先：**普通“允许”规则不能意外覆盖高危拒绝；放行必须通过明确、限时、可追溯的访问特例。
3. **默认可用、按风险收紧：**首期以黑名单为主，避免一开始启用白名单导致大面积业务中断。
4. **先整页、后动作、再监控：**页面拦截最稳定；复制/上传/下载等动作次之；元素规则和录像监控最后引入。
5. **命中原因可解释：**管理员和用户都能知道是哪个策略、哪个版本、哪个范围和哪个资源导致决策。
6. **管理员不天然豁免：**创建者也可以成为策略对象；紧急绕过必须二次验证、限时并形成高优先级日志。
7. **配置生效可证明：**管理端必须显示策略版本、已覆盖客户端、未同步/版本过旧设备，不能只显示一个开关。
8. **最小化采集：**首期记录元数据，不默认采集页面正文、输入内容、截图、文件原文或 Cookie。
9. **失败不静默：**客户端无法执行、日志上报失败或规则失效都必须可见；高危策略按明确降级规则处理。

## 6. 产品范围与分期

### 6.1 P0：安全闭环

- 安全中心入口及权限；
- 系统高危网页模板、自定义 URL 资源、匹配测试；
- 按成员/部门/角色和环境/环境分组/平台账号配置策略；
- 永久或定时生效；
- 整页拦截、允许并记录、命中即记录；
- 临时访问申请、审批、到期自动回收；
- 安全日志、详情决策链、策略版本、客户端生效状态；
- 通用限制中的查看密码、开发者工具、打印能力与现有权限整合；
- 首批系统模板：提现/打款、收款账户、支付方式、用户权限、敏感财务报表。

### 6.2 P1：操作级控制与管理效率

- 复制、上传、下载、打印、开发者工具、查看密码的按策略控制；
- 白名单模式和模拟命中预览；
- 安全概览、趋势、成员/环境/网页排行；
- 企业微信/飞书/邮件等审批和高危事件通知；
- 页面资源变更检测、模板灰度升级；
- 屏幕水印。

### 6.3 P2：高级监管与风险识别

- 页面元素级限制；
- 高危行为组合规则和频次阈值；
- 异常时段、异常设备、异常地理位置联动；
- 经合规评审后的截图证据或文件传输审计；
- 外部 SIEM/Webhook 对接和自动响应。

### 6.4 非目标

- 不替代平台自身的财务审批、双人复核和支付风控；
- 不承诺通过 URL 拦截识别所有单页应用中的后台 API 请求；
- 不在首期录制全量浏览器视频、键盘输入、密码、Cookie 或文件正文；
- 不通过前端隐藏代替服务端权限和客户端强制执行；
- 不允许业务管理员删除或修改历史安全事件。

## 7. 业务目标与成功指标

| 指标 | 定义 | 建议首期目标 |
|---|---|---|
| 高危页面策略覆盖率 | 已配置关键平台高危资源的生产团队 / 已启用安全中心团队 | 上线三个月后 >= 60% |
| 非授权高危访问拦截率 | 被策略正确拦截的非授权高危访问 / 抽样确认的应拦截访问 | 100% |
| 策略实际生效率 | 已同步且客户端支持完整能力的目标环境会话 / 策略目标环境会话 | >= 99.5% |
| 决策可解释率 | 日志可还原策略版本、匹配资源、范围和结果的事件 / 安全事件 | 100% |
| 临时授权自动回收率 | 到期后自动失效的访问特例 / 已到期访问特例 | 100% |
| 拦截误报率 | 经审批人确认不应拦截的事件 / 拦截事件 | < 2% |
| 安全事件丢失率 | 服务端确认缺失的应记录事件 / 应记录事件 | 0；上报失败须进入本地待传与告警 |

## 8. 主要风险与产品应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台 URL 或前端结构变化 | 规则失效或误拦截 | 系统模板版本化、命中健康度、资源校验、灰度升级 |
| 规则过多、冲突难理解 | 误放行或业务中断 | 单一确定性决策引擎、发布前预览、日志展示决策链 |
| 客户端版本碎片化 | 管理端与实际执行不一致 | 能力矩阵、最低版本门槛、环境启动前合规检查 |
| 离线或服务不可用 | 高危策略绕过或业务不可用 | 签名缓存策略包；关键模板失联时按 fail-closed，普通策略按已缓存版本执行 |
| 审批成为形式主义 | 大量长期放行 | 理由必填、限时、最小资源范围、到期回收、申请人与审批人分离 |
| 日志本身泄露敏感信息 | 二次安全事故 | URL 参数脱敏、按权限查看、导出审计、禁止记录正文和凭据 |
| 管理员滥用或误配置 | 全团队失控 | 创建者也受策略、双人审批可选、紧急解锁、策略版本与回滚 |
| 元素级策略脆弱 | 平台改版后失效 | P1/P2 再引入；元素选择器健康检查和自动降级告警 |

## 9. 待确认事项

以下问题不阻塞文档设计，但在进入原型和研发排期前需要业务确认：

1. 首批平台及高危页面优先级：Amazon、TikTok Shop、Shopee、Temu、SHEIN、Lazada 是否全部进入首期？
2. 临时访问审批人：仅团队创建者/安全管理员，还是允许按策略指定财务负责人？是否要求双人审批？
3. 安全日志在线保留期限、归档期限和导出格式；本文建议首期在线 180 天，但需结合套餐和合规成本确认。
4. 客户端离线时，提现、收款账户等系统高危模板是否必须禁止进入；本文建议关键模板 fail-closed。
5. 首期是否同步交付复制/上传/下载/打印控制；本文默认 P1。
6. 是否需要把屏幕水印纳入首期；本文默认 P1。
7. 企业微信、飞书、邮件或站内通知的首发渠道及审批 SLA。
8. 现有设置中心“环境安全策略”是否同意改名为“代理筛选偏好”，避免与本模块重名。

## 10. 需求评审结论

安全策略不是新增一个“禁止访问 URL”的设置项，而是一个贯穿组织、资产、客户端和审计的决策系统。YunLogin 应优先建立可验证的 P0 闭环，并以系统高危模板降低首次配置门槛。紫鸟的完整性值得借鉴，但录像、截图、文件备份和元素级控制不应在底座尚未稳定时一次性引入；网易跨境通的简洁值得借鉴，但不应继承预设资源封闭、管理员天然豁免和生效状态不透明的问题。
