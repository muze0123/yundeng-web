## 1. 需求概述

### 1.0.1 页面定位

|定位维度|页面定义|
|---|---|
|页面职责|让有权限的用户从真实可开票订单选择订单、填写受票信息、提交申请，并追踪审核、开具、交付、红冲和自动重开任务状态|
|系统位置|费用管理 > 开票管理一级页签；上游是订单、支付、履约、退款事实，下游是云登后台审核和第三方电子发票开具|
|核心决策|用户逐单发起申请，每个订单固定生成一张发票；用户选择票种和抬头，但不能决定开票主体、税率、税收分类或申请金额|
|边界|本页不支付、不修复履约、不审批退款、不维护销售主体/税务编码、不直接调用第三方开票平台；这些能力由相应服务承接|
|价值与风险|减少客服线下开票，保证法币交易可追溯；错误的资格、金额或权限判定会造成重复开票、税务风险或敏感信息泄露|

### 1.0.2 用户场景

| 编号   | 场景与优先级         | 前置条件、路径与结果                                                                                        | 中断与恢复                                                     |
| ---- | -------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| S-01 | P0 购买者提交法币订单开票 | 用户有订单查看和申请权限；从费用管理一级页签进入开票管理，筛选可申请订单，点击单行“申请开票”，填写抬头/内容/联系人，确认提交；服务端创建一条待审核申请和一张发票，页面进入开票记录并高亮新申请 | 订单在填写期间退款、履约回退、资格过期或权限变化时，保留表单并阻止提交，用户刷新后重新确认             |
| S-02 | P0 团队财务逐单处理    | 团队财务角色可查看团队订单；逐单发起申请并使用共享企业抬头；系统只创建当前订单对应的申请和发票                                                   | 普通成员只能看到本人订单或脱敏团队处理状态；无权订单不返回申请、票据或抬头详情                   |
| S-03 | P0 申请人查看进度和票据  | 用户从开票记录、订单详情或消息深链进入记录/详情；查看四维状态、票据、交付和时间线；开票成功后预览、下载或重发                                           | 深链对象不存在或权限失效时展示明确无权限/不存在状态，不跳转到其他申请；文件暂不可用时保留已开票状态并允许稍后重试 |
| S-04 | P0 用户处理驳回      | 申请处于已驳回；打开详情查看原因，点击“修改并重新提交”，服务端按原申请幂等创建草稿，用户修正后走预览和标准提交；历史版本只读，原申请新增提交版本后回到待审核                   | 草稿打开后资格或余额变化时显示阻断原因，保留输入，需刷新并重新确认                         |
| S-05 | P0 用户撤回待审核申请   | 申请处于待审核；用户确认撤回；服务端以状态与版本号同财务审批原子竞争，成功后释放占用并刷新订单余额和记录                                              | 若审批或其他操作先成功，返回最新状态，页面不擅自撤回并提示“申请已被处理，请刷新查看最新状态”           |
| S-06 | P0 已开票信息更正     | 原申请仅有一张成功蓝票且无进行中的红冲；用户针对该订单填写更正原因和目标信息，提交独立更正申请；审核通过后红冲，原蓝票需红冲的全部金额成功后系统创建唯一自动重开任务，系统自动提交重开       | 开票结果未知、红冲中或已有未终结更正时不可新建；结果未知只能查询，不能重复提交                   |
| S-07 | P1 超期支持指引      | 版本发布后订单超过自助期限；用户查看不可申请原因，页面明确提示联系平台支持，不在客户端创建人工开票工单                                                    | 平台支持或财务运营在后台核验交易和主体；客户端刷新后以服务端最新资格为准                      |
| S-08 | P0 重复提交与网络恢复   | 用户连续点击或提交响应超时；页面显示“正在确认提交”，使用原 submission_id 查询结果                                                 | 请求体一致返回当前订单原结果；请求体变化返回幂等冲突；禁止创建新 submission_id 盲目重提       |

### 1.0.3 边界条件汇总

### 1.0.3.1 开票能力版本与历史订单

|场景|服务端判定|客户端展示/操作|
|---|---|---|
|订单创建时间早于 `invoice_release_at`|`eligibility=INELIGIBLE`、`primary_reason_code=ORDER_BEFORE_INVOICE_RELEASE`|固定显示“不可申请”，查看原因；不提供恢复动作和申请入口|
|订单创建时间不早于 `invoice_release_at`，且支付/履约/退款/余额/税务均满足|进入正常资格计算并返回 `ELIGIBLE`|显示“可申请”，允许逐单申请一张发票|
|版本发布后订单超过 12 个月自助期限|`primary_reason_code=SELF_SERVICE_EXPIRED`|显示超期原因及联系平台支持指引；不与版本前历史订单混淆|

历史订单的不可申请是开票能力版本硬边界，不是可通过刷新、补配置或版本升级恢复的临时状态。线下财务核验不改变客户端的历史订单自助资格标记。

| 编号   | 触发条件                  | 系统判定与用户表现                                                   | 恢复方式                 |
| ---- | --------------------- | ----------------------------------------------------------- | -------------------- |
| B-01 | 支付方式为云币               | 订单不可申请，返回 `PAYMENT_NOT_ELIGIBLE`；行内仅提供查看原因，说明充值订单应在法币充值环节开票 | 无自助恢复                |
| B-02 | 法币充值支付成功              | 充值订单取得资格；可开票金额为法币实付净额                                       | 刷新列表后申请              |
| B-03 | 代理、套餐、续费已支付但未履约       | 返回 `FULFILLMENT_PENDING`，不进入可申请池                            | 完成履约后刷新              |
| B-04 | 开始时间晚于结束时间或超过查询跨度     | 阻止查询，字段就地提示；不发请求                                            | 修改日期后重试              |
| B-05 | 订单已全额退款、零法币实付或余额为零    | 返回相应原因；行内仅提供查看原因                                            | 查看原因                 |
| B-06 | 版本发布后订单取得资格超过 12 个月        | 返回 `SELF_SERVICE_EXPIRED`，不显示客户端人工工单入口                      | 查看原因并联系平台支持          |
| B-07 | 销售主体、税务映射或内容配置缺失      | 返回配置异常；不可提交并提示联系客服                                          | 等待后台配置后刷新            |
| B-08 | 当前订单销售主体或税务配置不兼容      | 单订单预览阻止提交并展示原因；金额只读                                         | 等待后台配置后刷新当前订单        |
| B-09 | 个人抬头选择专票              | 专票控件禁用并显示原因                                                 | 切换普票或企业抬头            |
| B-10 | 企业选填信息为空              | 允许继续；空值按申请快照保存，不显示伪造占位值                                     | 按需补充或保持为空            |
| B-11 | 同一订单被他人占用或状态变化        | 提交事务返回版本冲突；保留表单和失效订单                                        | 移除、刷新、重新预览           |
| B-12 | 同一 submission_id 重复提交 | 请求体一致返回原信封；请求体变化返回幂等冲突                                      | 查询原信封或生成新提交意图        |
| B-13 | 第三方结果未知               | 客户端保持“开票中”，不开放重提；后台先查询后决定                                   | 等待查询/后台核对            |
| B-14 | 开票成功但文件或邮件失败          | 主状态保持“已开票”，交付附加状态为发送失败或文件暂不可用                               | 重新获取或重发              |
| B-15 | 同一蓝票的第三方任务结果未知或明确失败   | 客户端仍按当前订单展示开票中/开票失败，任务细节仅后台可见                               | 后台查询或安全重试，不允许生成第二张蓝票 |
| B-16 | 两名审批人或用户撤回与审批同时提交     | 服务端以 `status=PENDING_REVIEW + version` 条件更新，仅一个命令成功         | 失败方刷新最新状态，不覆盖既有决定    |
| B-17 | 退款、用户更正和后台红冲并发        | 服务端按原蓝票账本和来源幂等键串行占额，不超过票面金额                                 | 用户查看结果；财务处理失败/未知子任务  |
| B-18 | 会话过期或权限中途变化           | 不持久化敏感字段；操作返回权限错误，不清空未提交非敏感选择                               | 重新登录并重新校验            |

### 1.1 背景与问题

费用管理高保真原型已拆分为四个独立页面，其中 `Prototype/费用管理-开票管理.html` 提供资格清单、三步申请、开票记录、常用抬头页内列表和票据演示操作；生产系统仍需交付与之匹配的资格、占额、审核、开具、交付、红冲和审计服务。原型页面不能替代服务端金额账本与第三方电子发票平台集成。

问题根因不是增加一个订单字段，而是缺少独立的发票申请、订单级开票关联、可开票余额、票据、交付、红冲和第三方任务模型。特别是法币充值与云币消费必须避免重复开票，支付、履约、退款和发票状态必须在页面上呈现为可解释的资格和动作。

本页面通过订单资格清单（可申请订单优先排序，支持按“是否可申请”筛选不可申请订单）、三步申请弹窗、开票记录、详情抽屉和常用抬头管理建立用户侧闭环；所有资格、金额、状态和权限仍以服务端返回为准。

### 1.2 一句话目标与成功指标

**一句话目标：**让有权限用户在 12 个月自助窗口内从法币支付且满足履约条件的订单提交准确、可追踪、不可重复占用的电子发票申请，并在异常时获得可恢复的下一步动作。

|指标|定义|目标|数据来源|
|---|---|---|---|
|自助申请完成率|成功提交申请数 / 进入申请流程且存在可开票订单的会话数|≥85%|客户端事件与服务端提交信封|
|资格计算准确率|财务抽样核对一致订单数 / 抽样订单数|100%|资格服务、财务对账|
|重复开票事故|同一订单金额被两张有效蓝票覆盖的次数|0|InvoiceableBalance 与票据对账|
|审核及时率|SLA 内完成审核申请数 / 待审核申请数|≥95%|后台审核日志|
|第三方最终一致率|与第三方核对一致的已提交记录 / 已提交记录|100%|ProviderTask 对账|
|交付成功率|至少一个交付渠道成功的已开票申请 / 已开票申请|≥99%|InvoiceDelivery|
|核心页面可交互耗时|列表接口返回并可操作的 P95|≤2 秒|前端性能监控|

#### 3.1.5 不可申请原因完整覆盖

原因弹窗仅显示一条主原因说明，不再重复显示“原因标题＋同义详情”；下方保留订单号、支付方式和订单金额，不展示原因码或恢复动作。订单金额取订单总额；保留关闭、遮罩、Escape 和“我知道了”。多原因按“权限 → 订单有效性 → 支付 → 履约/退款 → 占用或有效票据 → 期限 → 配置”选取主原因，其余原因保留在服务端数据中，不在弹窗重复罗列。订单本身已有退款、履约、支付等限制时不得被“发票申请中”覆盖。

|红冲原因|原订单在开票订单中的资格|处理规则|
|---|---|---|
|信息更正并自动重开|不可申请|系统在原申请单上自动创建新的开具版本并自动开票，用户不得再次普通申请。|
|销货退回、服务中止、全额退款|不可申请|已退款/终止服务金额不恢复开票资格；不得自动补开。|

验收：退款类红冲不恢复已退款金额；更正自动重开期间不出现申请入口；仅撤销且交易有效时可重新选单；原蓝票仍有有效金额、自动重开任务进行中或存在其他有效占用时不得恢复可申请。


### 3.2 申请开票弹窗

**页面目的：**在不允许用户修改金额和销售方的前提下，完成单订单确认、受票信息填写和提交确认。

**呈现形态：**三步 Modal，桌面宽度 760px、最大宽度 92vw，内容独立滚动。标题栏底部先显示分割线，分割线下的弹窗内容区顶部展示步进条“1 确认订单 → 2 填写信息 → 3 核对提交”，当前步骤和已完成步骤使用 primary 高亮，未到达步骤使用中性色。表单统一使用 90px 标签列和 400px 控件列，标签右对齐、控件左对齐且起点一致，间距 14px；输入框、下拉和单选组合控件高 30px，移动端控件列按可用宽度收缩。当前原型关闭按钮、取消、遮罩或 Esc 会直接关闭并丢弃内存表单；生产实现必须在检测到有效修改时增加未保存确认，此项属于原型模拟边界，不能据此降低数据保护要求。

#### 3.2.3 字段级校验

发票抬头右侧提供刷新图标。刷新保留所选抬头 ID，并同步最新名称、税号、银行、地址、电话和联系信息，成功提示“已刷新常用抬头信息，请核对后提交”并清空确认勾选；所选抬头已停用或删除时提示“当前抬头已停用或删除，请重新选择”，不静默套用其他抬头。新增和编辑的个人类型都禁选专票，保存与申请提交仍进行二次校验。

金额输入精确转换为整数分，汇总及占用计算使用整数运算，输出保留两位小数；不得仅将浮点运算结果 toFixed 后作为账本。接口采用整数分，越界或超过两位小数拒绝。已取消自助开票金额上限，不展示金额超限弹窗；开票申请仍按订单资格、支付方式、履约状态和税务配置校验。

### 3.4 开票记录与详情抽屉

#### 3.4.1 记录页签

结构化筛选字段固定为发票类型、开票状态和申请时间，在“筛选”打开的右侧抽屉中维护；申请单号、发票号码、开票订单、团队ID、申请人、发票抬头、金额等通过搜索框范围选择检索。记录页关键词搜索为范围搜索组合框：点击左侧范围前缀可选择搜索字段（全局搜索、申请单号、发票号码、开票订单、团队ID、申请人、申请时间、发票类型、发票抬头、金额、状态、发票编号），多关键词用中文逗号分隔、任一关键词命中即匹配（OR），搜索框即时生效并带清空按钮；抽屉条件确认后回第 1 页；取消、遮罩点击、关闭或 Escape 均丢弃重开任务。申请时间使用与订单管理创建时间一致的 300px 双端范围控件，显示“开始时间 ~ 结束时间”，支持双月日历、清空/取消/确定、单侧日期和逆序校验，按申请时间自然日闭区间筛选；逆序提交提示“开始申请时间不能晚于结束申请时间”。支付时间、申请时间两套日期筛选均以北京时间自然日为准，仅允许今天及以前，明天及未来日期禁选（日历禁选日期 hover 提示“只能选择今天及之前的日期”，确认及筛选提交校验失败 toast 同文案），历史缓存越界日期清空；未指定日期范围仍可看到当天记录，该限制只作用于日期筛选，不影响当天订单资格或申请。申请单号/发票号码为 `-` 或空值时不进入号码搜索索引，其他搜索字段按原逻辑匹配。开票状态选项为全部、待审核、开票中、已开票、已驳回、开票失败、红冲处理中、红冲失败、已红冲、已撤回、已取消。

表格固定为 12 列：申请单号、发票类型、发票抬头、发票号码、金额、申请时间、联系邮箱、开票订单、团队ID、申请人、开票状态、操作。状态使用纯语义色文字；工具栏左侧操作区提供"导出"与"刷新"按钮，右侧为搜索框与"筛选"入口，筛选旁显示当前筛选总数。“导出”弹窗提示“将按当前搜索与筛选条件导出 N 条开票记录。每次最多可导出 500 条数据”，确认后按当前条件导出。列表默认按状态分组升序排列，状态顺序为：待审核、已撤回、已驳回、已取消、开票中、开票失败、已开票、红冲处理中、红冲失败、已红冲；金额、申请时间等列仍支持手动升降序。申请单号提供复制按钮，成功提示“申请单号已复制”，失败提示“复制失败”；已驳回记录的开票状态旁提供“查看驳回原因”图标，无原因时展示兜底文案“暂无驳回原因，请联系财务确认”。每条记录包含末行均保留下边框；分页器距表格 20px，默认 10 条/页并支持 10、20、50 条/页。

### 3.5 更正申请与自动重开任务

用户只能对 `issuance_status=SUCCEEDED` 且蓝票有效、无进行中退款红冲/更正的申请发起更正。当前原型更正 Modal 固定包含：只读目标蓝票、更正原因（抬头信息有误、税号有误、票面内容有误、联系人信息有误、其他）、发票类型、更正抬头、只读更正税号、发票内容、联系邮箱、联系电话、最多 200 字更正说明和“全额红冲后生成唯一自动重开任务”确认声明。全部字段和确认声明均须校验；目标红冲金额由服务端按当前有效蓝票全额计算，不接受用户自定义。

更正主状态为 `PENDING_REVIEW`、`APPROVED`、`RED_PROCESSING`、`COMPLETED`，分支为 `REJECTED`、`WITHDRAWN`、`CANCELLED`、`RED_FAILED`；第三方待处理、提交中、红冲中、结果未知作为子状态展示。更正审批不设置领取或审批锁，有权限的管理员/财务以 `status=PENDING_REVIEW + version` 直接通过或驳回。驳回后创建新 `correction_request_id` 并关联 `previous_correction_request_id`，不覆盖旧记录。原蓝票需红冲的全部金额成功后，系统以 `correction_request_id` 幂等创建唯一自动重开任务；任务仍只关联原订单，系统自动提交开具，用户无需操作。

当前原型校验通过后把该记录的更正状态更新为“待审核”，保存原因、说明和更正快照，刷新列表/详情并提示“更正申请已提交，审核通过后将处理原发票红冲”；它不连接真实红冲任务，生产状态推进仍以服务端状态机为准。

红冲场景与业务边界（完整场景、金额示例及审计规则见[需求分析 §5.9.1—§5.9.2](./01-开票申请产品需求分析.md)）：

- 开票错误：数电票不以跨月或已报税作为红冲必要条件；平台更正策略为原票剩余有效金额全部红冲后，按已审核信息在原申请单自动创建新开具版本，不生成待用户提交草稿。
- 销货退回、销售折让、服务中止：以真实售后或结算依据确定对应的已开票减额，支持全额/部分红冲；部分红冲保留原票剩余有效金额，不重新补开剩余金额蓝票，不恢复已退款金额开票资格。
- 重复开票、误开、其他财务纠错：核验真实交易、目标原票和原因，保留证据；无真实交易不重开。“其他”不能绕过审核和金额校验。
- 仅撤销票据与信息更正自动重开分开：前者经财务审核全红成功后重算订单资格，用户需要时重新选原订单申请；后者全红成功且净额校验通过后自动重开。
- 客户端无需确认红冲，不提供确认按钮、确认指引或待用户处理状态；平台不增加红冲完成确认或重开二次确认，但不能免除税务红字信息确认。第三方要求受票方处理时应提供真实指引并等待可核验结果；红字信息确认成功不等于红票开票成功。外部平台若有额外税务处理要求，由后台跟进，未完成前保持处理中，不伪造成功。上线前财务及第三方确认具体条件。
- 退款红冲按该订单实际退款金额执行；部分退款仅减少原蓝票有效金额，全额退款终止该订单的开票额度，退款红冲不自动补开被退金额。退款到账不等待红冲，差异进入财务对账。
- 自动重开按 correction_request_id + 原蓝票标识幂等执行。金额以当前订单实付、退款、已红冲账本重新计算；原票仍有效、退款处理中或余额不足时暂停自动开具并交后台处理，不能覆盖金额、重复占用或生成第二张有效蓝票。临时任务创建失败由 Outbox 补偿；不开放用户重复重开入口。
- 申请状态保持已通过；重开版本开具状态依次为提交中、开票中、成功/失败/结果未知。客户端显示开票中、已开票或开票失败；红冲历史独立保留。红冲成功通知与新票开票成功通知分别记录。
- 单票按站内与邮件渠道独立交付，失败可重发，不改变开票成功。
- 红冲进度展示原因、原票、本次/累计红冲金额、剩余有效金额、状态及时间线；部分成功显示“已部分红冲”，更正全红主路径和部分退款路径不能混用。邮件发送失败、修改收票邮箱、常用抬头更新本身不触发红冲。
- 红冲进度弹窗使用 design.md 的圆角、边框、字号与间距，状态紧跟“当前状态：”右侧；处理进度为竖线＋圆点，显示已发生的节点名称、时间和内容。处理中显示查询进度，失败显示原因及等待财务处置；客户端不提供强制确认成功按钮。
- 进度弹窗按场景区分标题：开票中显示“开票处理进度”（引导文案“系统正在提交电子发票平台开票…”），红冲场景显示“红冲处理进度”。红冲进度字段包含：当前状态、关联订单、原蓝票号码、红冲金额、处理说明。任务失败或结果未知时弹窗底部提供“刷新结果”和“关闭”按钮，点击刷新重新查询最新进度。
- 已红冲记录详情展示“红票已由第三方电子发票平台开具成功，可下载票据文件”，预览下载按钮文案为“下载红票”。
- 已存在待审核更正申请时再次点击“申请更正”提示“更正申请已提交，请等待审核”；提交时再次校验则提示“更正申请已提交，请勿重复提交”。

通用流程：业务事件及证据核验 → 查询原票（未开票调整申请、未知先查询）→ 按原票幂等占额 → 核验税务前置条件（需对方确认则等待外部结果）→ 第三方红票开具 → 成功保存红票并结转账本 → 退款/折让结束，或仅撤销重算资格，或已审核更正自动重开并交付。失败/未知保留占用，查询或财务安全恢复。

验收：1,000 元原票部分退款/折让 200 元后有效净额为 800 元，不另开 800 元蓝票；全额退款不重开；无退款的抬头更正先全红再自动开新票；退款回调与同一折让事件不得重复红冲；税务确认未完成不得跳过；并发全额退款时终止自动重开。

### 3.6 超期支持指引

`SELF_SERVICE_EXPIRED` 订单只提供“查看原因”。760px 居中原因 Modal 明确展示订单已超过自助开票期限，并提示“请联系平台支持”。客户端不展示人工工单按钮、不打开人工工单弹窗，也不维护工单列表或状态；后续处理由平台支持和财务运营在后台完成，订单资格以刷新后服务端结果为准。

### 3.7 页面 Mock 数据与数据驱动要求

原型必须使用内联 JS 数组/对象驱动渲染，不在 HTML 中堆静态表格行。Mock 数据不得连接真实支付、订单、第三方发票或文件服务；用户可见开票字段使用合成值并完整展示，敏感字段仍不得进入 URL、存储、前端日志或埋点。

#### 3.7.1 订单 Mock 最小集合

当前原型提供 36 条资格订单，其中新增 20 条独立不可申请样例覆盖全部基础原因，不关联开票记录以避免场景互相覆盖；其他订单按关联记录派生已开票、占用、红冲或重开原因。每种原因均可通过“不可申请 → 查看原因”验证；筛选及分页按完整集合计算。生产联调与自动化测试仍须覆盖下表组合：

|Mock 场景|关键字段与预期|
|---|---|
|法币充值可申请|`eligibility=ELIGIBLE`、支付成功、余额大于 0|
|法币代理/套餐可申请|支付成功、履约成功、各有一个主体|
|法币续费未履约|`FULFILLMENT_PENDING`|
|云币消费|`PAYMENT_NOT_ELIGIBLE`|
|待支付/支付失败|`PAYMENT_PENDING`、`PAYMENT_FAILED`|
|部分退款|可开票余额小于法币实付|

#### 3.7.2 申请记录 Mock 最小集合

生产接口与联调 Fixture 每条记录至少包含：`application_id`、`application_status`、`issuance_status`、`document_status`、`delivery_status`、`client_status`、`invoice_type`、`title_name`、`taxpayer_id`、`content_name`、`amount`、`seller_name`、`applied_at`、`invoice_numbers`、`documents`、`deliveries`、`allowed_actions`、`timeline`。当前 HTML Mock 只保留列表、详情和操作演示所需的 `id/orders/created/type/title/tax/amount/status/no/email/phone` 及少量可选字段；用户可见页面按权限完整展示这些合成参数。

#### 3.7.3 抬头和异步任务 Mock

### 3.8 原型模拟边界

以下为当前 HTML 的演示简化，不得作为生产业务规则：

- 单订单预览展示一条订单和一张发票，第二步使用该订单表单；生产环境仍须在提交事务内校验开票主体、票种、税目、税率和内容兼容性。
- 关闭申请 Modal 不做未保存确认；生产实现检测到有效修改时必须二次确认。
- 已驳回可修改重提；开票失败仅在确认未开票且旧任务关闭后修改重提，补正仍只对应原订单，生产环境必须使用服务端补正草稿。
- 下载生成本地 HTML 演示文件，不是税务票据；生产环境必须再次鉴权并使用短时授权下载服务端文件。
- 重发成功 Toast 在原型中包含邮箱并立即更新 Mock；生产环境只能提示“发送任务已提交”，不得在 Toast 暴露收件邮箱，最终结果以异步交付状态为准。
- 当前原型用行渲染版本及表单打开版本拦截过期操作；可通过 `window.invoiceStatusAdapter` 接入已鉴权的服务端快照查询，记录页每 10 秒查询、窗口重新聚焦时查询，后台页隐藏时跳过，页面离开停止。未配置适配器时不声称已查询真实后台。生产推荐 WebSocket/SSE 推送，失败回退轮询；操作提交仍由后端校验，不能依赖最后一次轮询。
- 多标签页原型以浏览器命令互斥和共享状态版本演示竞争，不存储抬头、税号和联系人。跨标签页命令通过 `navigator.locks` 请求共享键 `yundeng.invoice.lifecycle.v4-status-examples` 原子执行（读取共享状态 → 执行命令 → 发布新状态）；环境不支持 Web Locks 时提示“当前预览环境不支持跨标签页原子操作，请使用本地 HTTP 预览”。`storage` 事件感知其他标签页变更后刷新列表并提示“申请已被其他用户处理，列表已更新”。生产采用服务端原子条件更新、请求幂等与权限校验。
- 远端状态同步：窗口重新聚焦触发查询；记录页每 10 秒轮询一次；`pagehide` 时清除轮询定时器。查询到状态变化提示“申请处理状态已更新，请查看最新结果”；查询失败提示“状态查询失败，请稍后刷新；当前操作尚未确认”，不改变本地占用。生产推荐 WebSocket/SSE 推送，失败回退轮询；操作提交仍由后端校验，不能依赖最后一次轮询。

### 5.4 并发、幂等与一致性

|场景|约束/方案|用户可见结果|
|---|---|---|
|连续点击提交|前端按钮 loading；`submission_id` 和 `(submission_id, order_id)` 唯一|只创建一条申请和一张发票|
|多人申请同订单|服务端锁定当前订单账本、校验 version 和余额|一方成功，另一方收到最新冲突|
|并发审核/撤回竞争|普通申请和更正申请均以 `status=PENDING_REVIEW + version` 条件更新；短事务内可锁订单/原票账本，禁止跨请求审批锁|仅一个命令成功，失败方刷新最新状态|
|订单提交失败|单订单事务回滚，确认未开票且旧任务关闭后创建补正草稿|原失败版本只读，原申请补正版本仍只对应原订单|
|网络超时|查询提交信封；结果未知不新建 ID|按钮保持确认中，最终结果可追溯|
|抬头并发编辑|`title_profile.version` 乐观锁|保留输入，提示对比后重试|
|打包/重发任务重复|`archive_id`/request_id 幂等，任务持久化|刷新页面不创建重复任务|
|退款/更正/财务红冲竞争|统一原票级红冲账本和来源键，金额总和不超过原票|详情展示成功/占用/失败金额|

开票记录中的待审核撤回、已驳回/已撤回/开票失败修改重提均须携带 request_id 和 expected_version，由服务端按当前状态原子校验；冲突时 Toast 告知实际最新状态并刷新列表、详情和时间线，不新增申请单、不重复释放占用。网络超时进入“提交结果待确认，请刷新查看”，未知结果只能查询。在入口、最终确认及提交事务均须再次核对版本和状态：已被撤回、财务已通过、已被重提或补正分别提示实际原因；重复请求返回原结果，不新增申请或重复释放金额。重提/补正、撤回、更正、重发、抬头编辑均需校验对象存在、权限、状态和版本；同键同载荷重放返回同结果，同键异载荷拒绝；未知结果只查询，不生成新请求绕过。历史版本和第三方旧任务回调不得覆盖新版本。退款、第三方回调、红冲、重发、抬头编辑和多标签页重复提交沿用同一版本、幂等和迟到事件归属规则。

原单重提与版本审计规则：

- 已驳回或已撤回后修改重提，或开票失败后修改重提，均保留原 `application_id` 和原订单；提交成功新增不可变 `revision`，对象 `version` 递增，当前状态更新为 `PENDING_REVIEW`，开具状态重置为 `NOT_SUBMITTED`。首次申请时间保留，另记最近提交时间；列表保持一条申请记录。
- 原版本完整保存票种、抬头、税号、内容、金额、联系人、企业信息、申请人及审核/失败结果；审核人、处理时间、原因与第三方任务关联在审计事件中永久保留。详情时间线按先后追加修改重提或补正提交事件，并可展开历史提交快照，不能只保存一条文字日志。
- 开票失败补正必须有确认未开票证据、旧任务已关闭且不可重试；仅 `canRemediate` 标记不足以授权。旧版本保留已通过与失败事实，新版本重新审核；旧任务迟到事件只归属旧版本，不得改写当前版本。
- `POST /billing/invoice-applications/{id}/revisions` 的状态和版本条件更新、资格复核、单订单唯一有效占用、版本快照及事件写入必须在同一事务完成；任一失败全部回滚。已生成有效蓝票、结果未知、红冲中或其他申请占用时拒绝。
- 红冲失败不开放修改重提或普通补正，只允许核对后安全恢复原红冲任务。原票完成红冲后的重开在原申请单上自动创建新的开具版本；独立更正申请驳回后的版本链不变，与普通申请原单重提分开。
- 验收：连续提交或旧版本提交只成功一次；多次驳回再重提始终同号且版本递增；失败补正只保留一份占用；原票有效/结果未知/任务未关闭时拒绝；历史快照不可变；红冲失败不回待审核；原票红冲后的重开仍关联原申请单的新开具版本。

一票一单统一约束的原子性要求：同一订单同一时点最多存在一条有效申请占用和一张仍有有效金额的蓝票；占用转为蓝票时须原子结转，已有有效蓝票不得再次普通申请。更正重开必须先将原蓝票剩余有效金额全部红冲，再为原订单创建唯一关联草稿；部分退款的红票、已红冲旧蓝票及重开版本属于同一订单历史，不得产生两张同时有效的蓝票。更正接口只接收单个 `source_document_id` 及其版本，必须属于 `source_application_id` 对应的同一订单，拒绝票据数组和跨订单目标。服务端必须同时校验订单资格、版本、占用及有效蓝票，不能只依赖前端单选或金额余额。

### 6.3 异步任务约定

提交信封、第三方开票、文件补拉、打包下载、邮件发送和红冲均须持久化任务。前台可见时每 5–10 秒轮询对应查询接口；离开页面停止轮询，重新进入按任务 ID恢复。状态由后端返回，不由前端估算。任务结果文件使用短时签名 URL，过期后最多自动重新获取一次；重试必须有 request_id/幂等键和最大次数，结果未知必须先查询真实结果。

### 开票记录与详情字段同步

团队ID 对应 `teamId`，使用等宽字体，位于申请人左侧；申请人对应 `applicant`，展示脱敏登录账号（手机号或邮箱，例如 `138****8001`、`li***@example.com`），不展示昵称，且与发票联系邮箱独立。列表、详情及历史提交快照使用同一申请身份；新申请取当前登录身份，修改重提保留原团队ID和申请人。缺失值显示 `-`，不得用收票邮箱推断申请账号。生产由服务端返回已鉴权、已脱敏的身份字段。

全局搜索及指定字段搜索支持团队ID、申请人账号。

初始 Mock 固定 10 条，每种状态一条，默认按业务阶段及异常分支排列：待审核、已撤回、已驳回、已取消、开票中、开票失败、已开票、红冲处理中、红冲失败、已红冲。金额和申请时间支持用户手动升降序排序；该顺序用于样例展示，不表示所有状态构成单一迁移链。操作后状态按实际交互更新，不强制维持每状态一条。新版 Mock 缓存不导入旧演示数据。

详情底栏按当前状态展示：待审核为关闭、撤回；已驳回/已撤回/开票失败为关闭、修改重提；开票中/红冲处理中/红冲失败为关闭、查看进度；已红冲为关闭、查看红票；已取消仅关闭；已开票为重发、更正、下载、预览。沿用原操作校验。底栏遵循 design.md §5.7：高 64px、左右内边距 24px、按钮右对齐、间距 12px；按钮遵循 §5.1：32px 高、4px 圆角，主按钮蓝底白字、次按钮白底描边，包含 hover/active/focus-visible 状态。
