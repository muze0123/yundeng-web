# YunLogin 开票业务流程

### 红冲场景统一补充（2026-09-08）

完整场景、金额示例及审计规则见[需求分析 §5.9.1—§5.9.2](./01-开票申请产品需求分析.md)。本补充优先于本文旧有的“无需确认/不提供确认指引”等笼统描述。

- 开票错误：数电票不以跨月或已报税作为红冲必要条件；平台更正策略为原票剩余有效金额全部红冲后，按已审核信息在原申请单自动创建新开具版本，不生成待用户提交草稿。
- 销货退回、销售折让、服务中止：以真实售后或结算依据确定对应的已开票减额，支持全额/部分红冲；部分红冲保留原票剩余有效金额，不重新补开剩余金额蓝票，不恢复已退款金额开票资格。
- 重复开票、误开、其他财务纠错：核验真实交易、目标原票和原因，保留证据；无真实交易不重开。“其他”不能绕过审核和金额校验。
- 仅撤销票据与信息更正自动重开分开：前者经财务审核全红成功后重算订单资格，用户需要时重新选原订单申请；后者全红成功且净额校验通过后自动重开。一单一票、不合并订单、不同时存在两张有效蓝票。
- 平台不增加红冲完成确认或重开二次确认，但不能免除税务红字信息确认。第三方要求受票方处理时应提供真实指引并等待可核验结果；红字信息确认成功不等于红票开具成功。上线前财务及第三方确认具体条件。
- 进度展示原因、原票、本次/累计红冲金额、剩余有效金额、状态及时间线。部分成功显示“已部分红冲”；更正全红主路径和部分退款路径不能混用。邮件发送失败、修改收票邮箱、常用抬头更新本身不触发红冲。

通用流程：业务事件及证据核验 → 查询原票（未开票调整申请、未知先查询）→ 按原票幂等占额 → 核验税务前置条件（需对方确认则等待外部结果）→ 第三方红票开具 → 成功保存红票并结转账本 → 退款/折让结束，或仅撤销重算资格，或已审核更正自动重开并交付。失败/未知保留占用，查询或财务安全恢复；退款到账不等待红冲，差异进入财务对账。

验收：1,000 元原票部分退款/折让 200 元后有效净额为 800 元，不另开 800 元蓝票；全额退款不重开；无退款的抬头更正先全红再自动开新票；退款回调与同一折让事件不得重复红冲；税务确认未完成不得跳过；并发全额退款时终止自动重开。


> **一票一单统一约束（2026-09-07）**：每份普通申请必须且只能关联一个 `order_id`，每份申请最多生成一张蓝票，每张蓝票或关联红票只能归属该订单。申请金额为该订单全部剩余可开票金额，不允许合并订单、批量申请、拆分金额或拆成多张蓝票；配置不兼容时阻止提交；不以拆票绕过。服务端必须同时校验订单资格、版本、占用及有效蓝票，不能只依赖前端单选或金额余额。
> 同一订单同一时点最多存在一条有效申请占用和一张仍有有效金额的蓝票；占用转为蓝票时须原子结转，已有有效蓝票不得再次普通申请。驳回、撤回、取消和安全关闭后的补正可保留历史申请；更正重开必须先将原蓝票剩余有效金额全部红冲，再为原订单创建唯一关联草稿。部分退款的红票、已红冲旧蓝票及重开版本属于同一订单历史，不得产生两张同时有效的蓝票。
> 普通开具任务只处理唯一目标蓝票，不存在 `issuance_status=PARTIAL`；重试与回调不得新增蓝票。更正接口只接收单个 `source_document_id` 及其版本，必须属于 `source_application_id` 对应的同一订单，拒绝票据数组和跨订单目标。部分红冲金额与多渠道部分送达属于后续处理状态，不代表部分开票。

### 原单重提与版本审计（本次确认）

- 普通申请已驳回或已撤回后修改重提，或开票失败后修改重提，均保留原 `application_id` 和原订单；提交成功新增不可变 `revision`，对象 `version` 递增，当前状态更新为 `PENDING_REVIEW`，开具状态重置为 `NOT_SUBMITTED`。首次申请时间保留，另记最近提交时间；列表保持一条申请记录。
- 原版本完整保存票种、抬头、税号、内容、金额、联系人、企业信息、申请人及审核/失败结果；审核人、处理时间、原因与第三方任务关联在审计事件中永久保留。详情时间线按先后追加修改重提或补正提交事件，并可展开历史提交快照，不能只保存一条文字日志。
- 开票失败补正必须有确认未开票证据、旧任务已关闭且不可重试；仅 `canRemediate` 标记不足以授权。旧版本保留已通过与失败事实，新版本重新审核；旧任务迟到事件只归属旧版本，不得改写当前版本。
- 提交接口 `POST /billing/invoice-applications/{id}/revisions` 接收 `request_id`、预期 `version`、原单 `order_id` 和完整表单快照；同一 request_id 重放返回同一结果，载荷变化拒绝。状态和版本条件更新、资格复核、单订单唯一有效占用、版本快照及事件写入必须在同一事务完成；任一失败全部回滚。已生成有效蓝票、结果未知、红冲中或其他申请占用时拒绝。
- 原型在入口和提交时校验状态、版本、其他有效申请/蓝票及补正条件；成功后原行进入待审核，重提入口消失，失败保留表单。生产中的多人/多窗口并发与幂等由服务端保证，不能以原型本地数组替代。
- 红冲失败不开放修改重提或普通补正，只允许核对后安全恢复原红冲任务。原票完成红冲后的重开在原申请单上自动创建新的开具版本；独立更正申请驳回后的版本链不变，与普通申请原单重提分开。
- 验收：连续提交或旧版本提交只成功一次；多次驳回再重提始终同号且版本递增；失败补正只保留一份占用；原票有效/结果未知/任务未关闭时拒绝；历史快照不可变；红冲失败不回待审核；原票红冲后的重开仍关联原申请单的新开具版本。


### 本轮页面与交互补充

- 已撤回、已驳回、开票失败均提供“修改重提”，提交前校验未开票、旧任务关闭、最新状态和版本。三者保留原申请单号、原订单及首次申请时间；提交新增版本、当前状态回待审核、旧入口消失，详情时间线保留各轮操作和快照。取消申请仍按取消规则处理，不能与撤回混用。
- 撤回确认文案：“撤回后，本次申请将停止处理。如财务已审核通过，则无法撤回。是否继续？”入口、确认、提交均按最新状态及预期 version 校验。被其他操作撤回提示“该申请已被撤回”；已审核通过提示无法撤回；被重新提交提示正在待审核；其他变更提示最新状态。拒绝请求不得释放占用或追加成功事件。
- 重提/补正、撤回、更正、重发、抬头编辑均需校验对象存在、权限、状态和版本。创建、更正、重发等写请求携带 request_id；同键同载荷重放返回同结果，同键异载荷拒绝；未知结果只查询，不生成新请求绕过。前端禁用只能改善体验，服务端必须原子比较更新。历史版本和第三方旧任务回调不得覆盖新版本。
- 当前原型用行渲染版本及表单打开版本拦截过期操作；可通过 `window.invoiceStatusAdapter` 接入已鉴权的服务端快照查询，记录页每 10 秒查询、窗口重新聚焦时查询，后台页隐藏时跳过，页面离开停止。未配置适配器时不声称已查询真实后台。生产推荐 WebSocket/SSE 推送，失败回退轮询；操作提交仍由后端校验，不能依赖最后一次轮询。
- 发票抬头右侧增加刷新图标。刷新保留所选抬头 ID，并同步最新名称、税号、银行、地址、电话和联系信息；修改后的信息需再次确认。停用或删除时提示重新选择，不静默套用其他抬头。新增和编辑的个人类型都禁选专票，保存与申请提交仍进行二次校验。
- 金额输入精确转换为整数分，汇总及占用计算使用整数运算，输出保留两位小数；不得仅将浮点运算结果 toFixed 后作为账本。接口采用整数分，越界或超过两位小数拒绝。
- 支付时间、申请时间两套日期筛选均以北京时间自然日为准，仅允许 T-1（昨天）及以前。今天和未来日期禁选，确认及筛选提交再次校验，历史缓存越界日期清空。未指定日期范围仍可看到当天记录；T-1 只限制日期筛选，不影响当天订单资格或申请。
- 发票号码为 `-`、空值时不进入号码搜索索引；其他搜索字段按原逻辑匹配。
- 已取消自助开票金额上限，不展示金额超限弹窗；开票申请仍按订单资格、支付方式、履约状态和税务配置校验。
- 红冲进度弹窗使用 design.md 的圆角、边框、字号与间距，状态紧跟“当前状态：”右侧；处理进度为竖线＋圆点，显示已发生的节点名称、时间和内容。处理中显示查询进度，失败显示原因及等待财务处置；客户端不提供强制确认成功按钮。

### 红冲与自动重开（2026-09-08 确认）

1. 客户端无需确认红冲，不提供确认按钮、确认指引或待用户处理状态。第三方处理成功后告知用户已红冲；结果未知继续查询，明确失败由财务安全重试。外部平台若有额外税务处理要求，由后台跟进，未完成前保持处理中，不伪造成功。
2. 退款红冲按该订单实际退款金额执行；部分退款仅减少原蓝票有效金额，全额退款终止该订单的开票额度。退款红冲不自动补开被退金额。
3. 信息更正或财务纠错需要重开时，后台审核固化更正快照；唯一原蓝票剩余有效金额全部红冲成功后，服务端在同一申请单上创建下一开具版本并自动写入重开 Outbox，无需用户再次确认、提交或审核。保留原 application_id、order_id、旧蓝票与红票及不可变版本快照。
4. 自动重开按 correction_request_id + 原蓝票标识幂等执行。金额以当前订单实付、退款、已红冲账本重新计算；原票仍有效、退款处理中或余额不足时暂停自动开具并交后台处理，不能覆盖金额、重复占用或生成第二张有效蓝票。临时任务创建失败由 Outbox 补偿；不开放用户重复重开入口。
5. 申请状态保持已通过；重开版本开具状态依次为提交中、开票中、成功/失败/结果未知。客户端显示开票中、已开票或开票失败；红冲历史独立保留。红冲成功通知与新票开具成功通知分别记录。
6. 单票按站内与邮件渠道独立交付，失败可重发，不改变开具成功。客户端红冲进度展示“当前状态：状态值”和竖线圆点时间线，只显示已发生的事件。

## 1. 泳道定义

主流程以“受票方 / 开票方”两大参与方呈现，并细分系统执行责任：

|主泳道|子泳道|职责|
|---|---|---|
|受票方|YunLogin 用户|选单、填写、确认、撤回、修改重提、接收票据、必要时确认红字信息|
|受票方|YunLogin 客户端|展示资格、单订单预览、表单校验、状态映射、站内预览与下载|
|开票方|云登发票服务|权威资格校验、金额占用、状态机、第三方任务、回调、文件、交付、红冲与对账|
|开票方|财务管理员|在授权销售主体范围内直接通过/驳回、异常重试、红冲处置和审计；不领取审批锁|
|开票方|第三方电子发票平台|开具蓝票/红票、返回受理与终态、提供票据文件|

“第三方平台”是开票方的受托技术执行方，不改变订单销售主体作为法定开票方的业务责任。

## 2. 前置条件

### 2.1 订单资格

订单进入自助可开票池必须同时满足：

1. 当前用户具有订单数据权限；
2. 支付方式为支付宝、微信、银联等法币渠道，不是云币；
3. 云币充值订单已支付成功；或代理、套餐、续费订单已支付成功且履约完成；
4. 不是零元、赠送、兑换或全额退款订单；
5. 当前可开票余额大于 0；
6. 资格取得时间未超过 12 个月；
7. 开票主体和发票内容税务映射有效；
8. 不存在覆盖同一金额的有效申请占用或蓝票。

超过 12 个月只退出自助池，仍可进入人工核验流程；不得直接视为永久不可开票。

### 2.2 金额口径

```text
资格法币净额 = 已确认法币实付金额 - 已确认退款金额
当前可开票余额 = max(0,
  资格法币净额
  - 有效申请占用金额
  - 未被红冲的有效蓝票金额
)
```

展示金额是预览；提交、审核通过、退款和红冲完成时均由服务端重新计算。

“有效申请占用金额”是尚未释放且尚未转为有效蓝票的单订单占用金额，包括待审核、已通过待提交、提交中、开票中、结果未知和失败待处置。驳回/撤回/取消需在服务端释放后才退出占用；失败待补正需确认未开票并关闭旧任务后释放；成功金额转为有效蓝票，不重复计入两处。

### 2.3 当前客户端承载边界

- 用户从费用管理一级页签“开票管理”直接进入独立页面；页面不设置订单管理返回按钮或面包屑。
- 独立页面包含“开票订单”“开票记录”和“常用抬头”三个同级 Tab，常用抬头以页内数据列表呈现并提供搜索、筛选和新增；超期订单通过居中原因 Modal 提示联系平台支持，客户端不创建人工开票工单。
- 当前 HTML 用 Mock 数据演示资格筛选、三步申请、记录、详情、预览、下载、重发和更正；本流程中的服务端占额、审核、第三方开具、文件授权和异步交付仍是生产实现要求。
- 原型中的直接修改重提、本地 HTML 下载、即时重发成功和关闭表单不确认均为演示简化，不改变本文件定义的安全恢复、幂等、补正草稿和异步结果规则。

客户端业务基线为“一订单一张发票”：订单列表不支持多选、跨页选择、批量申请或合并开票；每个申请只携带一个 `order_id`，申请成功后只生成一条申请和一张有效蓝票。客户端主状态不展示“部分开票异常”或“已部分红冲”，相关子任务/金额仅保留在后台用于查询和补偿。

## 3. 正常开票主流程

|步骤|责任方|输入/触发|系统动作|输出/状态|
|---|---|---|---|---|
|F-01|用户|进入“费用管理 > 开票管理”一级页签（`index.html?page=billing-invoice`）|客户端请求可开票订单|展示本人或团队权限范围内订单|
|F-02|客户端/发票服务|筛选条件|服务端鉴权并计算每单余额、主体、内容兼容项和原因码|可申请/不可申请解释列表|
|F-03|用户|点击一笔可申请订单的“申请开票”|客户端请求该订单预览|待确认单订单|
|F-04|发票服务|单个订单 ID + version|重新读取资格，校验销售主体和税务兼容性，返回固定一张发票的金额|单订单申请预览|
|F-05|用户|确认订单|选择发票类型、抬头、发票内容，填写邮箱和电话|完整单订单申请表单|
|F-06|客户端|点击下一步|执行必填、格式、个人/专票和内容兼容预校验|确认页或字段错误|
|F-07|用户|核对并提交|客户端生成稳定 submission_id 并携带单个 order_id + version，按钮进入确认中|一个单订单提交信封|
|F-08|发票服务|提交信封|单订单事务内重新鉴权、锁定订单账本、重算余额和资格|订单成功占用或明确失败|

## 4. 审核驳回、撤回与重新提交

### 4.1 用户撤回

```text
待审核 -> 用户点击撤回 -> 服务端尝试申请版本锁
  -> 若 status=PENDING_REVIEW 且 version 匹配：申请变为已撤回，释放订单金额占用
  -> 若管理员/财务审批已先成功：撤回失败，返回最新状态
```

撤回后原申请保留历史；用户点击“修改重提”，在原单编辑新版本，重新校验资格后回到待审核，不新建申请单号。

### 4.2 财务驳回

1. 有权限的管理员或财务从待审核详情选择结构化驳回原因；
2. 服务端保存驳回版本和说明；
3. 对可修改重提的原因释放占用并通知用户；
4. 用户点击“修改并重新提交”，系统复制原表单快照；
5. 系统先重新校验原订单资格；
6. 用户修正字段并提交，保留原申请 ID，新增不可变提交版本并递增 version；
7. 原申请当前状态回到待审核，历史版本永久保留驳回事实。

普通申请和更正申请都不设置领取或审批锁。管理员/财务的通过、驳回和用户撤回均以 `status=PENDING_REVIEW + version` 条件更新；旧页面提交返回版本冲突和最新状态，不能覆盖先成功的决定。

### 4.3 不允许直接修改的状态

- 已通过或已驳回：审批决定已形成，原申请只读；
- 开票提交中、开票中、结果未知：第三方可能已受理；
- 已开票：必须先红冲；
- 红冲中：等待红冲终态。

## 5. 第三方开具异常

### 5.1 明确失败

第三方明确返回未受理或开票失败：

- 开具状态变为“开票失败”；
- 保留金额占用，避免用户在管理员判断期间重新申请；
- 管理员根据归一化错误修复配置；
- 重试复用原 provider_request_id，或在确认旧请求未受理并关闭后生成新任务；
- 若需要用户修改信息，管理员执行“关闭旧任务并要求补正”：必须先取得第三方未开票证据，关闭旧任务且永久禁用其重试，再释放占用、开放补正入口并通知用户；用户点击后由服务端按来源申请与处置版本幂等创建/读取补正草稿，再从该草稿提交原申请的新版本。关闭事件本身不自动生成草稿；补正提交前原申请保持“已通过 + 开票失败”；提交后新版本回到待审核，旧版本保留原审核和失败事实。

这里的“开具失败补正”只处理尚未生成蓝票的资料/配置错误，不创建 `InvoiceCorrectionRequest`；后者仅用于已生成蓝票后的信息更正，必须先走红冲。

### 5.2 请求超时/结果未知

超时不能判定失败：

```text
第三方请求超时
  -> ProviderTask = UNKNOWN
  -> 金额继续冻结，客户端仍展示“开票中”
  -> 按请求号/受理号主动查询
     -> 查询成功：按真实终态处理
     -> 查询明确不存在：记录证据后允许安全重试
     -> 长时间未知：进入财务人工核对，不允许用户重提
```

### 5.3 重复与乱序回调

- 回调先写入 Inbox；
- 验签失败进入隔离队列，不更新业务状态；
- 相同 event ID/事件指纹只处理一次；
- 旧版本“处理中”不得覆盖已经落库的“成功/失败”；
- 重放回调可以重新触发未完成的文件补拉或交付，但不能重复创建票据。

### 5.4 唯一蓝票任务异常（后台内部）

- 每份申请只对应一个蓝票开具目标，不拆分票据或金额；发送尝试记录与业务开具目标分离。
- 超时或结果未知时保留占用，只查询原请求；不得创建并行开具任务。
- 明确失败后可安全重试原请求；只有取得未受理证据并关闭旧任务后才能创建替代任务，替代任务仍绑定同一申请和唯一蓝票目标。
- 蓝票成功后原子结转全部申请占用，重复或乱序回调返回同一票据；禁止再次开具。
- 无蓝票且第三方明确失败时显示“开票失败”，处理中或未知时显示“开票中”；前后台均不生成部分开票状态。
- 需要补正时先确认未开票并关闭旧任务，再开放原订单的补正草稿。

## 6. 票据文件与交付异常

### 6.1 文件补拉失败

第三方已确认开票成功，但 PDF/OFD/XML 获取失败：

- 开具状态保持“开票成功”；
- 票据记录已存在，文件状态标记异常；
- 后台自动重试补拉并告警；
- 客户端显示“已开票，文件暂不可用”；
- 不允许为此重新开具。

### 6.2 邮件失败

- 站内票据与开票状态不受影响；
- 邮件渠道标记发送失败，交付可为“部分送达”；
- 用户或管理员可重新发送到本次指定邮箱；
- 重发不修改申请、抬头或原交付记录；
- 频控：同一发票 60 秒内最多一次，每日最多 5 次，后台应支持受控豁免。

## 7. 退款、红冲与重新开票

### 7.1 退款发生在尚未开票阶段

|当前阶段|处理|
|---|---|
|选单/填表|提交时重新校验，移除或更新退款订单金额|
|待审核|自动取消当前订单申请并释放该订单占用|
|提交第三方前|取消开具任务并按退款金额调整/取消申请|

### 7.2 退款与第三方提交并发

若 ProviderTask 已提交、开票中或结果未知：

1. 不创建第二张蓝票，也不直接释放占用；
2. 等待查询得到第三方终态；
3. 若明确未开票，取消/调整申请并处理退款；
4. 若已经开票，立即创建对应金额红冲任务；
5. 退款资金到账不等待红冲，但红冲任务必须进入财务 SLA 和告警。

### 7.3 已开票后退款

```text
退款审批通过
  -> 以 source_type=REFUND + refund_id + invoice_document_id 识别来源幂等，金额作为不可变载荷校验
  -> 锁定原票统一红冲账本，重算可红冲余额并创建 InvoiceRedAllocation
  -> 在同一事务内占用金额，判断全额/部分红冲及是否第三方需额外处理
  -> 调用第三方红冲
  -> 成功：保存红票、更新蓝票关系、重算可开票余额、交付红票
  -> 失败/未知：金额继续冻结，进入查询/重试/人工核对
```

统一金额规则适用于退款、用户更正和后台人工红冲：

```text
原票可红冲余额 = 原蓝票金额 - 成功红冲金额 - 有效红冲占用金额
有效红冲占用 = 第三方待处理 + 待提交 + 红冲中 + 结果未知 + 失败待处置
0 <= 成功红冲金额 + 有效红冲占用金额 <= 原蓝票金额
```

同一来源事件重复投递返回原 `InvoiceRedAllocation`；不同来源同时到达时，以原蓝票账本锁内先成功提交的事务取得占用，后到请求只能占用剩余余额。红冲失败不自动释放，只有确认第三方未受理并关闭任务后才释放，避免未知结果与新任务重叠。

### 7.4 用户信息错误更正

用户信息错误更正使用独立对象 `InvoiceCorrectionRequest`，不把原 `InvoiceApplication` 回退为已驳回，也不直接修改已开票快照。

1. 用户在已开票详情填写更正信息，只读展示当前订单唯一有效蓝票、结构化原因和期望更正快照；提交时目标金额必须等于该蓝票当前有效金额，服务端创建 `correction_request_id`，固化不可变快照并进入 `PENDING_REVIEW`。
2. 更正申请不设置领取或审批锁。授权管理员/财务使用 `status=PENDING_REVIEW + version + request_id` 直接通过或驳回；审核驳回进入 `REJECTED` 并保存结构化原因，原蓝票继续有效。
3. 被驳回后用户复制最新快照修改并提交新的 `correction_request_id`，通过 `previous_correction_request_id` 形成版本链；原更正单、审核人、证据和决定永久保留。待审核可撤回为 `WITHDRAWN`，撤回与直接审批按同一版本原子竞争。
4. 审核通过命令在同一事务重新校验该订单唯一原蓝票，锁定其统一红冲账本并原子占额。信息更正必须覆盖提交快照中的唯一原蓝票的全部有效金额；若退款/财务纠错已有占用、金额已变化或该原票余额不足，整个命令失败且不产生部分占用，返回冲突供审核员驳回，用户基于最新事实创建关联的新更正单。
5. 事务成功后更正进入 `APPROVED` 并创建关联 RedTask，任务开始后更正进入 `RED_PROCESSING`。第三方待处理、提交中、红冲中和结果未知均是 RedTask 子状态；结果未知只允许查询，更正聚合状态仍为 `RED_PROCESSING`。无处理中/未知任务且任一目标明确失败时更正为 `RED_FAILED`，占用保持并仅恢复具体失败子任务。
- 更正审核通过后，原蓝票剩余有效金额全部红冲成功，系统在原申请单上新增开具版本，按 correction_request_id 幂等自动提交重开；保留原订单、原票与红票历史。金额冲突暂停至后台处理，用户无需再次确认。
7. 系统按已审核更正快照及最新订单金额自动创建重开版本；校验成功即提交第三方开具，无需用户确认。
8. 红冲成功和自动重开通过 Outbox 及幂等键连接，任务失败由后台补偿，不允许重复生成有效蓝票。

更正请求状态如下：

```text
PENDING_REVIEW -> APPROVED -> RED_PROCESSING -> COMPLETED
       |             |                           |
       +-> REJECTED  |                           +-> RED_FAILED -> 安全重试 -> RED_PROCESSING
       |                  -> 新 correction_request_id + previous_correction_request_id
       +-> WITHDRAWN

审批前原票已无有效金额 -> CANCELLED
RedTask 待确认 / 提交中 / 红冲中 / UNKNOWN -> 更正申请均保持 RED_PROCESSING
- 更正审核通过后，原蓝票剩余有效金额全部红冲成功，系统在原申请单上新增开具版本，按 correction_request_id 幂等自动提交重开；保留原订单、原票与红票历史。金额冲突暂停至后台处理，用户无需再次确认。
```

### 7.5 第三方红冲结果

客户端只查看处理进度；第三方确认红票成功后显示已红冲。信息更正按本文件“红冲与自动重开”规则自动继续，不要求用户确认。

## 8. 并发场景与裁决规则

### 8.1 两名用户同时申请同一订单

|时序|用户 A|发票服务|用户 B|
|---|---|---|---|
|1|提交订单 O1|—|几乎同时提交 O1|
|2|—|按订单 ID 锁定账本，先处理 A|等待锁|
|3|收到成功申请|占用 O1 全部余额并提交事务|—|
|4|—|处理 B 时重算余额为 0|收到版本冲突/已占用提示|

裁决：先成功提交事务的一方获得占用；不是按前端点击时间或请求到达顺序口头判定。

### 8.2 用户撤回与管理员审批同时发生

- 两个命令均携带相同申请 version；
- 服务端只允许一个条件更新成功；
- 撤回先成功：管理员审批失败并刷新为已撤回；
- 审批先成功：用户撤回失败并刷新为已通过或已驳回；
- 失败方不得本地乐观改状态。

### 8.3 管理员并发审核

- 任一授权管理员或财务都可从待审核直接提交决定，不存在“我的审批”或锁持有人；
- 审核通过/驳回使用 `request_id + application_version`，并以 `status=PENDING_REVIEW + version` 条件更新；
- 重复点击返回第一次结果；
- 另一管理员基于旧版本提交时返回冲突和最新状态。

### 8.4 第三方超时后管理员点击重试

- `UNKNOWN` 状态不提供普通“重试开票”按钮，只提供“查询结果”；
- 只有主动查询明确未受理后 `allowed_actions` 才包含重试；
- 人工确认未受理必须填写依据并留下审计；
- 任何重试前再次按原请求号查询一次。

### 8.5 退款、更正与人工红冲并发

- 三类来源共用原票级 `InvoiceRedAllocation`，来源类型固定为 `REFUND`、`USER_CORRECTION`、`FINANCE_CORRECTION`，来源幂等键为 `source_type + source_business_id + invoice_document_id`；金额属于不可变请求载荷，相同键金额不一致必须报幂等冲突。同一来源重复请求返回已有分摊和任务。
- 仅有来源幂等键仍不够：创建任意红冲任务前必须锁定 `invoice_document_id` 对应红冲账本，并在同一事务中校验“成功红冲 + 有效红冲占用 + 本次金额 <= 原蓝票金额”。
- 不同来源竞争同一余额时先提交成功的事务取得占用；后到请求若余额不足不得超额创建 ProviderTask。退款事件仍幂等落 RedIntent 为“等待前序对账”且不阻塞退款款项，用户更正/财务纠错的审核通过事务则整体失败并返回冲突，不创建无占用任务。
- 同一蓝票任一时点最多一个任务进入待确认、提交中、红冲中或结果未知，其余已占用任务保持待处理；调度优先级固定为 `REFUND > FINANCE_CORRECTION > USER_CORRECTION`，同优先级按创建时间和任务 ID。用户更正必须覆盖提交快照中的唯一原蓝票的全部有效金额；后台人工红冲只能占用当前剩余余额并必须填写业务依据。
- 前序任务终态后按原票锁重新计算后继意图；若所需金额已被同一业务事实关联的成功红票满足，则将后继意图标记“已满足”并释放未使用占用，不再调用第三方。
- 已成功金额从占用集合原子转入成功集合；结果未知、失败待处置继续占用；只有取得未受理证据并关闭任务才释放。定时对账校验所有来源累计不超原票金额，异常立即冻结后续红冲并告警。

### 8.6 直接审批与旧页面提交

- 普通开票申请、更正申请及红冲审批均不使用领取、租约或跨请求审批锁，也不产生“我的审批”队列。
- 审批命令必须携带 `request_id + version`，并在单个短事务中完成状态条件更新、最新业务事实复核、必要的订单/原票账本行锁、领域事件和 Outbox 写入；事务结束即释放数据库锁。
- 旧页面基于旧 version 提交时返回冲突和最新状态，不得覆盖新审核决定。数据库短事务行锁属于一致性实现，不得暴露为用户可见审批状态。

## 10. 云登后台状态图说明

### 10.1 申请状态 `application_status`

```text
DRAFT -> PENDING_REVIEW -> APPROVED
                |              |
                |              +-> REJECTED
                +-> WITHDRAWN
                +-> CANCELLED（退款/系统规则）
```

### 10.2 开具状态 `issuance_status`

```text
NOT_SUBMITTED -> SUBMITTING -> ISSUING -> SUCCEEDED
                       |          +-> FAILED（确认唯一蓝票未开具且任务明确失败/关闭）
                       +-> UNKNOWN -> 查询 -> ISSUING / SUCCEEDED / FAILED / 安全重试
```

唯一蓝票目标的当前有效 ProviderTask 是开具事实源。审核通过前为 `NOT_SUBMITTED`；审核事务写入 Outbox 后立即为 `SUBMITTING`，任务未创建或 Outbox 补偿期间不回退。受理后为 `ISSUING`，超时为 `UNKNOWN`，确认唯一蓝票成功后为 `SUCCEEDED`，无蓝票且确认失败后为 `FAILED`。历史失败尝试不参与当前状态判断，迟到失败不覆盖成功；长期未知保持 `UNKNOWN` 并升级人工核对。禁止拆分开具目标或产生部分开票状态。

### 10.3 票据状态 `document_status`

```text
NONE --蓝票成功--> ACTIVE
ACTIVE / PARTIALLY_RED / RED_FAILED --创建有效红冲占用--> RED_PENDING
RED_PENDING --全部目标金额成功--> FULLY_RED
RED_PENDING --部分成功且无处理中/失败待处置--> PARTIALLY_RED
RED_PENDING --无处理中且存在失败待处置--> RED_FAILED
RED_FAILED --安全重试--> RED_PENDING
RED_FAILED --确认未受理并释放--> ACTIVE / PARTIALLY_RED（按已成功金额重算）
```

申请级票据状态仅按该申请唯一原蓝票及其红冲金额计算：

```text
B = 该申请唯一原蓝票票面金额
S = 成功红冲额（red_document_id + original_document_id 去重，累计不超过该原票）
P = 待确认、待提交、处理中或结果未知的红冲占用
F = 明确失败但尚待重试/处置的红冲占用
```

四个集合互斥且 `0 <= S + P + F <= B`。聚合优先级固定为：`B=0` 时 `NONE`；否则 `F>0` 时 `RED_FAILED`；`F=0 且 P>0` 时 `RED_PENDING`；`S=B` 时 `FULLY_RED`；`0<S<B 且 P=F=0` 时 `PARTIALLY_RED`；`S=P=F=0 且 B>0` 时 `ACTIVE`。因此“部分已红冲 + 其余失败待处置”唯一聚合为 `RED_FAILED`；即使同时还有处理中金额也不再命中第二个主状态，详情必须同时返回 `S、P、F、B`。

### 10.4 交付状态 `delivery_status`

```text
NOT_SENT --创建交付单元但尚无尝试--> NOT_SENT
NOT_SENT --开始发送--> SENDING
SENDING --全部必达单元成功--> DELIVERED
SENDING --部分单元成功--> PARTIALLY_DELIVERED
SENDING --无成功且全部终态失败--> FAILED
FAILED --安全重发--> SENDING
PARTIALLY_DELIVERED --其余单元成功--> DELIVERED
PARTIALLY_DELIVERED --其余单元发送中/失败--> PARTIALLY_DELIVERED
DELIVERED --新增该原票关联红票目标单元--> PARTIALLY_DELIVERED
```

目标票据按 `invoice_document_id` 去重，可包含需要交付的蓝票和红票；覆盖金额按各票据票面绝对值统计，只表示交付覆盖，不参与可开票余额计算。目标交付单元以 `invoice_document_id + channel + recipient_version` 唯一，当前聚合只使用当前有效收件人版本，并互斥地处于未开始、发送中、成功或失败。`accessible_amount` 只累加至少一个用户可访问渠道成功的唯一票据金额，每张票最多一次；渠道是否完整另按交付单元判断：

- 全部必达交付单元成功：`DELIVERED`；
- 至少一个成功但并非全部成功：`PARTIALLY_DELIVERED`，包括站内成功但邮件失败；
- 尚无成功且存在发送中或结果未知尝试：`SENDING`；
- 尚无成功/发送中且存在失败尝试：`FAILED`；
- 全部交付单元均无发送尝试，或尚未创建交付单元：`NOT_SENT`。

同一单元可有多次发送尝试，但只以 `invoice_document_id + channel + recipient_version` 计一次；任一尝试成功后，迟到失败不得覆盖成功。渠道发送结果未知时对应单元为 `SENDING`，并先查询真实渠道结果再重试；重试耗尽后为 `FAILED`，但不回退开具成功。文件补拉失败/未知不等于发送失败，对应单元在文件可用前保持 `NOT_SENT`，文件状态另行显示异常。该原票新增关联红票会扩充目标集合并重新聚合：已有成功单元时为 `PARTIALLY_DELIVERED`，尚无成功且新单元尚未尝试时为 `NOT_SENT`。详情同时返回票据金额覆盖与渠道覆盖，禁止把两个渠道或历史收件人版本对同一票据的成功金额相加。

### 10.5 更正申请状态

|当前状态|事件/条件|下一状态|约束|
|---|---|---|---|
|PENDING_REVIEW|用户撤回|WITHDRAWN|终止当前更正单|
|PENDING_REVIEW|审批前原票有效金额归零|CANCELLED|通知最新票据事实|
|PENDING_REVIEW|授权管理员/财务驳回|REJECTED|以 status + version 条件更新；保留原因；用户修改后创建新 correction_request_id 并关联 previous_correction_request_id|
|PENDING_REVIEW|授权管理员/财务通过且唯一原蓝票原子占额成功|APPROVED|以 status + version 条件更新；同事务写 RedTask/Outbox；尚未代表红冲成功|
|PENDING_REVIEW|金额变化、余额不足或该原票占额失败|PENDING_REVIEW|整个通过命令失败且零新增占用；刷新后基于最新事实驳回，不静默修改目标|
|APPROVED|RedTask 已创建但仍在待处理，或 Outbox 正在补偿|APPROVED|持续重试并按 SLA 告警，不重复创建任务|
|APPROVED|RedTask 开始处理/等第三方待处理|RED_PROCESSING|关联任务驱动，不允许人工改写|
|RED_PROCESSING|RedTask 结果未知|RED_PROCESSING|子状态为 UNKNOWN，只查询不重提/释放|
|RED_PROCESSING|仍有任务处理中/未知|RED_PROCESSING|保留该原票已成功红冲事实，继续核对剩余金额|
|RED_PROCESSING|无处理中/未知且任一目标明确失败|RED_FAILED|失败金额继续占用|
|RED_FAILED|安全重试|RED_PROCESSING|只重试失败子任务|
|RED_PROCESSING / RED_FAILED|全部目标红冲金额成功且唯一重开任务创建成功|COMPLETED|以 correction_request_id 幂等创建 replacement_revision|
|RED_PROCESSING|全部红冲成功但重开任务暂未创建|RED_PROCESSING|子状态“红冲成功，重开任务生成中”；Outbox 补偿并告警|
|COMPLETED|自动重开任务受理|COMPLETED|原申请新开具版本进入 SUBMITTING；用户无需操作|
|COMPLETED|自动重开任务余额不足|COMPLETED|重开任务保留并标记不可提交；客户端提示联系平台支持，后台人工处置|

`version` 是对象乐观锁版本，每次审核、撤回和系统推进均递增；更正业务字段在提交后不可变。唯一原蓝票尚有有效金额时更正红冲仍未完成，仅全部目标金额成功且唯一重开任务创建成功后为 `COMPLETED`。更正的编排状态独立于申请、开具、票据、交付四维状态；全部状态只通过领域命令和事件转换，禁止页面直接写状态码。

|开票失败|需要用户修改时通知；纯技术重试不频繁打扰|立即待办|
|结果未知超时|客户端保持开票中|超过阈值告警|
|更正审核驳回|站内 + 邮件，包含原因和修改入口|无|
|更正审核通过|状态通知，不宣告红冲成功|红冲编排监控|
|红冲处理中|站内 + 邮件，突出时限|红冲任务待确认|
|红冲结果未知/失败|客户端显示核对中或失败且不可重复提交|查询/重试/人工核对待办|
|红冲成功|站内 + 邮件交付红票；更正重开任务创建成功后通知自动重开进度|账本重算；更正重开任务幂等创建监控|
|交付失败|站内提示仍可下载|交付失败待办|

## 13. 流程验收场景

|用例|前置|预期|
|---|---|---|
|TC-01 法币充值开票|充值支付成功|立即进入可开票池，可提交并完成开票|
|TC-02 云币消费不可开票|订单支付方式为云币|不进入可申请池，原因明确|
|TC-03 履约后开票|代理订单已支付未履约|履约前不可申请，完成后进入|
|TC-04 单订单申请|点击一条可申请订单|一次确认，生成一条申请和一张发票|
|TC-05 同订单并发申请|两用户同时提交|仅一方占用成功，另一方看到冲突|
|TC-06 撤回/审批竞争|待审核同时操作|仅一个版本成功，双方状态一致|
|TC-07 驳回重提|税号有误|申请单号不变，新增提交版本回到待审核，历史驳回版本只读保留|
|TC-08 第三方超时但成功|请求超时后平台实际开票|先结果未知，查询/回调后只生成一张票|
|TC-09 重复回调|相同成功回调多次|只落一张票，交付任务幂等|
|TC-10 单订单开票失败|第三方确认未开票且旧任务关闭|客户端显示开票失败，可针对原订单修改重提|
|TC-11 邮件失败|票据文件已生成|主状态已开票，交付失败可重发|
|TC-12 待审核退款|单订单申请中发生退款|取消该订单申请并释放占用|
|TC-13 开票中退款|ProviderTask 结果未知|冻结并查询；成功后红冲，失败后取消/调整|
|TC-14 已开票部分退款|退款小于原票金额|创建部分红冲，成功后蓝红票关系正确|
|TC-15 抬头错误重开|已开票|更正审核与版本可追溯；全部目标红冲成功后系统幂等创建唯一自动重开任务，系统自动提交新开具版本，不覆盖原票|
|TC-16 红冲处理中超时|第三方需额外处理|按第三方真实结果恢复，不假定成功|
|TC-17 超过 12 个月|资格时间超过窗口|不能自助提交；原因 Modal 提示联系平台支持，客户端不创建工单，后台进入人工核验|
|TC-18 权限越权|普通成员访问他人申请 ID|服务端拒绝，不返回票面信息|
|TC-19 跨成员逐单权限|团队财务处理成员 A/B 订单，A 查询本人订单|A 只能看到本人订单状态，不能获得 B 的申请、抬头、金额和文件|
|TC-20 普通申请并发审批|两名授权人员基于同一版本分别通过/驳回|仅一个决定成功；失败方返回版本冲突并刷新最新状态|
|TC-21 更正驳回重提|更正申请 A 被驳回|A 只读保留；修改后创建更正申请 B 并以 previous_correction_request_id 关联 A，审核记录不覆盖|
|TC-22 更正申请并发审批|两名授权人员基于同一版本审批更正请求|仅一个决定成功；失败方返回版本冲突；红冲余额不重复占用|
|TC-23 三来源红冲竞争|退款、更正、人工红冲同时针对同一原票|按原票账本串行占额且总额不超过票面；更正/财务纠错占额不足时不通过，退款意图可等待但不超额占用|
|TC-24 同一蓝票分次退款红冲|该原票一笔红冲成功、另一笔处理中|聚合唯一为 RED_PENDING，同时展示成功金额/原蓝票总额；全部终态后按金额转部分或全部红冲|
|TC-25 红冲结果未知|第三方超时且是否红冲不明|保持占用与核对中，只查询不重提；真实终态回写后再转换|
|TC-26 自动重开任务补偿|更正红冲全部成功但首次建重开任务失败|更正保持 RED_PROCESSING 的“重开任务生成中”子状态并告警；补偿按 correction_request_id 仅建一个重开任务，成功后转 COMPLETED|
|TC-27 单票多渠道交付|唯一蓝票站内成功、邮件失败|可访问金额按该蓝票只计一次，渠道聚合为 PARTIALLY_DELIVERED，开具状态保持成功|
|TC-28 文件补拉失败|第三方确认开票成功但文件未取得|对应交付单元保持 NOT_SENT、文件状态异常；不伪造发送失败且开具状态不回退|
|TC-29 红冲失败与处理中并存|同一原蓝票一笔红冲失败待处置、另一笔仍处理中|聚合唯一为 RED_FAILED，同时返回 S/P/F/B 展示处理中与成功金额|

### 13.1 一票一单补充验收

|用例|输入或前置条件|预期|
|---|---|---|
|单订单基数|零个订单、多个订单或订单数组|前后端拒绝；不创建申请、不占额|
|禁止拆票|税务配置不兼容|阻止在线提交并提示处理方式，不按金额拆成多个申请或蓝票|
|唯一开具目标|相同请求重试、重复或乱序成功回调|返回同一蓝票 ID；成功后不得再次开具|
|更正目标归属|票据数组、其他订单票据或与来源申请不匹配的票据|拒绝创建更正单和红冲占用|
|部分红冲后重开|原蓝票仍有有效金额|禁止新普通申请及重开提交；完成剩余有效金额红冲后才可继续|
|重开版本链|原蓝票有效金额已归零，系统自动执行唯一重开任务|原申请的新开具版本仍绑定原 order_id，保留旧申请/蓝红票关系；最多一张有效蓝票|

### 并发与页面验收补充（2026-09-08）

- 已撤回、已驳回修改重提和开票失败修改重提都保留原申请单号，提交增加 revision 与 version 并回到待审核；历史信息和时间线不可覆盖。补正必须确认旧任务关闭且未开票。
- 在入口、最终确认及提交事务再次核对版本和状态：已被撤回、财务已通过、已被重提或补正分别提示实际原因。重复请求返回原结果；不新增申请或重复释放金额。
- 多标签页原型以浏览器命令互斥和共享状态版本演示竞争，不存储抬头、税号和联系人。生产采用服务端原子条件更新、请求幂等与权限校验；记录页每 10 秒轮询，重新聚焦查询，隐藏暂停、离开停止；推送可替代轮询但不能替代提交校验。
- 联系客服进入现有在线会话；抬头刷新同步已维护资料；个人只能选普票；号码占位值不参与号码搜索。金额按分计算，日期筛选以北京时间昨天为上限。
