> 适用系统：YunLogin PC 端、云登后台管理系统、发票领域服务、第三方电子发票平台  
> 文档状态：方案基线已确认  
> 最后更新：2026-08-18

## 0. 图例入口

原生 Draw.io 文件：![[开票业务流程.drawio]]

文件包含四个页面：

1. `01-完整开票泳道`：从用户选择订单到开票交付，并覆盖驳回、退款、更正和红冲；
2. `02-YunLogin客户端状态`：用户可见状态、允许动作及重提/红冲闭环；
3. `03-云登后台开票状态`：申请、开具、票据、交付四维状态；
4. `04-异常与并发补偿`：重复提交、撤回/领取竞争、第三方结果未知、退款/开票竞争。

## 1. 泳道定义

主流程以“受票方 / 开票方”两大参与方呈现，并细分系统执行责任：

|主泳道|子泳道|职责|
|---|---|---|
|受票方|YunLogin 用户|选单、填写、确认、撤回、修改重提、接收票据、必要时确认红字信息|
|受票方|YunLogin 客户端|展示资格、拆分预览、表单校验、状态映射、站内预览与下载|
|开票方|云登发票服务|权威资格校验、金额占用、状态机、第三方任务、回调、文件、交付、红冲与对账|
|开票方|财务管理员|领取审核、通过/驳回、异常重试、红冲处置和审计|
|开票方|第三方电子发票平台|开具蓝票/红票、返回受理与终态、提供票据文件|

“第三方平台”是开票方的受托技术执行方，不改变订单销售主体作为法定开票方的业务责任。

## 2. 前置条件

### 2.1 订单资格

订单进入自助可开票池必须同时满足：

1. 当前用户具有订单数据权限；
2. 支付方式为支付宝、微信、银联等法币渠道，不是云币；
3. 云币充值订单已支付成功；或代理、套餐、续费订单已支付成功且履约完成；
4. 不是零元、赠送、兑换或全额退款订单；
5. 当前可开票余额大于 0；
6. 资格取得时间未超过 12 个月；
7. 开票主体和发票内容税务映射有效；
8. 不存在覆盖同一金额的有效申请占用或蓝票。

超过 12 个月只退出自助池，仍可进入人工核验流程；不得直接视为永久不可开票。

### 2.2 金额口径

```text
资格法币净额 = 已确认法币实付金额 - 已确认退款金额
当前可开票余额 = max(0,
  资格法币净额
  - 有效申请占用金额
  - 未被红冲的有效蓝票金额
)
```

展示金额是预览；提交、审核通过、退款和红冲完成时均由服务端重新计算。

“有效申请占用金额”是尚未释放且尚未转为有效蓝票的订单分摊金额，包括待审核、审核中、已通过待提交、提交中、开票中、结果未知和失败待处置。驳回/撤回/取消需在服务端释放后才退出占用；失败待补正需确认未开票并关闭旧任务后释放；成功部分转为有效蓝票，不重复计入两处。

## 3. 正常开票主流程

|步骤|责任方|输入/触发|系统动作|输出/状态|
|---|---|---|---|---|
|F-01|用户|进入“费用管理 > 订单管理 > 开票管理”|客户端请求可开票订单|展示本人或团队权限范围内订单|
|F-02|客户端/发票服务|筛选条件|服务端鉴权并计算每单余额、主体、内容兼容项和原因码|可申请/不可申请解释列表|
|F-03|用户|勾选一笔或多笔订单|客户端请求分组预览|待确认订单集合|
|F-04|发票服务|订单 ID + version|重新读取资格，按开票主体和税务兼容性分组，为每组生成稳定 group_fingerprint|预计生成 N 个申请及拆分原因|
|F-05|用户|确认分组|为每组选择发票类型、抬头、发票内容，填写邮箱和电话|完整申请表单|
|F-06|客户端|点击下一步|执行必填、格式、个人/专票和内容兼容预校验|确认页或字段错误|
|F-07|用户|核对并提交|客户端生成稳定 submission_id 并携带各组 group_fingerprint，按钮进入确认中|一个提交信封|
|F-08|发票服务|提交信封|逐组编排；每组事务内重新鉴权、锁定该组订单账本、重算余额和资格|每组成功占用或明确失败|
|F-09|发票服务|某组校验通过|生成该组申请、订单分摊和抬头/内容快照；以 submission_id + group_fingerprint 去重|该组申请“待审核”|
|F-10|客户端|信封结果|展示成功申请与失败组；网络中断按 submission_id 查询，成功组不重提|全部成功/部分成功/全部失败|
|F-11|财务管理员|待审核队列|使用申请 version 领取审核锁|申请状态“审核中”|
|F-12|财务管理员/发票服务|审核详情|系统复核支付、履约、退款、余额、抬头、内容和主体配置|审核检查结果|
|F-13|财务管理员/发票服务|审核通过|事务内固化最终开票快照、置为已通过并写开具 Outbox 命令；审核员不直接创建第三方任务|申请“已通过”，开具“提交中”|
|F-14|发票服务内部任务编排器|开具 Outbox 命令|以内置服务身份幂等创建唯一首个 ProviderTask，并以稳定 provider_request_id 调用第三方|第三方受理号或结果未知/失败|
|F-15|第三方平台|开票请求|执行数电发票开具|开票成功/明确失败/处理中|
|F-16|发票服务|回调或主动查询|验签、去重、顺序校验并更新任务|开具状态终态或继续处理中|
|F-17|发票服务|开票成功|保存 InvoiceDocument，补拉 PDF/OFD/XML 并校验哈希|票据状态“正常”|
|F-18|发票服务|票据可用|创建站内和邮件交付任务|交付“发送中”|
|F-19|客户端/邮件服务|至少一个渠道成功|站内展示预览/下载，邮件发送结果入库|交付“已送达/部分送达”|
|F-20|用户|打开通知或记录|查看发票信息、预览、下载或重新发送|开票闭环完成|

## 4. 审核驳回、撤回与重新提交

### 4.1 用户撤回

```text
待审核 -> 用户点击撤回 -> 服务端尝试申请版本锁
  -> 若仍待审核：申请变为已撤回，释放订单金额占用
  -> 若管理员已领取：撤回失败，返回审核中最新状态
```

撤回后原申请只读保留。用户从最新可开票订单重新创建申请，不复用旧申请 ID。

### 4.2 财务驳回

1. 管理员在审核锁有效期内选择结构化驳回原因；
2. 服务端保存驳回版本和说明；
3. 对可修改重提的原因释放占用并通知用户；
4. 用户点击“修改并重新提交”，系统复制原表单快照；
5. 系统先重新校验原订单资格；
6. 用户修正字段并提交，生成新申请 ID/版本，关联 `previous_application_id`；
7. 新申请重新进入待审核，旧申请永久保持已驳回。

审核锁采用带租约的排他锁。管理员主动释放、会话异常或租约超时且没有审核决定时，服务端以条件更新清除锁持有人，将申请从 `REVIEWING` 恢复为 `PENDING_REVIEW` 并记录原因；用户随后重新获得待审核状态下的撤回权。锁已过期的管理员提交通过/驳回必须返回版本冲突，不能覆盖新锁持有人的决定。

### 4.3 不允许直接修改的状态

- 审核中：已被管理员锁定；
- 开票提交中、开票中、结果未知：第三方可能已受理；
- 已开票：必须先红冲；
- 红冲中：等待红冲终态。

## 5. 第三方开具异常

### 5.1 明确失败

第三方明确返回未受理或开票失败：

- 开具状态变为“开票失败”；
- 保留金额占用，避免用户在管理员判断期间重新申请；
- 管理员根据归一化错误修复配置；
- 重试复用原 provider_request_id，或在确认旧请求未受理并关闭后生成新任务；
- 若需要用户修改信息，管理员执行“关闭旧任务并要求补正”：必须先取得第三方未开票证据，关闭旧任务且永久禁用其重试，再释放占用、开放补正入口并通知用户；用户点击后由服务端按来源申请与处置版本幂等创建/读取补正草稿，再从该草稿提交新申请。关闭事件本身不自动生成草稿；原申请保持“已通过 + 开票失败”，不得倒退为“已驳回”。

这里的“开具失败补正”只处理尚未生成蓝票的资料/配置错误，不创建 `InvoiceCorrectionRequest`；后者仅用于已生成蓝票后的信息更正，必须先走红冲。

### 5.2 请求超时/结果未知

超时不能判定失败：

```text
第三方请求超时
  -> ProviderTask = UNKNOWN
  -> 金额继续冻结，客户端仍展示“开票中”
  -> 按请求号/受理号主动查询
     -> 查询成功：按真实终态处理
     -> 查询明确不存在：记录证据后允许安全重试
     -> 长时间未知：进入财务人工核对，不允许用户重提
```

### 5.3 重复与乱序回调

- 回调先写入 Inbox；
- 验签失败进入隔离队列，不更新业务状态；
- 相同 event ID/事件指纹只处理一次；
- 旧版本“处理中”不得覆盖已经落库的“成功/失败”；
- 重放回调可以重新触发未完成的文件补拉或交付，但不能重复创建票据。

### 5.4 部分开票成功

一份申请因系统拆票生成多个子任务时：

- 每个子任务、票据和金额独立记录；
- 成功子任务生成有效票据并可交付；
- 失败子任务进入“部分开票异常”；
- 已成功金额保持已开票，不能整单重新提交；
- 管理员只对失败子任务查询/重试；
- 每个子任务变化后立即重算申请聚合状态；全部子任务终态后再确定最终结果，已关闭未开具的剩余子任务使申请保持“部分成功”，不得把已成功票据回退或把未开金额伪装为成功。

## 6. 票据文件与交付异常

### 6.1 文件补拉失败

第三方已确认开票成功，但 PDF/OFD/XML 获取失败：

- 开具状态保持“开票成功”；
- 票据记录已存在，文件状态标记异常；
- 后台自动重试补拉并告警；
- 客户端显示“已开票，文件暂不可用”；
- 不允许为此重新开具。

### 6.2 邮件失败

- 站内票据与开票状态不受影响；
- 邮件渠道标记发送失败，交付可为“部分送达”；
- 用户或管理员可重新发送到本次指定邮箱；
- 重发不修改申请、抬头或原交付记录；
- 频控：同一发票 60 秒内最多一次，每日最多 5 次，后台应支持受控豁免。

## 7. 退款、红冲与重新开票

### 7.1 退款发生在尚未开票阶段

|当前阶段|处理|
|---|---|
|选单/填表|提交时重新校验，移除或更新退款订单金额|
|待审核|自动取消单订单申请，或从合并申请剔除退款订单并重算；全部剔除则取消申请|
|审核中|标记订单事实变化，阻止审核通过；管理员驳回或系统剔除后重审|
|提交第三方前|取消开具任务并按退款金额调整/取消申请|

### 7.2 退款与第三方提交并发

若 ProviderTask 已提交、开票中或结果未知：

1. 不创建第二张蓝票，也不直接释放占用；
2. 等待查询得到第三方终态；
3. 若明确未开票，取消/调整申请并处理退款；
4. 若已经开票，立即创建对应金额红冲任务；
5. 退款资金到账不等待红冲，但红冲任务必须进入财务 SLA 和告警。

### 7.3 已开票后退款

```text
退款审批通过
  -> 以 source_type=REFUND + refund_id + invoice_document_id 识别来源幂等，金额作为不可变载荷校验
  -> 锁定原票统一红冲账本，重算可红冲余额并创建 InvoiceRedAllocation
  -> 在同一事务内占用金额，判断全额/部分红冲及是否需要受票方确认
  -> 调用第三方红冲
  -> 成功：保存红票、更新蓝票关系、重算可开票余额、交付红票
  -> 失败/未知：金额继续冻结，进入查询/重试/人工核对
```

统一金额规则适用于退款、用户更正和后台人工红冲：

```text
原票可红冲余额 = 原蓝票金额 - 成功红冲金额 - 有效红冲占用金额
有效红冲占用 = 待受票方确认 + 待提交 + 红冲中 + 结果未知 + 失败待处置
0 <= 成功红冲金额 + 有效红冲占用金额 <= 原蓝票金额
```

同一来源事件重复投递返回原 `InvoiceRedAllocation`；不同来源同时到达时，以原蓝票账本锁内先成功提交的事务取得占用，后到请求只能占用剩余余额。红冲失败不自动释放，只有确认第三方未受理并关闭任务后才释放，避免未知结果与新任务重叠。

### 7.4 用户信息错误更正

用户信息错误更正使用独立对象 `InvoiceCorrectionRequest`，不把原 `InvoiceApplication` 回退为已驳回，也不直接修改已开票快照。

1. 用户在已开票详情填写更正信息，选择同一开票主体下的目标蓝票、结构化原因和期望更正快照；提交时目标金额必须等于所选蓝票当前有效金额，服务端创建 `correction_request_id`，固化不可变快照并进入 `PENDING_REVIEW`。
2. 财务使用对象 `version` 领取审核锁，进入 `REVIEWING`；锁释放/超时且未决策时回到 `PENDING_REVIEW`。审核驳回进入 `REJECTED` 并保存结构化原因，原蓝票继续有效。
3. 被驳回后用户复制最新快照修改并提交新的 `correction_request_id`，通过 `previous_correction_request_id` 形成版本链；原更正单、审核人、证据和决定永久保留。待审核可撤回为 `WITHDRAWN`，审核中不可撤回。
4. 审核通过命令在同一事务重新校验全部目标原票，按原票升序锁定统一红冲账本并整组占额。信息更正必须覆盖提交快照中的全部目标有效蓝票金额；若退款/财务纠错已有占用、金额已变化或任一原票余额不足，整个命令失败且不产生部分占用，返回冲突供审核员驳回，用户基于最新事实创建关联的新更正单。
5. 事务成功后更正进入 `APPROVED` 并创建关联 RedTask，任务开始后更正进入 `RED_PROCESSING`。待受票方确认、提交中、红冲中和结果未知均是 RedTask 子状态；结果未知只允许查询，更正聚合状态仍为 `RED_PROCESSING`。无处理中/未知任务且任一目标明确失败时更正为 `RED_FAILED`，占用保持并仅恢复具体失败子任务。
6. 部分目标票据成功时保存已成功红票并继续处理剩余任务，不创建重开草稿。仅当全部目标红冲金额成功，系统以 `correction_request_id` 为幂等键自动创建且仅创建一个 `InvoiceApplication` 重开草稿，关联 `previous_application_id`、原蓝票、红票及更正申请；草稿创建成功后更正进入 `COMPLETED`。
7. 草稿预填已审核的更正快照，但金额按最新支付、退款和红冲账本重新计算。用户必须查看并主动提交；提交成功后新申请进入普通 `PENDING_REVIEW`，更正申请保持 `COMPLETED`。若最新余额不足，草稿仍保留并展示不可提交原因，不自动开票、不重复建草稿。
8. 红冲成功与建草稿通过事务 Outbox 衔接；临时建草稿失败时更正保持 `RED_PROCESSING` 的“红冲成功，草稿生成中”子状态，补偿任务按同一幂等键重试并持续告警，禁止用户手工绕过创建第二份重开申请。

更正请求状态如下：

```text
PENDING_REVIEW -> REVIEWING -> APPROVED -> RED_PROCESSING -> COMPLETED
       |             |                           |
       |             +-> REJECTED                +-> RED_FAILED -> 安全重试 -> RED_PROCESSING
       |                  -> 新 correction_request_id + previous_correction_request_id
       +-> WITHDRAWN

审批前原票已无有效金额 -> CANCELLED
RedTask 待确认 / 提交中 / 红冲中 / UNKNOWN -> 更正申请均保持 RED_PROCESSING
全部红冲成功但草稿未建成 -> RED_PROCESSING（红冲成功，草稿生成中）
```

### 7.5 受票方确认

当税务/第三方规则要求受票方确认红字信息时：

- 红冲任务进入“待受票方确认”；
- 客户端显示确认原因、操作指引和有效期；
- 系统通过第三方查询确认结果，不以“用户点击已确认”直接判定税务平台已确认；
- 确认超时进入查询/人工核对路径：第三方确认有效则继续红冲，明确失效/未受理才允许按原红冲占用安全重发，仍未知则保持冻结；不能假定成功、失败或释放金额。

## 8. 并发场景与裁决规则

### 8.1 两名用户同时申请同一订单

|时序|用户 A|发票服务|用户 B|
|---|---|---|---|
|1|提交订单 O1|—|几乎同时提交 O1|
|2|—|按订单 ID 锁定账本，先处理 A|等待锁|
|3|收到成功申请|占用 O1 全部余额并提交事务|—|
|4|—|处理 B 时重算余额为 0|收到版本冲突/已占用提示|

裁决：先成功提交事务的一方获得占用；不是按前端点击时间或请求到达顺序口头判定。

### 8.2 用户撤回与管理员领取同时发生

- 两个命令均携带相同申请 version；
- 服务端只允许一个条件更新成功；
- 撤回先成功：管理员领取失败并刷新为已撤回；
- 领取先成功：用户撤回失败并刷新为审核中；
- 失败方不得本地乐观改状态。

### 8.3 管理员重复审核

- 申请只能被一个有效审核锁持有人操作；
- 审核通过/驳回使用 `request_id + application_version`；
- 重复点击返回第一次结果；
- 另一管理员基于旧版本提交时返回冲突和最新状态。

### 8.4 第三方超时后管理员点击重试

- `UNKNOWN` 状态不提供普通“重试开票”按钮，只提供“查询结果”；
- 只有主动查询明确未受理后 `allowed_actions` 才包含重试；
- 人工确认未受理必须填写依据并留下审计；
- 任何重试前再次按原请求号查询一次。

### 8.5 退款、更正与人工红冲并发

- 三类来源共用原票级 `InvoiceRedAllocation`，来源类型固定为 `REFUND`、`USER_CORRECTION`、`FINANCE_CORRECTION`，来源幂等键为 `source_type + source_business_id + invoice_document_id`；金额属于不可变请求载荷，相同键金额不一致必须报幂等冲突。同一来源重复请求返回已有分摊和任务。
- 仅有来源幂等键仍不够：创建任意红冲任务前必须锁定 `invoice_document_id` 对应红冲账本，并在同一事务中校验“成功红冲 + 有效红冲占用 + 本次金额 <= 原蓝票金额”。
- 不同来源竞争同一余额时先提交成功的事务取得占用；后到请求若余额不足不得超额创建 ProviderTask。退款事件仍幂等落 RedIntent 为“等待前序对账”且不阻塞退款款项，用户更正/财务纠错的审核通过事务则整体失败并返回冲突，不创建无占用任务。
- 同一蓝票任一时点最多一个任务进入待确认、提交中、红冲中或结果未知，其余已占用任务保持待处理；调度优先级固定为 `REFUND > FINANCE_CORRECTION > USER_CORRECTION`，同优先级按创建时间和任务 ID。用户更正必须覆盖提交快照中的全部目标有效蓝票金额；后台人工红冲只能占用当前剩余余额并必须填写业务依据。
- 前序任务终态后按原票锁重新计算后继意图；若所需金额已被同一业务事实关联的成功红票满足，则将后继意图标记“已满足”并释放未使用占用，不再调用第三方。
- 已成功金额从占用集合原子转入成功集合；结果未知、失败待处置继续占用；只有取得未受理证据并关闭任务才释放。定时对账校验所有来源累计不超原票金额，异常立即冻结后续红冲并告警。

### 8.6 审核锁过期与旧页面提交

- 普通开票申请和更正申请都使用带租约的审核锁，锁记录包含 `lock_id`、持有人、到期时间和对象 `version`。
- 管理员主动释放、会话异常或租约超时且尚无审核决定时，条件更新将 `REVIEWING` 恢复为 `PENDING_REVIEW`；恢复操作写审计日志并触发队列刷新。
- 原管理员在旧页面提交时必须携带原 `lock_id + version`；服务端返回冲突和最新状态，不得重新把对象写回审核中或覆盖新审核决定。

### 9.2 交付状态作为附加状态

交付失败不改变“已开票”。客户端在主状态旁显示：

- 邮件发送中；
- 已发送；
- 邮件发送失败，可重发；
- 站内文件暂不可用，正在恢复。

当一份申请包含多张票时，“已送达金额”按唯一票据计算，同一张票站内和邮件均成功也只计一次；“部分送达”同时可能表示只有部分票据可访问，或票据均可站内访问但某个必达渠道失败。详情必须展示每张票、每个渠道的独立状态，不能只展示聚合文案。

## 10. 云登后台状态图说明

### 10.1 申请状态 `application_status`

```text
DRAFT -> PENDING_REVIEW -> REVIEWING -> APPROVED
                |              |      |
                |              |      +-> REJECTED
                |              +-> PENDING_REVIEW（审核锁释放/超时且无决定）
                +-> WITHDRAWN
                +-> CANCELLED（退款/系统规则）
```

### 10.2 开具状态 `issuance_status`

```text
NOT_SUBMITTED -> SUBMITTING -> ISSUING -> SUCCEEDED
                       |          |  \-> PARTIAL -> SUCCEEDED（其余任务全部恢复）
                       |          +-> FAILED（无成功任务且全部终态失败/关闭）
                       +-> UNKNOWN -> 查询 -> ISSUING / SUCCEEDED / FAILED / 安全重试
```

任务级状态是已创建 ProviderTask 的事实源；无任务窗口先按审批与 Outbox 事实判定：申请尚未审核通过、未写开具 Outbox 且没有 ProviderTask 时为 `NOT_SUBMITTED`；审核通过事务已写开具 Outbox 后立即为 `SUBMITTING`，即使编排器尚未创建 ProviderTask 也不得回退 `NOT_SUBMITTED`。任务创建后按以下顺序聚合：全部目标任务成功为 `SUCCEEDED`；存在成功且仍有任何非成功任务（包括处理中、未知、失败或已关闭未开具）为 `PARTIAL`；无成功时，任一 `UNKNOWN` 为 `UNKNOWN`，否则任一 `ISSUING` 为 `ISSUING`，否则任一 `SUBMITTING/QUEUED` 为 `SUBMITTING`，全部任务终态失败/关闭才为 `FAILED`。Outbox 待消费或补偿时保持 `SUBMITTING` 并由补偿任务恢复。`allowed_actions` 必须定位到具体失败/未知子任务，禁止对已成功部分整单重试；长期未知仍保持 `UNKNOWN/PARTIAL` 并升级人工核对，不能按超时自行转失败。

### 10.3 票据状态 `document_status`

```text
NONE --蓝票成功--> ACTIVE
ACTIVE / PARTIALLY_RED / RED_FAILED --创建有效红冲占用--> RED_PENDING
RED_PENDING --全部目标金额成功--> FULLY_RED
RED_PENDING --部分成功且无处理中/失败待处置--> PARTIALLY_RED
RED_PENDING --无处理中且存在失败待处置--> RED_FAILED
RED_FAILED --安全重试--> RED_PENDING
RED_FAILED --确认未受理并释放--> ACTIVE / PARTIALLY_RED（按已成功金额重算）
```

申请级票据状态不是任选一张票的状态，而是按唯一原蓝票的金额分摊聚合：

```text
B = 原蓝票总额（invoice_document_id 去重）
S = 成功红冲额（red_document_id + original_document_id 去重，逐张不超过原票）
P = 待确认、待提交、处理中或结果未知的红冲占用
F = 明确失败但尚待重试/处置的红冲占用
```

四个集合互斥且 `0 <= S + P + F <= B`。聚合优先级固定为：`B=0` 时 `NONE`；否则 `F>0` 时 `RED_FAILED`；`F=0 且 P>0` 时 `RED_PENDING`；`S=B` 时 `FULLY_RED`；`0<S<B 且 P=F=0` 时 `PARTIALLY_RED`；`S=P=F=0 且 B>0` 时 `ACTIVE`。因此“部分已红冲 + 其余失败待处置”唯一聚合为 `RED_FAILED`；即使同时还有处理中金额也不再命中第二个主状态，详情必须同时返回 `S、P、F、B`。

### 10.4 交付状态 `delivery_status`

```text
NOT_SENT --创建交付单元但尚无尝试--> NOT_SENT
NOT_SENT --开始发送--> SENDING
SENDING --全部必达单元成功--> DELIVERED
SENDING --部分单元成功--> PARTIALLY_DELIVERED
SENDING --无成功且全部终态失败--> FAILED
FAILED --安全重发--> SENDING
PARTIALLY_DELIVERED --其余单元成功--> DELIVERED
PARTIALLY_DELIVERED --其余单元发送中/失败--> PARTIALLY_DELIVERED
DELIVERED --新增蓝票/红票目标单元--> PARTIALLY_DELIVERED
```

目标票据按 `invoice_document_id` 去重，可包含需要交付的蓝票和红票；覆盖金额按各票据票面绝对值统计，只表示交付覆盖，不参与可开票余额计算。目标交付单元以 `invoice_document_id + channel + recipient_version` 唯一，当前聚合只使用当前有效收件人版本，并互斥地处于未开始、发送中、成功或失败。`accessible_amount` 只累加至少一个用户可访问渠道成功的唯一票据金额，每张票最多一次；渠道是否完整另按交付单元判断：

- 全部必达交付单元成功：`DELIVERED`；
- 至少一个成功但并非全部成功：`PARTIALLY_DELIVERED`，包括站内成功但邮件失败；
- 尚无成功且存在发送中或结果未知尝试：`SENDING`；
- 尚无成功/发送中且存在失败尝试：`FAILED`；
- 全部交付单元均无发送尝试，或尚未创建交付单元：`NOT_SENT`。

同一单元可有多次发送尝试，但只以 `invoice_document_id + channel + recipient_version` 计一次；任一尝试成功后，迟到失败不得覆盖成功。渠道发送结果未知时对应单元为 `SENDING`，并先查询真实渠道结果再重试；重试耗尽后为 `FAILED`，但不回退开具成功。文件补拉失败/未知不等于发送失败，对应单元在文件可用前保持 `NOT_SENT`，文件状态另行显示异常。新增蓝票/红票会扩充目标集合并重新聚合：已有成功单元时为 `PARTIALLY_DELIVERED`，尚无成功且新单元尚未尝试时为 `NOT_SENT`。详情同时返回票据金额覆盖与渠道覆盖，禁止把两个渠道或历史收件人版本对同一票据的成功金额相加。

### 10.5 更正申请状态

|当前状态|事件/条件|下一状态|约束|
|---|---|---|---|
|PENDING_REVIEW|管理员领取有效锁|REVIEWING|校验对象 version|
|PENDING_REVIEW|用户撤回|WITHDRAWN|终止当前更正单|
|PENDING_REVIEW / REVIEWING|审批前原票有效金额归零|CANCELLED|清除审核锁并通知最新票据事实|
|REVIEWING|审核锁释放/超时且无决定|PENDING_REVIEW|清锁并拒绝旧页面提交|
|REVIEWING|驳回|REJECTED|保留原因；用户修改后创建新 correction_request_id 并关联 previous_correction_request_id|
|REVIEWING|通过且全部原票整组占额成功|APPROVED|同事务写 RedTask/Outbox；尚未代表红冲成功|
|REVIEWING|金额变化、余额不足或任一原票占额失败|REVIEWING|整个通过命令失败且零占用；刷新后驳回，不静默修改目标|
|APPROVED|RedTask 已创建但仍在待处理，或 Outbox 正在补偿|APPROVED|持续重试并按 SLA 告警，不重复创建任务|
|APPROVED|RedTask 开始处理/等待受票方确认|RED_PROCESSING|关联任务驱动，不允许人工改写|
|RED_PROCESSING|RedTask 结果未知|RED_PROCESSING|子状态为 UNKNOWN，只查询不重提/释放|
|RED_PROCESSING|仍有任务处理中/未知|RED_PROCESSING|已成功子任务保留，继续等待剩余任务|
|RED_PROCESSING|无处理中/未知且任一目标明确失败|RED_FAILED|失败金额继续占用|
|RED_FAILED|安全重试|RED_PROCESSING|只重试失败子任务|
|RED_PROCESSING / RED_FAILED|全部目标红冲金额成功且唯一草稿创建成功|COMPLETED|以 correction_request_id 幂等创建 replacement_application_id|
|RED_PROCESSING|全部红冲成功但草稿暂未创建|RED_PROCESSING|子状态“红冲成功，草稿生成中”；Outbox 补偿并告警|
|COMPLETED|用户提交重开草稿|COMPLETED|更正状态不再变化；新 InvoiceApplication 进入 PENDING_REVIEW|
|COMPLETED|重开草稿余额不足|COMPLETED|草稿保留并标记不可提交，提供人工处理入口|

`version` 是对象乐观锁版本，每次领取、释放、审核、撤回和系统推进均递增；更正业务字段在提交后不可变。多目标票据部分红冲成功仍视为红冲未完成，仅全部目标金额成功且唯一草稿创建成功后为 `COMPLETED`。更正的编排状态独立于申请、开具、票据、交付四维状态；全部状态只通过领域命令和事件转换，禁止页面直接写状态码。

|事件|状态影响|金额影响|
|---|---|---|
|申请提交成功|申请 -> 待审核|增加有效占用|
|用户撤回成功|申请 -> 已撤回|释放占用|
|管理员领取|申请 -> 审核中|不变|
|审核锁主动释放/超时|申请/更正 -> 待审核；清除锁持有人|不变|
|审核驳回|申请 -> 已驳回|审核发生在第三方提交前，释放本申请全部有效占用|
|审核通过|申请 -> 已通过；开具 -> 提交中|占用保持|
|第三方受理|开具 -> 开票中|占用保持|
|请求超时|开具 -> 结果未知|占用保持|
|蓝票成功|子任务 -> 成功；重算申请开具聚合状态；票据 -> 正常|该子任务金额从占用转有效蓝票金额|

|更正申请提交|新更正单 -> 待审核；业务快照不可变|不占红冲金额|
|更正驳回|当前更正单 -> 已驳回；修改后创建关联的新 correction_request_id|不变，原蓝票有效|
|更正审核通过|整组锁原票并占额成功后，更正 -> 已通过并创建 RedTask|任一原票冲突则整个命令失败、零新增占用，状态不前进|
|红冲请求超时|RedTask -> 结果未知；更正保持红冲处理中|有效红冲占用保持，只允许查询|
|红冲成功|红冲分摊从占用转成功；票据 -> 部分/全部红冲|减少有效蓝票金额，再按退款净额重算余额，不重复释放|
|红冲明确失败|票据/更正 -> 红冲失败|金额继续占用到安全重试或取得未受理证据后关闭|
|更正目标全部红冲成功|更正保持红冲处理中子状态“草稿生成中”；按 correction_request_id 创建唯一重开草稿|按最新退款净额形成草稿金额，不自动新增蓝票占用|
|重开草稿创建成功|更正 -> 已完成并关联 replacement_application_id|不变，草稿本身不占开票余额|
|重开草稿创建暂时失败|更正保持红冲处理中；Outbox 补偿重试|不变，禁止人工创建重复草稿|
|用户提交重开草稿|新申请 -> 待审核；更正保持已完成|按普通申请规则重新校验并增加有效申请占用|

## 12. 通知节点

|节点|用户通知|后台待办/告警|
|---|---|---|
|申请提交|站内通知，可选邮件|待审核队列增加|
|审核驳回|站内 + 邮件，包含可理解原因|无|
|审核通过|可选状态通知，不宣告开票成功|开票任务监控|
|开票成功|站内 + 邮件交付|文件/交付任务|
|开票失败|需要用户修改时通知；纯技术重试不频繁打扰|立即待办|
|结果未知超时|客户端保持开票中|超过阈值告警|
|更正审核驳回|站内 + 邮件，包含原因和修改入口|无|
|更正审核通过|状态通知，不宣告红冲成功|红冲编排监控|
|红冲待确认|站内 + 邮件，突出时限|红冲任务待确认|
|红冲结果未知/失败|客户端显示核对中或失败且不可重复提交|查询/重试/人工核对待办|
|红冲成功|站内 + 邮件交付红票；更正草稿创建成功后提示复核草稿|账本重算；更正草稿幂等创建监控|
|交付失败|站内提示仍可下载|交付失败待办|

## 13. 流程验收场景

|用例|前置|预期|
|---|---|---|
|TC-01 法币充值开票|充值支付成功|立即进入可开票池，可提交并完成开票|
|TC-02 云币消费不可开票|订单支付方式为云币|不进入可申请池，原因明确|
|TC-03 履约后开票|代理订单已支付未履约|履约前不可申请，完成后进入|
|TC-04 多主体拆分|选择两个主体订单|一次确认，生成两个独立申请|
|TC-05 同订单并发申请|两用户同时提交|仅一方占用成功，另一方看到冲突|
|TC-06 撤回/领取竞争|待审核同时操作|仅一个版本成功，双方状态一致|
|TC-07 驳回重提|税号有误|旧申请保留，新申请关联并重新审核|
|TC-08 第三方超时但成功|请求超时后平台实际开票|先结果未知，查询/回调后只生成一张票|
|TC-09 重复回调|相同成功回调多次|只落一张票，交付任务幂等|
|TC-10 部分开票成功|拆票任务一成一败|成功票可下载，失败子任务单独恢复|
|TC-11 邮件失败|票据文件已生成|主状态已开票，交付失败可重发|
|TC-12 待审核退款|合并申请中一单退款|剔除该单并重算，或全部取消|
|TC-13 开票中退款|ProviderTask 结果未知|冻结并查询；成功后红冲，失败后取消/调整|
|TC-14 已开票部分退款|退款小于原票金额|创建部分红冲，成功后蓝红票关系正确|
|TC-15 抬头错误重开|已开票|更正审核与版本可追溯；全部目标红冲成功后系统幂等创建唯一重开草稿，用户确认提交，不覆盖原票|
|TC-16 红冲待确认超时|需要受票方确认|按第三方真实结果恢复，不假定成功|
|TC-17 超过 12 个月|资格时间超过窗口|不能自助提交，可转人工工单|
|TC-18 权限越权|普通成员访问他人申请 ID|服务端拒绝，不返回票面信息|
|TC-19 跨成员合并后的越权|团队财务将成员 A/B 订单合成一张票，A 查询本人订单|A 只看到“团队已处理”摘要，不能获得申请/票据 ID 或 B 的订单、抬头、金额和文件|
|TC-20 普通审核锁超时|管理员领取后离线且未决策|锁到期后申请回到待审核；旧页面提交冲突，其他管理员可重新领取|
|TC-21 更正驳回重提|更正申请 A 被驳回|A 只读保留；修改后创建更正申请 B 并以 previous_correction_request_id 关联 A，审核记录不覆盖|
|TC-22 更正审核锁超时|更正请求处于审核中|无决定时回到更正待审核；红冲余额尚未占用|
|TC-23 三来源红冲竞争|退款、更正、人工红冲同时针对同一原票|按原票账本串行占额且总额不超过票面；更正/财务纠错占额不足时不通过，退款意图可等待但不超额占用|
|TC-24 多票红冲混合状态|一张红冲成功、另一张处理中|聚合唯一为 RED_PENDING，同时展示成功金额/原蓝票总额；全部终态后按金额转部分或全部红冲|
|TC-25 红冲结果未知|第三方超时且是否红冲不明|保持占用与核对中，只查询不重提；真实终态回写后再转换|
|TC-26 重开草稿补偿|更正红冲全部成功但首次建草稿失败|更正保持 RED_PROCESSING 的“草稿生成中”子状态并告警；补偿按 correction_request_id 仅建一个草稿，成功后转 COMPLETED|
|TC-27 多票多渠道交付|两张票均站内成功、一张邮件失败|可访问金额按两张票各计一次，渠道聚合为 PARTIALLY_DELIVERED，开具状态保持成功|
|TC-28 文件补拉失败|第三方确认开票成功但文件未取得|对应交付单元保持 NOT_SENT、文件状态异常；不伪造发送失败且开具状态不回退|
|TC-29 红冲失败与处理中并存|一张红冲失败待处置、另一张仍处理中|聚合唯一为 RED_FAILED，同时返回 S/P/F/B 展示处理中与成功金额|
