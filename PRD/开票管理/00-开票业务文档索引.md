# YunLogin 开票业务文档索引

## 1. 文档目的

本目录用于统一说明 YunLogin 用户侧与云登后台管理系统的开票业务。文档覆盖需求依据、产品结构、字段和交互、后台审核与第三方电子发票平台集成、端到端流程、状态机、异常补偿、并发控制和验收标准。

本目录同时维护产品分析、页面级 PRD、交互设计与流程设计文档；HTML 原型仅用于交互和视觉验收，不代表生产接口实现。

## 3. 已确认的设计基线

- 支付宝、微信、银联等法币支付产生的交易订单支持开票；云币支付产生的消费订单不支持开票。
- 法币充值云币的订单在支付成功后具备资格；代理、套餐、续费等履约型订单需支付成功且履约完成或服务生效。
- 支持数电普通发票与数电专用发票；个人抬头仅可申请普通发票，企业或组织抬头可申请普通或专用发票。
- 每个订单独立生成一张发票；不支持在客户端选择多笔订单合并开票，也不支持一张发票关联多个订单。
- 用户只能按单个订单全部剩余可开票金额申请，不支持手工部分金额开票；一笔订单的申请、占用、开具、交付、红冲和更正均独立追踪。
- 首期采用系统校验后进入财务人工审核；不设置领取、我的审批或审批锁，销售主体数据范围内有审批权限的管理员或财务可直接通过/驳回，审核通过后调用第三方电子发票服务平台。
- 发票内容从财务配置且与订单兼容的有限选项中选择，不允许自由输入。
- 企业常用抬头团队共享并由有权限角色维护，个人常用抬头仅本人可见。
- 普通成员只查看本人创建订单的资格及本人提交申请生成的票据；团队角色也必须逐单申请和逐单查看，订单创建人仅看到本订单的处理状态，不能据此访问其他订单或票面。
- 退款不因开票阻塞：未开具则自动撤销或移除相关申请，已开具则创建红冲任务；红冲成功后将红冲占用原子转为成功红冲记账，并按退款净额重算可开票金额。
- 已开票信息更正使用独立 `InvoiceCorrectionRequest` 审核链，普通申请、更正申请和红冲审批均不设置业务审批锁；全部目标红冲成功后系统按更正申请幂等创建唯一重开草稿，用户确认提交后重新进入普通审核。
- 退款、用户更正和财务纠错共用原蓝票级红冲账本、来源业务键和可红冲余额占用；金额作为不可变载荷校验，不进入来源键，不同来源并发也不得重复或超额红冲。
- 客户端通过费用管理一级页签“开票管理”直接进入，和“订单管理”“优惠券”处于同一层级；后台在“财务管理 > 发票管理”设置独立模块。
- 开票页面不展示订单管理面包屑，也不提供订单页“开票管理”按钮；内容区使用“开票订单 / 开票记录 / 常用抬头”三个同级 Tab，常用抬头在页内以数据列表呈现，提供搜索、筛选和新增抬头。
- 发票通过站内通知和邮箱交付，联系电话用于联系及可选通知；第三方返回结果未知时必须先查询后重试。
- 自助开票期为订单具备资格后的 12 个月，超期转人工支持或财务处理，不直接判定永久不可开票。

## 4. 状态口径

开票业务禁止用单一状态字段承载全部含义。系统分别维护：

1. 申请状态：草稿、待审核、已驳回、已撤回、已通过、已取消。
2. 开具状态：未提交、提交中、开票中、开票成功、开票失败、结果未知。
3. 票据状态：无票据、正常、红冲待处理/红冲中、已红冲、红冲失败。
4. 交付状态：未发送、发送中、已送达、部分送达、发送失败。

客户端可将四维状态映射为简明展示状态，后台必须保留各维原值、时间、操作者、原因、第三方请求号和状态变更日志。

当前客户端主状态固定为：待审核、开票中、已开票、已驳回、开票失败、红冲待确认、红冲处理中、红冲失败、已红冲、待确认重开信息、已撤回、已取消。客户端不展示“部分开票异常”“已部分红冲”或“部分成功”；这些仅可作为后台 ProviderTask/账本内部事实。一订单只能存在一条有效申请并生成一张有效蓝票。

更正申请另有独立状态：待审核、已通过、已驳回、已撤回/取消、红冲处理中、红冲失败和已完成；它不能覆盖原开票申请的四维状态。授权审批通过/驳回以 `status=PENDING_REVIEW + version` 原子竞争，审批事务内仅允许使用数据库短事务行锁和红冲账本锁，不得产生用户可见、跨请求持有的审批锁。

## 5. 文档维护规则

- 业务口径变化时，先更新需求分析中的决策记录，再同步用户侧、后台侧、流程文档和 Draw.io 图。
- 用户侧字段或动作变化时，同步检查后台审核字段、接口契约、状态映射、通知模板和埋点。
- 状态新增或迁移变化时，同步更新客户端状态图、后台状态图、异常补偿图和测试场景。
- 法律法规与第三方平台能力可能变化，上线前由财务、法务、税务和技术共同复核，文档中的产品规则不替代专业税务意见。
