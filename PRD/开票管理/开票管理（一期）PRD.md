### 0.3 一期依赖与不做的前提

- 一期**必须**依赖的财务侧能力：待审核申请的通过/驳回、审核通过后触发第三方开具的后台编排。开票配置（主体、内容、税务映射）在一期由财务后台或人工维护，客户端只消费服务端返回值。
- 一期**不做**红冲，因此「已开票后退款」不在客户端产生红冲任务；一期口径为：**已开票订单发生退款时，客户端不做任何红冲入口、不生成红票、不改变已开票记录**，由财务在后台线下台账跟进，二期由红冲任务正式承接（见 §7）。
- 一期**不做**更正，因此已开票记录不再提供「更正」操作；票面信息有误在一期走客服/财务线下处理，二期由更正申请承接。

## 1. 需求概述

### 1.1 背景与问题

费用管理高保真原型已拆分为四个独立页面，其中 `Prototype/费用管理-开票管理.html` 提供资格清单、三步申请、开票记录、常用抬头页内列表和票据演示操作。一期先打通**最高频、最刚需**的路径：用户自助申请 → 财务审核 → 第三方开票 → 交付下载，快速替代线下客服开票。

问题根因不是增加一个订单字段，而是缺少独立的发票申请、订单级开票关联、可开票余额、票据与交付模型。特别是法币充值与云币消费必须避免重复开票，支付、履约、退款和发票状态必须在页面上呈现为可解释的资格和动作。

红冲与更正属于**低频异常分支**，实现成本高、跨系统依赖多（税务红字信息确认、第三方红冲能力、原票账本），因此拆分到二期，避免阻塞一期主链路交付。

### 1.2 一句话目标与成功指标

**一句话目标：**让有权限用户在 12 个月自助窗口内从法币支付且满足履约条件的订单提交准确、可追踪、不可重复占用的电子发票申请，并在异常时获得可恢复的下一步动作。

|指标|定义|目标|数据来源|
|---|---|---|---|
|自助申请完成率|成功提交申请数 / 进入申请流程且存在可开票订单的会话数|≥85%|客户端事件与服务端提交信封|
|资格计算准确率|财务抽样核对一致订单数 / 抽样订单数|100%|资格服务、财务对账|
|重复开票事故|同一订单金额被两张有效蓝票覆盖的次数|0|InvoiceableBalance 与票据对账|
|审核及时率|SLA 内完成审核申请数 / 待审核申请数|≥95%|后台审核日志|
|第三方最终一致率|与第三方核对一致的已提交记录 / 已提交记录|100%|ProviderTask 对账|
|交付成功率|至少一个交付渠道成功的已开票申请 / 已开票申请|≥99%|InvoiceDelivery|
|核心页面可交互耗时|列表接口返回并可操作的 P95|≤2 秒|前端性能监控|

## 2. 信息架构、入口与用户流程

### 2.1 入口与路由

|入口|前置条件|页面/路由|初始参数|返回行为|
|---|---|---|---|---|

### 2.2 一期主流程（端到端）

```text
用户进入「费用管理 > 开票管理」
  -> 服务端返回默认可申请订单与统计（资格、原因、余额）
  -> 按关键词搜索，或在筛选抽屉中按「是否可申请」聚焦不可申请订单
  -> 点击一行「申请开票」（一次仅一个订单，一票一单）
  -> 服务端预览当前订单资格、金额与税种/内容兼容项
  -> 填写该订单票种、抬头、内容、邮箱和电话，核对并勾选确认声明
  -> submission_id 幂等提交，订单占用额度
  -> 申请写入开票记录，状态「待审核」
  -> 财务管理员审核通过（或驳回 -> 用户修改重提）
  -> 后台编排器调用第三方电子发票平台开具数电蓝票
  -> 第三方回调/查询确认成功，保存票据文件
  -> 站内 + 邮件交付，用户预览/下载/重发
  -> 一期闭环结束（红冲与更正属二期）
```

## 3. 页面与交互规格

### 3.0 页面整体结构

**页面目的：**在费用管理上下文中完成用户侧开票申请和票据追踪。

**呈现形态：**费用管理独立一级页签；页面内提供「开票订单 / 开票记录 / 常用抬头」三个同级 Tab。申请、新增/编辑抬头、不可申请原因、预览、重发使用 Modal；申请详情使用右侧 Drawer，常用抬头不使用 Drawer。客户端不提供人工开票工单入口；一期不出现任何红冲与更正入口。

**布局与滚动：**SystemFrame 提供顶栏和侧栏；业务内容独立滚动；表格容器允许横向滚动；申请 Modal 内部独立滚动；列表工具栏统一采用「左侧页面操作/业务指标、右侧搜索框+筛选」布局；单订单金额摘要和行内申请操作位于所属数据区，不设置选择摘要或批量申请按钮。

```text
┌────────────────────────────────────────────────────────────────────┐
│ 开票订单 / 开票记录 / 常用抬头                                      │
│ 开票订单 | 开票记录                                      常用抬头     │
├────────────────────────────────────────────────────────────────────┤
│ [页面操作 / 金额指标]                         [搜索框] [筛选]       │
│ 订单资格清单 N                                                      │
│ 订单资格表格                                                       │
│ 分页（数据列表右下方）                                             │
└────────────────────────────────────────────────────────────────────┘
```

### 3.2 申请开票弹窗

**页面目的：**在不允许用户修改金额和销售方的前提下，完成单订单确认、受票信息填写和提交确认。

**呈现形态：**三步 Modal，桌面宽度 760px、最大宽度 92vw，内容独立滚动。标题栏底部先显示分割线，分割线下的弹窗内容区顶部展示步进条「1 确认订单 → 2 填写信息 → 3 核对提交」，当前步骤和已完成步骤使用 primary 高亮，未到达步骤使用中性色。表单统一使用 90px 标签列和 400px 控件列，标签右对齐、控件左对齐且起点一致，间距 14px；输入框、下拉和单选组合控件高 30px，移动端控件列按可用宽度收缩。当前原型关闭按钮、取消、遮罩或 Esc 会直接关闭并丢弃内存表单；生产实现必须在检测到有效修改时增加未保存确认，此项属于原型模拟边界，不能据此降低数据保护要求。

#### 3.2.3 字段级校验

发票抬头右侧提供刷新图标。刷新保留所选抬头 ID，并同步最新名称、税号、银行、地址、电话和联系信息，成功提示「已刷新常用抬头信息，请核对后提交」并清空确认勾选；所选抬头已停用或删除时提示「当前抬头已停用或删除，请重新选择」，不静默套用其他抬头。新增和编辑的个人类型都禁选专票，保存与申请提交仍进行二次校验。

金额输入精确转换为整数分，汇总及占用计算使用整数运算，输出保留两位小数；不得仅将浮点运算结果 toFixed 后作为账本。接口采用整数分，越界或超过两位小数拒绝。已取消自助开票金额上限，不展示金额超限弹窗；开票申请仍按订单资格、支付方式、履约状态和税务配置校验。

### 3.4 开票记录与详情抽屉

#### 3.4.1 记录页签

结构化筛选字段固定为发票类型、开票状态和申请时间，在「筛选」打开的右侧抽屉中维护；申请单号、发票号码、开票订单、团队ID、申请人、发票抬头、金额等通过搜索框范围选择检索。记录页关键词搜索为范围搜索组合框：点击左侧范围前缀可选择搜索字段（全局搜索、申请单号、发票号码、开票订单、团队ID、申请人、申请时间、发票类型、发票抬头、金额、状态、发票编号），多关键词用中文逗号分隔、任一关键词命中即匹配（OR），搜索框即时生效并带清空按钮；抽屉条件确认后回第 1 页；取消、遮罩点击、关闭或 Escape 均丢弃重开任务。申请时间使用与订单管理创建时间一致的 300px 双端范围控件，显示「开始时间 ~ 结束时间」，支持双月日历、清空/取消/确定、单侧日期和逆序校验，按申请时间自然日闭区间筛选；逆序提交提示「开始申请时间不能晚于结束申请时间」。支付时间、申请时间两套日期筛选均以北京时间自然日为准，仅允许今天及以前，明天及未来日期禁选（日历禁选日期 hover 提示「只能选择今天及之前的日期」，确认及筛选提交校验失败 toast 同文案），历史缓存越界日期清空；未指定日期范围仍可看到当天记录，该限制只作用于日期筛选，不影响当天订单资格或申请。申请单号/发票号码为 `-` 或空值时不进入号码搜索索引，其他搜索字段按原逻辑匹配。

**一期开票状态选项为：全部、待审核、开票中、已开票、已驳回、开票失败、已撤回、已取消**（红冲处理中、红冲失败、已红冲为二期状态，一期不提供筛选选项、不进入状态分组顺序）。

表格固定为 12 列：申请单号、发票类型、发票抬头、发票号码、金额、申请时间、联系邮箱、开票订单、团队ID、申请人、开票状态、操作。状态使用纯语义色文字；工具栏左侧操作区提供「导出」与「刷新」按钮，右侧为搜索框与「筛选」入口，筛选旁显示当前筛选总数。「导出」弹窗提示「将按当前搜索与筛选条件导出 N 条开票记录。每次最多可导出 500 条数据」，确认后按当前条件导出。列表默认按状态分组升序排列，**一期状态顺序为：待审核、已撤回、已驳回、已取消、开票中、开票失败、已开票**；金额、申请时间等列仍支持手动升降序。申请单号提供复制按钮，成功提示「申请单号已复制」，失败提示「复制失败」；已驳回记录的开票状态旁提供「查看驳回原因」图标，无原因时展示兜底文案「暂无驳回原因，请联系财务确认」。每条记录包含末行均保留下边框；分页器距表格 20px，默认 10 条/页并支持 10、20、50 条/页。

#### 3.4.2 详情抽屉

详情使用 800px 右侧 Drawer，**一期区块顺序固定为 5 段**：

1. 申请摘要：申请单号、申请时间、团队ID、申请人（脱敏登录账号）、当前状态、申请金额；
2. 受票信息：发票类型、发票抬头、完整税号、接收邮箱、完整联系电话；
3. 关联订单：订单号、订单类型、商品名称、订单金额、应付金额；应付金额为优惠抵扣后的金额，订单金额独立取值，未优惠时可相同。不展示销售方及「一订单一张发票，当前申请仅关联 1 个订单」提示；表格横向滚动；
4. 票据与交付：发票号码、开票时间、票据文件、交付渠道；文件字段显示 `云登电子发票_发票号码.pdf` 等文件名，未生成显示「未生成」；
5. 处理时间线：使用竖线＋圆点，按时间从早到晚展示已发生节点，每项包含节点名称、处理时间、处理内容；待审核仅显示提交节点，不预填尚未发生的审核或成功节点。撤回和重发操作追加对应事件。历史时间为内联 Mock，生产读取审计事件。

> 二期「红冲与重开」区块（更正状态、红冲金额、红票号码、处理进度、失败原因、自动重开任务）在一期不展示；二期实现时插入到「票据与交付」与「处理时间线」之间，保持区块顺序兼容。

详情底栏按当前状态展示：**待审核为关闭、撤回；已驳回/已撤回/开票失败为关闭、修改重提；开票中为关闭、查看进度；已取消仅关闭；已开票为重发、下载、预览**（一期已开票不提供「更正」）。沿用原操作校验。底栏遵循 design.md §5.7：高 64px、左右内边距 24px、按钮右对齐、间距 12px；按钮遵循 §5.1：32px 高、4px 圆角，主按钮蓝底白字、次按钮白底描边，包含 hover/active/focus-visible 状态。底部全部使用纯文字按钮，不显示图标，保留原功能。文件名为票据参数演示，不代表已生成真实 PDF；预览为 760px 票面演示 Modal；下载生成明确标记「原型演示」的本地 HTML 文件；重发为 760px 单邮箱表单。生产环境仍须使用对象级鉴权和短时文件授权。

|客户端状态|允许操作|
|---|---|
|待审核|撤回、详情|
|已驳回|修改重提、详情|
|已撤回|修改重提、详情|

### 3.6 超期支持指引

`SELF_SERVICE_EXPIRED` 订单只提供「查看原因」。760px 居中原因 Modal 明确展示订单已超过自助开票期限，并提示「请联系平台支持」。客户端不展示人工工单按钮、不打开人工工单弹窗，也不维护工单列表或状态；后续处理由平台支持和财务运营在后台完成，订单资格以刷新后服务端结果为准。

### 3.7 页面 Mock 数据与数据驱动要求

原型必须使用内联 JS 数组/对象驱动渲染，不在 HTML 中堆静态表格行。Mock 数据不得连接真实支付、订单、第三方发票或文件服务；用户可见开票字段使用合成值并完整展示，敏感字段仍不得进入 URL、存储、前端日志或埋点。

#### 3.7.1 订单 Mock 最小集合

### 3.8 原型模拟边界

以下为当前 HTML 的演示简化，不得作为生产业务规则：

- 单订单预览展示一条订单和一张发票，第二步使用该订单表单；生产环境仍须在提交事务内校验开票主体、票种、税目、税率和内容兼容性。
- 关闭申请 Modal 不做未保存确认；生产实现检测到有效修改时必须二次确认。
- 已驳回可修改重提；开票失败仅在确认未开票且旧任务关闭后修改重提，补正仍只对应原订单，生产环境必须使用服务端补正草稿。
- 下载生成本地 HTML 演示文件，不是税务票据；生产环境必须再次鉴权并使用短时授权下载服务端文件。
- 重发成功 Toast 在原型中包含邮箱并立即更新 Mock；生产环境只能提示「发送任务已提交」，不得在 Toast 暴露收件邮箱，最终结果以异步交付状态为准。
- 当前原型用行渲染版本及表单打开版本拦截过期操作；可通过 `window.invoiceStatusAdapter` 接入已鉴权的服务端快照查询，记录页每 10 秒查询、窗口重新聚焦时查询，后台页隐藏时跳过，页面离开停止。生产推荐 WebSocket/SSE 推送，失败回退轮询；操作提交仍由后端校验，不能依赖最后一次轮询。
- 多标签页原型以浏览器命令互斥和共享状态版本演示竞争，不存储抬头、税号和联系人。跨标签页命令通过 `navigator.locks` 请求共享键 `yundeng.invoice.lifecycle.v4-status-examples` 原子执行；环境不支持 Web Locks 时提示「当前预览环境不支持跨标签页原子操作，请使用本地 HTTP 预览」。生产采用服务端原子条件更新、请求幂等与权限校验。

## 5. 数据模型、业务规则与状态机

### 5.1 领域对象与关系

|对象|唯一标识|页面使用字段|关系|
|---|---|---|---|
|订单|`order_id`|支付、履约、退款、主体、资格和版本|一订单最多对应一条有效开票申请和一张有效蓝票|
|可开票余额|`order_id`|法币实付、退款、占用、蓝票、余额|一订单一账本|
|开票申请|`application_id`|申请人、受票信息、状态、版本|一申请一订单、一张蓝票|
|订单关联|`allocation_id`|订单、申请、订单金额和快照|一对一关联；一个申请不得关联多个订单|
|抬头档案|`title_profile_id/version`|常用抬头和默认状态|申请保存不可变快照|
|票据|`invoice_document_id`|蓝票号码、金额、文件|一期每个有效申请仅一张蓝票|
|交付|`delivery_id`|渠道、收件版本、状态、尝试|一票据多渠道|
|提交信封|`submission_id`|订单 ID、结果、父提交|一提交一申请|

> 二期扩展：新增 `InvoiceCorrectionRequest`（更正申请）、红票文档与红冲账本 `InvoiceRedAllocation`。一期建表时须预留 `document_type`（蓝票/红票）、`source_document_id`（红票指向原蓝票）、`red_reason` 等字段，**但一期不写入、不展示**，以降低二期迁移成本。

```text
用户/团队 -> 订单 -> 可开票余额
申请人 -> InvoiceApplication -> InvoiceOrderAllocation -> 订单
InvoiceApplication -> InvoiceDocument -> InvoiceDelivery
InvoiceApplication -> ProviderTask -> 第三方电子发票平台
（二期：InvoiceDocument -> InvoiceCorrectionRequest -> 红票/自动重开任务）
```

### 5.2 枚举与客户端状态机

#### 5.2.1 申请状态

|代码|展示|进入条件|可执行动作|退出条件|
|---|---|---|---|---|
|`PENDING_REVIEW`|待审核|申请事务成功|查看、撤回|授权管理员/财务直接通过或驳回；用户撤回；系统取消（退款），均按 version 原子竞争|
|`APPROVED`|已通过|财务审核通过|查看开具状态|开具任务推进（客户端展示为开票中）|
|`REJECTED`|已驳回|财务驳回|查看原因、编辑原单重提草稿|原申请新版本进入待审核|
|`WITHDRAWN`|已撤回|用户撤回成功|查看、修改重提|原申请新版本进入待审核|
|`CANCELLED`|已取消|退款或系统取消|查看、从订单重新申请|终态|

#### 5.2.2 开具、票据和交付状态（一期）

后台可记录同一订单蓝票的重试、结果未知等内部任务事实；客户端只展示单订单派生状态：

|客户端状态|精确条件|动作|
|---|---|---|
|开票失败|`issuance_status=FAILED` 且确认唯一蓝票未生成|查看原因、修改重提（仅旧任务已关闭且未开票）|
|开票中|申请已通过且开具为提交中/开票中/未知|查看进度|
|已开票|仅 `issuance_status=SUCCEEDED` 且未命中更高红冲状态|预览、下载、重发|
|待审核/已驳回/已撤回/已取消|按申请状态|见操作矩阵|

一期客户端状态集固定为：**待审核、已驳回、已撤回、已取消、开票中、开票失败、已开票**（7 类）。二期新增红冲处理中、红冲失败、已红冲。

交付状态只作附加标签（未发送/发送中/已送达/部分送达/发送失败）；邮件失败不改变已开票。普通申请仅对应一张蓝票，普通开具任务只处理唯一目标蓝票，重试与回调不得新增蓝票。

### 5.3 业务规则清单

|编号|规则|触发时机|实现责任|验证方式|
|---|---|---|---|---|
|R-01|法币支付订单可开票，云币消费不可开票；充值按法币实付形成资格|资格查询/提交|资格服务|订单矩阵测试|
|R-02|服务订单必须支付成功且履约完成/权益生效|资格查询/提交|订单与资格服务|履约边界测试|
|R-03|当前余额为法币净额减有效占用和未红冲蓝票金额，金额以分保存|统计/提交|发票服务|金额对账|
|R-04|一票一单：每个订单按全部剩余可开票金额一次申请并生成一张发票，申请金额只读|预览/提交|发票服务|单订单金额测试|
|R-05|客户端不支持多订单合并，服务端拒绝同一申请携带多个订单|提交|发票服务|多订单请求拒绝测试|
|R-06|个人仅普通发票，企业可普通/专票|表单|前后端|字段测试|
|R-07|内容来自财务配置，不允许自由输入|内容选择|配置服务|未知内容拒绝|
|R-08|申请提交保存抬头快照，主数据变化不覆盖历史|提交/抬头编辑|发票服务|历史快照测试|
|R-09|每个写操作需权限、幂等、版本校验、成功刷新和失败保留输入|所有写操作|前后端|接口与 E2E|
|R-10|第三方结果未知先查后重试；唯一蓝票成功后不得重提或再次开具|详情/恢复|后台编排|异常流程测试|
|R-11|交付与开具正交；文件/邮件失败只更新交付|详情|交付服务|状态聚合测试|
|R-12|待审核阶段订单退款时自动取消申请并释放占用；已开票后退款一期不生成红冲任务（二期承接）|资格/退款回调|发票服务|退款边界测试|

一票一单专项验收：零订单、多订单或订单数组提交必须拒绝；超限不得拆票；同一请求重试及重复成功回调只返回同一蓝票 ID；原蓝票仍有有效金额时不得提交新的普通申请。

### 5.4 并发、幂等与一致性

|场景|约束/方案|用户可见结果|
|---|---|---|
|连续点击提交|前端按钮 loading；`submission_id` 和 `(submission_id, order_id)` 唯一|只创建一条申请和一张发票|
|多人申请同订单|服务端锁定当前订单账本、校验 version 和余额|一方成功，另一方收到最新冲突|
|并发审核/撤回竞争|普通申请以 `status=PENDING_REVIEW + version` 条件更新；短事务内可锁订单账本，禁止跨请求审批锁|仅一个命令成功，失败方刷新最新状态|
|订单提交失败|单订单事务回滚，确认未开票且旧任务关闭后创建补正草稿|原失败版本只读，原申请补正版本仍只对应原订单|
|网络超时|查询提交信封；结果未知不新建 ID|按钮保持确认中，最终结果可追溯|
|抬头并发编辑|`title_profile.version` 乐观锁|保留输入，提示对比后重试|
|打包/重发任务重复|`archive_id`/request_id 幂等，任务持久化|刷新页面不创建重复任务|

开票记录中的待审核撤回、已驳回/已撤回/开票失败修改重提均须携带 request_id 和 expected_version，由服务端按当前状态原子校验；冲突时 Toast 告知实际最新状态并刷新列表、详情和时间线，不新增申请单、不重复释放占用。网络超时进入「提交结果待确认，请刷新查看」，未知结果只能查询。在入口、最终确认及提交事务均须再次核对版本和状态：已被撤回、财务已通过、已被重提或补正分别提示实际原因；重复请求返回原结果，不新增申请或重复释放金额。重提/补正、撤回、重发、抬头编辑均需校验对象存在、权限、状态和版本；同键同载荷重放返回同结果，同键异载荷拒绝；未知结果只查询，不生成新请求绕过。历史版本和第三方旧任务回调不得覆盖新版本。第三方回调、重发、抬头编辑和多标签页重复提交沿用同一版本、幂等和迟到事件归属规则。

原单重提与版本审计规则：

- 已驳回或已撤回后修改重提，或开票失败后修改重提，均保留原 `application_id` 和原订单；提交成功新增不可变 `revision`，对象 `version` 递增，当前状态更新为 `PENDING_REVIEW`，开具状态重置为 `NOT_SUBMITTED`。首次申请时间保留，另记最近提交时间；列表保持一条申请记录。
- 原版本完整保存票种、抬头、税号、内容、金额、联系人、企业信息、申请人及审核/失败结果；审核人、处理时间、原因与第三方任务关联在审计事件中永久保留。详情时间线按先后追加修改重提或补正提交事件，并可展开历史提交快照，不能只保存一条文字日志。
- 开票失败补正必须有确认未开票证据、旧任务已关闭且不可重试；仅 `canRemediate` 标记不足以授权。旧版本保留已通过与失败事实，新版本重新审核；旧任务迟到事件只归属旧版本，不得改写当前版本。
- `POST /billing/invoice-applications/{id}/revisions` 的状态和版本条件更新、资格复核、单订单唯一有效占用、版本快照及事件写入必须在同一事务完成；任一失败全部回滚。已生成有效蓝票、结果未知或其他申请占用时拒绝。
- 验收：连续提交或旧版本提交只成功一次；多次驳回再重提始终同号且版本递增；失败补正只保留一份占用；原票有效/结果未知/任务未关闭时拒绝；历史快照不可变。

一票一单统一约束的原子性要求：同一订单同一时点最多存在一条有效申请占用和一张仍有有效金额的蓝票；占用转为蓝票时须原子结转，已有有效蓝票不得再次普通申请。服务端必须同时校验订单资格、版本、占用及有效蓝票，不能只依赖前端单选或金额余额。

|`TITLE_REFERENCED`|阻止删除，建议停用|否|该抬头已被历史申请引用，请改为停用|
|`INTERNAL_ERROR`|保留输入并允许恢复|幂等写可重试|系统异常，请稍后重试|

### 6.3 异步任务约定

提交信封、第三方开票、文件补拉、打包下载和邮件发送均须持久化任务。前台可见时每 5–10 秒轮询对应查询接口；离开页面停止轮询，重新进入按任务 ID 恢复。状态由后端返回，不由前端估算。任务结果文件使用短时签名 URL，过期后最多自动重新获取一次；重试必须有 request_id/幂等键和最大次数，结果未知必须先查询真实结果。

> 二期增加红冲任务的持久化与轮询。
