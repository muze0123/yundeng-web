## 1. 需求概述

### 1.0.1 页面定位

|定位维度|页面定义|
|---|---|
|页面职责|让有权限的用户从真实可开票订单选择订单、填写受票信息、提交申请，并追踪审核、开具、交付、红冲和重开草稿状态|
|系统位置|费用管理 > 订单管理 > 开票管理二级视图；上游是订单、支付、履约、退款事实，下游是云登后台审核和第三方电子发票开具|
|核心决策|用户决定哪些订单一起申请、使用哪类发票和抬头，并确认系统拆分结果；用户不能决定开票主体、税率、税收分类或申请金额|
|边界|本页不支付、不修复履约、不审批退款、不维护销售主体/税务编码、不直接调用第三方开票平台；这些能力由相应服务承接|
|价值与风险|减少客服线下开票，保证法币交易可追溯；错误的资格、金额或权限判定会造成重复开票、税务风险或敏感信息泄露|

|S-08|P0 重复提交与网络恢复|用户连续点击或提交响应超时；页面显示“正在确认提交”，使用原 submission_id 查询结果|请求体一致返回原结果并续跑未处理分组；请求体变化返回幂等冲突；禁止创建新 submission_id 盲目重提|

### 1.1 背景与问题

费用管理当前可以查询交易订单，但订单管理没有申请开票入口、可开票金额和票据状态。用户只能通过客服或线下沟通，无法自助提交、追踪审核和取得电子发票；后台也没有与第三方电子发票平台连接的审核、开具、交付、红冲和审计工作台。

问题根因不是增加一个订单字段，而是缺少独立的发票申请、订单分摊、可开票余额、票据、交付、红冲和第三方任务模型。特别是法币充值与云币消费必须避免重复开票，支付、履约、退款和发票状态必须在页面上呈现为可解释的资格和动作。

本页面通过“可申请/不可申请”订单双范围、三步申请弹窗、开票记录、详情抽屉和常用抬头管理建立用户侧闭环；所有资格、金额、状态和权限仍以服务端返回为准。

### 1.2 一句话目标与成功指标

**一句话目标：**让有权限用户在 12 个月自助窗口内从法币支付且满足履约条件的订单提交准确、可追踪、不可重复占用的电子发票申请，并在异常时获得可恢复的下一步动作。

|指标|定义|目标|数据来源|
|---|---|---|---|
|自助申请完成率|成功提交申请数 / 进入申请流程且存在可开票订单的会话数|≥85%|客户端事件与服务端提交信封|
|资格计算准确率|财务抽样核对一致订单数 / 抽样订单数|100%|资格服务、财务对账|
|重复开票事故|同一订单金额被两张有效蓝票覆盖的次数|0|InvoiceableBalance 与票据对账|
|审核及时率|SLA 内完成审核申请数 / 待审核申请数|≥95%|后台审核日志|
|第三方最终一致率|与第三方核对一致的已提交记录 / 已提交记录|100%|ProviderTask 对账|
|交付成功率|至少一个交付渠道成功的已开票申请 / 已开票申请|≥99%|InvoiceDelivery|
|核心页面可交互耗时|列表接口返回并可操作的 P95|≤2 秒|前端性能监控|

|订单行“查看开票原因”|订单不可申请或暂不可申请|同上|`invoiceTab=eligible`、`eligibility=INELIGIBLE`、定位订单|返回原因范围|
|订单详情“开票信息”|存在本人有权查看的申请|同上|`invoiceTab=records&applicationId=...`|无权或不存在不回退到其他申请|
|消息中心发票状态通知|通知对象仍有权限|同上|`invoiceTab=records&applicationId=...`|关闭详情返回记录|

外层路由只使用稳定 `page=billing`。模块内部的 Tab、筛选和详情参数写入 SystemFrame 约定的 `moduleSearch` 命名空间，不覆盖外层 `page`；无效 Tab 回退“开票订单”，无效申请 ID 展示对象不存在状态。

### 2.2 主流程

```text
进入开票管理
  -> 服务端返回默认可申请订单与统计
  -> 筛选或切换不可申请范围
  -> 选择订单（跨页保留，最多 100 笔）
  -> 服务端预览兼容组与销售主体拆分
  -> 分组填写票种、抬头、内容、邮箱和电话
  -> 查看订单明细与金额，勾选确认声明
  -> submission_id 幂等提交
  -> 待审核申请写入记录
  -> 后台审核通过后第三方开票
  -> 票据文件取得并站内/邮件交付
  -> 用户查看、下载、重发或按规则发起更正
```

### 3.5 更正申请与重开草稿

用户只能对 `issuance_status=SUCCEEDED` 且蓝票有效、无进行中退款红冲/更正的申请发起更正。更正表单必须包含：目标蓝票、原因码、说明、拟更正票种/抬头/税号/内容/联系人快照、确认红冲声明。目标红冲金额由服务端按当前有效蓝票全额计算，不接受用户自定义。

更正主状态为 `PENDING_REVIEW`、`REVIEWING`、`APPROVED`、`RED_PROCESSING`、`COMPLETED`，分支为 `REJECTED`、`WITHDRAWN`、`CANCELLED`、`RED_FAILED`；待受票方确认、提交中、红冲中、结果未知作为子状态展示。驳回后创建新 `correction_request_id` 并关联 `previous_correction_request_id`，不覆盖旧记录。全部目标红冲成功后，系统以 `correction_request_id` 幂等创建唯一重开草稿；用户必须主动确认和提交，草稿不会自动开票。

### 3.6 超期支持指引

`SELF_SERVICE_EXPIRED` 订单只提供“查看原因”。原因 Drawer 明确展示订单已超过自助开票期限，并提示“请联系平台支持”。客户端不展示人工工单按钮、不打开人工工单弹窗，也不维护工单列表或状态；后续处理由平台支持和财务运营在后台完成，订单资格以刷新后服务端结果为准。

### 5.1 领域对象与关系

### 6.2 通用响应与错误约定

```json
{
  "requestId": "req_xxx",
  "code": "VALIDATION_ERROR",
  "message": "请求参数不合法",
  "fieldErrors": [{"field": "taxpayer_id", "code": "INVALID_TAXPAYER_ID", "message": "纳税人识别号格式不正确，请核对"}]
}
```

|错误码|页面处理|是否重试|正式文案|
|---|---|---|---|
|`UNAUTHENTICATED`|提示后跳转登录，恢复非敏感上下文|一次|登录已失效，请重新登录|
|`FORBIDDEN`|展示无权限或权限变化状态|否|您暂无权限执行此操作|
|`VALIDATION_ERROR`|字段级展示|否|使用接口返回字段文案|
|`VERSION_CONFLICT`|拉取最新对象并保留输入|否|订单信息已变化，请核对最新金额后重新提交|
|`IDEMPOTENCY_CONFLICT`|定位原提交，不创建新结果|否|该提交编号已用于其他内容，请查询原申请|
|`RATE_LIMITED`|按 retryAfter 禁用|按服务端|操作过于频繁，请稍后再试|
|`DEPENDENCY_UNKNOWN`|保持处理中/结果未知|先查询|正在确认开票平台结果，请勿重复操作|
|`TITLE_REFERENCED`|阻止删除，建议停用|否|该抬头已被历史申请引用，请改为停用|
|`INTERNAL_ERROR`|保留输入并允许恢复|幂等写可重试|系统异常，请稍后重试|

### 6.3 异步任务约定

提交信封、第三方开票、文件补拉、打包下载、邮件发送和红冲均须持久化任务。前台可见时每 5–10 秒轮询对应查询接口；离开页面停止轮询，重新进入按任务 ID恢复。状态由后端返回，不由前端估算。任务结果文件使用短时签名 URL，过期后最多自动重新获取一次；重试必须有 request_id/幂等键和最大次数，结果未知必须先查询真实结果。

## 7. 异常、边界与降级

|场景|页面表现|系统处理|恢复路径|
|---|---|---|---|

|默认无数据|内容空态与查看不可申请|不报错|切换范围或返回订单|

## 11. 发布、灰度与回滚

|阶段|内容|通过条件|回滚条件|
