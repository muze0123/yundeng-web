# 《Vibe Coding产品PRD模版》

> 定位：适用于 Web 管理后台、桌面端、移动端与跨端功能的**可开发 PRD**。
交付对象：产品、设计、前端、后端、测试、数据、运维与项目经理。
使用原则：用“可验证的事实、规则和状态”替代“做一个、支持一下、尽量、适配”等模糊描述。本文中 `【】`、`< >`、`[ ]` 均为待填写占位内容；交付前必须清空所有未决占位。

## A\. 这份模板的编写范式

### A\.1 从样本中提炼的有效做法

高质量页面 PRD 不是原型旁白，而是研发可据以实现并让测试可据以验证的契约。角色/成员管理类页面证明，复杂后台必须把组织、权限、字段校验、批量操作、特殊主体保护、空/异常状态写清；订单页面证明，跨模块状态口径、敏感数据处理、外部同步时效和一期边界必须前置；消息和任务页面证明，全局入口、筛选关系、未读/任务状态、轮询、文件生命周期及跨页跳转不能只在原型里默认存在；增长弹窗类需求则证明，目标、资格、频控、外部转化的“不可直接推断”、配置和埋点闭环要独立成章。

因此，完整 PRD 应同时回答以下问题：

|研发/测试的核心疑问|PRD 必须提供的答案|
|---|---|
|为什么做、做到什么程度|背景、问题、目标、量化指标、范围与非目标|
|谁能在何处使用|用户/角色、权限、入口、前置条件、端与版本|
|页面长什么样、怎么操作|信息架构、布局、组件/字段、交互、文案、响应式规则|
|系统到底如何判定|数据字典、状态机、业务规则、优先级、边界、幂等与并发策略|
|前后端如何对接|API 契约、错误码、事件、缓存/刷新、权限校验和异步任务约定|
|出问题或数据缺失怎么办|空、加载、失败、离线、超时、权限变化、重试与降级|
|如何证明交付正确|埋点、日志、验收标准、自测用例、灰度/回滚和待确认事项|

### A\.2 “最小闭环”判定

一项功能仅当用户能完成目标动作、后端能持久化或异步处理结果、权限与审计可追溯、失败可恢复、数据可观测时，才算闭环。不要把“按钮可点”当作完成。每个写操作至少要写明：触发条件、入参、前端防重复、服务端幂等键/版本校验、成功后的界面刷新、失败后的界面回滚、审计记录与埋点。

### A\.3 需求分层

|层级|写什么|典型遗漏|
|---|---|---|
|L0 业务层|目标、角色、范围、指标、约束|只描述 UI，没人知道为何做|
|L1 体验层|页面、字段、流程、文案、状态、交互|只给原型，未定义规则|
|L2 领域层|实体、关系、状态机、规则、权限、审计|多端/多页面状态口径不一致|
|L3 实现层|API、错误、异步、缓存、性能、安全、埋点|开发依赖口头补充，联调反复返工|
|L4 验收层|验收标准、测试矩阵、发布与回滚|只能“看起来差不多”地验收|

### A\.4 强制写作规则

1. **一个概念一个口径。**同一状态、金额、人数、时间、权限范围只定义一次；其它章节引用该定义。

2. **事实与假设分开。**已确认内容写“规则”；接口、运营、法务尚未确认的内容写入“待确认”，不得伪装成结论。

3. **按状态写，而非仅按页面写。**每个对象明确状态值、进入条件、退出条件、可做动作、展示文案和服务端事件。

4. **权限由后端兜底。**前端隐藏或置灰只是体验，所有读取/写入接口必须再次鉴权。

5. **批量操作允许部分成功。**写清作用范围（当前页/当前筛选/已选项）、最大数量、逐项结果、可下载失败明细及重试策略。

6. **敏感数据默认最小暴露。**明确脱敏、复制、导出、下载、日志和埋点的处理方式；不要把明文写进前端埋点。

7. **文案也是接口。**高频提示、确认弹窗、空态和错误提示必须给正式文案，不把“提示用户”留给开发临场发挥。

### 1\.0\.1 页面定位（建议默认填写）

页面定位用于定义本页面在产品体系中的职责边界，而不是重复页面名称。对存在独立入口、承接上下游流程、涉及多角色协作、存在详情/列表/编辑等多页面组合，或可能与相邻模块职责重叠的功能，必须填写；纯展示型、无独立业务决策的通用组件可简写为“复用组件，不单独定义页面定位”。

|定位维度|必须说明|填写示例|
|---|---|---|
|页面职责|本页解决的核心任务与不承担的任务|“集中查询并处理导出任务；不在本页发起导出。”|
|系统位置|所属模块、入口、上下游页面及深链参数|“由成员导出成功提示进入，默认定位下载任务 Tab。”|
|核心决策|用户在此需要判断、选择或提交什么|“按状态筛选订单，并决定查看详情或发起异常。”|
|边界|与相邻模块的分工、一期不做的动作|“只读订单与标记异常；退款由售后工单处理。”|
|价值与风险|效率/合规/风险控制价值及错误操作后果|“缩短异常定位时间；导出需权限与审计。”|

**可复制填写：**“【页面名称】是【系统/模块】中的【页面类型】，面向【主要角色】在【触发场景】完成【核心任务】。它承接【上游入口/数据】并输出【下游动作/状态】，核心决策是【】。本页不负责【】，相关能力由【模块】承接；当【风险条件】发生时，必须【控制措施】。”

### 1\.0\.2 用户场景（建议默认填写）

用户场景与 JTBD 互补：JTBD 描述长期要完成的任务，场景描述一次具体使用发生时的触发、上下文、路径、例外与结果。凡是页面有多入口、预设筛选、异步任务、权限差异、异常分支或会影响跨页状态时，必须至少列出“正常主路径、异常/恢复路径、权限/边界路径”三类场景。

|场景字段|填写要求|
|---|---|
|场景名称与优先级|按“角色 \+ 触发 \+ 目标”命名，如“运营人员从异常待办查看订单”；标注 P0/P1。|
|前置条件|账号、权限、对象状态、网络/外部依赖和初始数据。|
|触发与路径|入口、携带参数、用户逐步动作与系统逐步响应；每步可观察。|
|成功结果|界面最终状态、持久化结果、后续可达页面和应上报事件。|
|中断/恢复|校验失败、权限不足、并发冲突、网络中断、异步失败、关闭再进入时如何处理。|

**场景模板：**“S\-01【P0】【角色】在【前置条件】下，从【入口】进入【页面】；当其【动作 1】时，系统【响应 1】；当其【动作 2】时，系统【响应 2】；成功后【持久化/跳转/提示/埋点】。若【异常条件】，则【降级/错误文案/重试/状态保留】。”

**场景覆盖检查：**至少覆盖首次进入、默认查询、带参数进入、创建/编辑/删除、批量处理、无数据、加载失败、无权限、并发/重复提交、异步处理中与任务终态；不适用项必须显式写“不适用”及原因。

### 1\.0\.3 边界条件汇总（建议默认填写）

边界条件不是“开发兜底”，而是产品规则在极值、例外和状态切换时的明确行为。对于存在状态流转、金额/数量/时间限制、数据脱敏、角色权限、异步任务、并发编辑、搜索筛选、批量操作或外部依赖的需求，必须在需求概述先建立边界条件索引；页面级规格、状态机、接口及验收用例再按编号展开。纯静态展示页面可写“不适用”，并说明不存在可变状态或交互边界的原因。

**编写规则：**每条边界必须是“可触发、可判断、可实现、可验收”的 if–then 规则，不能只写“异常处理”“长度过长时截断”。需明确触发条件或阈值、系统判定、前端表现、服务端结果/数据状态、用户是否可恢复，以及对应的页面或规则编号；未知业务口径必须列入 1\.5 前置约束与假设，标明确认人和截止时间，不能由研发自行猜测。

|边界类别|必须覆盖的判断点|典型示例|
|---|---|---|
|输入与展示|空值、最小/最大长度、格式、非法字符、精度、超长文本、省略与复制、默认值。|搜索词为空时返回默认列表；超过【50】字符时阻止查询并展示字段级错误；订单号超过容器宽度时省略，但悬停/复制可取得完整值。|
|状态与时序|初始状态、允许/禁止转换、倒计时临界点、过期、撤销、重复操作、刷新后的状态回退。|仅【进行中】订单可结束；倒计时归零后服务端自动取消；前端倒计时仅展示，不得代替服务端状态判定。|
|数据与计算|0 值、空集合、负值、上限、舍入、币种/单位、时区、统计口径、数据延迟与刷新时机。|金额为 0 显示【¥0\.00】；千分位、精度与舍入规则由服务端统一；外部结果未回传前显示【处理中】而非成功。|
|权限与隐私|无菜单权限、无数据权限、字段脱敏、越权访问、权限在操作中变更、审计与下载控制。|手机号默认脱敏；有授权时可临时查看明文并记录审计；直达链接无权限时进入明确的无权限状态，不返回空白页面。|
|异步、并发与外部依赖|重复提交、并发修改、幂等键、任务排队、超时、重试、网络中断、回调失败、第三方不可用。|提交后按钮 loading 并防重复点击；版本冲突时保留用户输入并提示刷新/合并；导出任务失败可重试且不重复生成有效文件。|
|页面与布局|加载、空数据、筛选无结果、局部失败、长列表、横向溢出、窄屏、抽屉关闭、离开未保存页面。|查询无结果使用内容区空状态；表格超宽只在表格容器横向滚动；关闭未保存表单时二次确认且说明保留/丢弃规则。|

|编号|触发条件/前置状态|判定与系统规则|用户可见表现与恢复路径|数据、接口与验收关联|
|---|---|---|---|---|
|B\-01|【角色】在【页面】输入【字段】为【空值/阈值/非法值】|【前端预校验/服务端最终校验】；是否允许提交【是/否】|【字段错误/空状态/禁用/二次确认/Toast】；用户可通过【动作】恢复|字段 key【】；错误码【】；引用【3\.1\.2/F\-xx/API\-xx/TC\-xx】|

**边界条件覆盖检查：**至少逐项检查输入、状态、时间、金额/数量、列表空态、长文本、权限/脱敏、网络/外部依赖、异步任务、并发/重复提交、撤销/删除、路由参数与响应式布局。凡是用户会在异常下迷失、数据可能被误改、服务端和前端可能产生不同结果、或需要研发选择默认行为的场景，均必须形成 B 编号。

### 1\.0\.4 Toast 提示汇总（按需填写）

Toast 汇总应在需求概述中作为“非阻塞即时反馈”的单一索引：适用于操作已完成、操作失败但用户仍留在当前上下文、复制/刷新等轻量结果，以及可恢复的网络异常。它不替代字段级校验、页面空状态、危险操作二次确认、任务进度/结果页或必须被用户阅读的系统告警。查询无结果优先用内容区空状态；输入格式/长度问题优先用字段级错误；删除、结束、发布等不可逆操作须先确认，成功或失败后再按需提示。

**去重原则：**本节维护跨页面可复用的提示编号与正式文案；3\.1\.4 仅引用 T 编号并补充页面位置/变量，不应为同一触发条件重复维护两套文案。网络异常、登录过期、权限不足、通用操作失败等平台级文案优先复用；业务特定失败必须保留可行动信息，避免只写“失败，请重试”。

|编号|页面/区域与触发条件|级别与正式文案|持续、去重与后续行为|数据状态与关联规则|
|---|---|---|---|---|
|T\-01|【页面/操作】成功完成，例如复制、保存、刷新|成功；【订单号已复制/保存成功】|展示【】秒；同类提示【替换/合并/排队】；是否自动刷新【】|服务端成功条件【】；引用【A\-xx/API\-xx/TC\-xx】|
|T\-02|【页面/操作】失败，例如取消订单、结束订单、提交保存|错误；【操作失败，请重试】或【具体失败原因与下一步】|展示【】秒；按钮恢复可点；是否提供【重试/查看详情】入口【】|失败后数据是否回滚/保持【】；错误码【】；引用【B\-xx/API\-xx】|
|T\-03|平台级网络、登录或权限异常|错误/警告；【网络异常，请检查网络连接】、【登录已过期，请重新登录】、【您没有权限执行此操作】|防止同一错误连续弹出；登录过期跳转前说明；权限不足不自动反复重试|~~【修订前】该字段未填写。~~<br>错误源【网络/鉴权/权限码】；引用【全局错误码/权限规则】|

**Toast 最小规格：**每条 T 编号必须写明触发事件、前置/返回条件、提示级别、正式文案、变量替换规则、展示时长、同类消息去重方式、触发后数据/UI 状态、是否有可点击动作，以及关联的错误码和测试用例。成功 Toast 不能在服务端结果未确认前提前出现；异步任务仅提示“已提交/处理中”时，还须给出任务状态的可查询入口与最终结果反馈。

**文案规范：**成功文案使用“对象 \+ 已完成”的确定表达；失败文案优先说明原因与可行动下一步；不要泄露内部错误码、技术栈或敏感数据。示例：可写“订单已取消”“刷新失败，请重试”；不可仅写“Error”“请求失败”。若一次操作涉及多个对象，应明确成功/失败数量和失败项获取路径。

### 1\.1 背景与问题

【用 2–5 段说明现有流程、用户证据和造成的损失。避免“为了提升体验”这种无证据表述。】

- 当前流程：`【角色】在【场景】通过【现有路径】完成【任务】`。

- 已知问题：`【可量化问题/投诉/效率损失/风险】`。

- 根因假设：`【流程、数据、权限、性能或认知问题】`。

### 3\.0 页面整体结构（独立页面与全局框架必填）

本节用于定义页面在产品信息架构中的空间骨架、全局区域责任和跨端行为，使设计、前端、后端能在实现前对固定区、滚动区、内容容器、全局浮层与响应式降级达成同一理解。凡是新增独立路由、详情页、工作台、列表页、配置页、带导航壳的业务页面，或会改变全局导航、抽屉、悬浮入口、页面滚动策略的需求，均应填写本节；仅在既有页面中新增且不改变版式的微型控件，可注明“沿用【页面/组件】布局规范”，并仅写差异。

**填写原则：**先说明页面由哪些区域组成，再说明每个区域的位置、尺寸、内容、状态和边界；尺寸不得只写“适中”“自适应”，须给出固定值、最小/最大值、栅格规则或可核验的断点。视觉色值、圆角、间距等 token 引用设计系统即可，业务 PRD 不重复维护视觉稿。

#### 3\.0\.1 整体布局

**页面骨架：**请按以下顺序描述，并用【】替换为本需求的实际值：应用壳（App Shell） → 顶部导航（可选） → 侧边导航（可选） → 主内容区 → 页面头/筛选或操作区 → 业务内容区 → 分页或底部操作区 → 全局层（抽屉、弹窗、Popover、通知）。若页面采用双栏、三栏、主从详情、全屏工作台或向导式结构，必须明确各栏的职责与收起/展开规则。

### 6\.2 通用响应与错误约定

```JSON
{
  "requestId": "req_xxx",
  "code": "VALIDATION_ERROR",
  "message": "请求参数不合法",
  "fieldErrors": [{"field": "name", "code": "DUPLICATE", "message": "名称已存在"}]
```

|错误码|前端处理|是否重试|用户文案|日志级别|
|---|---|---|---|---|
|`UNAUTHENTICATED`|刷新令牌/跳登录|是（一次）|登录已失效，请重新登录|warn|
