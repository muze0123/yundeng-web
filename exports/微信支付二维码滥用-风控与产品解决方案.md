# 云登客户端支付二维码被滥用（截图代付 / 跑分）风控与产品解决方案

> 适用场景：YunLogin 客户端购买代理套餐、云币充值等微信 Native 扫码支付场景。
> 问题现象：支付弹窗中的收款二维码被截图转发，诱骗/引导第三人扫码代付，或被黑产利用刷钱洗钱；纠纷引发举报，导致微信支付渠道被平台管控，无法继续使用。

---

## 一、问题定性

**行为链条**：
截图收款码 → 转发（代付 / 跑分平台挂码）→ 第三人扫码支付 → 权益归属争议 → 被付款人举报 → 微信平台判定商户通道涉嫌"跑分/违规代收" → 交易拦截、限权甚至关闭商户号（部分管控类型不可恢复）。

**为什么会被管控**：微信侧风控盯的是"像不像正常经营"。高频小额居多 + 金额雷同连刷 + 投诉率高 + 资金归属纠纷，正是跑分的典型画像。平台无法感知"二维码是否被截图转发"（收款码与截图码对平台完全一样），**防控责任在商户**。

**技术症结**：Native 扫码是"一码付"——二维码本身不含身份，任何人扫都能付，事前无从拦截；若商户不做校验，代付也能正常到账，纠纷自然产生。

---

## 二、关键技术事实（微信支付 APIv3，已核对官方文档）

| # | 事实 | 对方案的意义 |
|---|------|------------|
| 1 | 支付成功回调（TRANSACTION.SUCCESS）对 Native/JSAPI/H5/APP/小程序**统一返回 `payer.openid`**（实际扫码付款人在商户绑定 appid 下的 openid） | 商户**可以**识别"实际付款人是谁"，做支付后一致性校验 |
| 2 | openid 按 appid 隔离：微信登录（网站应用/开放平台 appid）与支付商户号绑定的 appid 若不同，openid **无法直接比对**，需通过 **unionid** 打通（两者绑定到同一开放平台账号下） | 方案落地的前置检查项，务必先确认 appid 对齐情况 |
| 3 | JSAPI 支付下单**必须传 openid**，且仅在微信内可拉起 | 可实现"事前拦截"：不是绑定微信的人，连收银台都进不去 |
| 4 | 用户侧"付款码截图"微信已可识别拦截；但商户"收款码"的截图转发，微信侧无法感知 | 别指望平台解决，商户必须自己做 |

## 三、方案总览：四道防线

### 防线 1（产品层·治本）：让"截图代付"无效

**① P0 — 支付后一致性校验（不改现有支付路径，最快 1~2 周上线）**

```
Native 回调 → 解析 payer.openid → unionid 映射 → 与充值账号绑定的微信身份比对
├─ 一致      → 正常发放权益
└─ 不一致/无绑定 → 权益不发放，订单转人工，24h 内原路退款 + 客户端站内通知
```

- 微信登录用户已有 openid，可直接比对（注意第 2 条事实，用 unionid 对齐）。
- 仅手机号/账密/邮箱注册、未绑微信的账号：首充时引导绑定微信（"绑定后可微信快捷支付"），或支付后 24h 内绑定认领、逾期自动退款。
- 效果：代付者付了钱拿不到任何权益、自动原路退回——代付失去意义；跑分团伙也无法借你的通道洗钱（钱进不来就留不住）。

**② P1 — 事前拦截：扫码打开 H5 收银台（微信内 JSAPI）**

- 支付弹窗二维码内容从 `weixin://wxpay/bizpayurl?...`（code_url）改为**商户 H5 收银台链接**：`https://pay.yunlogin.com/c/{订单token}`，token 带 HMAC 签名 + 5 分钟时效。
- 用户微信扫码 → 微信内置浏览器打开收银台 → 网页授权静默取 openid → **与账号绑定微信比对**：
  - 一致 → 展示订单信息 → 一键 JSAPI 支付；
  - 不一致 → 阻断，提示"请使用注册/绑定本账号的微信支付"。
- 效果：截图转发出去后，任何其他人的微信打开即被拦，**事前就无法拉起支付**，比事后退款体验好、纠纷为零。
- 前置条件：认证服务号（网页授权域名）+ 商户号与该 appid 绑定。PC 端仍保留 Native 扫码作为兜底时，两类二维码务必统一走同一套校验。

**③ 通用增强（与①②并行）**

- **一单一码、短时效**：订单 3~5 分钟失效，二维码旁倒计时，超时需重新下单生成新码；支付完成/关闭后立即作废。截图传播出去，码很快就是废码。
- **金额随机分尾数**：每单金额加随机分（±0.01~0.99 元），既便于对账，也能识别"同码多笔不同金额"的滥用。
- **限额**：单账号单日充值笔数/金额上限；新注册账号首日/首充低限额，随账号年龄与实名等级逐步放开。
- **疏导真实代付需求（可选）**：若"请朋友帮忙付"是真实需求，提供合规范式——登录态下生成官方"代付链接"，代付人需微信授权登录并确认，权益仍归属发起账号，把私下转码行为引导到可控通道。

### 防线 2（风控层·兜底）：识别跑分与异常交易

- **事中规则（高频小额场景重点）**：
  - 同设备指纹 / IP / 网段短时聚集多笔订单、付款人 openid 高度分散；
  - 等额连刷、金额尾号规律、整点集中；
  - 二维码生成到实际支付的**间隔异常长**（截图传播的时间差特征）；
  - 付款人 openid 首次出现且账号行为异常（新号、无业务使用记录）。
- **处置分级**：放行 → 延迟到账（T+1 人工复核后发放）→ 拒绝 → 冻结账号 + 原路退款。
- **权益发放异步化**：支付成功 ≠ 立即到账。命中风险的订单先进复核队列——这是把"资金纠纷"变成"售后流程"的关键设计。
- **KYC 分级**：单日/累计充值超阈值触发实名认证（姓名 + 身份证二要素）；实名黑名单与投诉账号联动。
- **名单体系**：投诉关联账号、涉诈设备指纹、跑分特征账号库，支持拉黑与灰度观察。

### 防线 3（合规与运营层）：保住通道

- **投诉响应 SOP**：微信支付商家投诉的处理率与时长直接影响商户风控等级。纠纷订单（含代付争议）优先原路退款、限时响应。**"投诉拖着不处理"是持续加重风控的典型原因。**
- **协议与提示**：用户协议明确"收款二维码仅限本人支付，禁止截图转发、代付、刷单"，违者可冻结处置；支付弹窗加警示文案："二维码仅限本人支付，请勿截图转发给他人，谨防代付诈骗"。
- **商户号治理**：按业务线/风险等级拆分商户号（或服务商子商户），单通道被限不影响全局；经营类目如实申报（软件服务/信息技术服务），避免类目错配。
- **数据留存**：订单—设备指纹—IP—openid—支付流水全链路留存，既是风控弹药，也是申诉举证材料。

### 防线 4（申诉与恢复）：已被管控时

1. **微信支付商家助手**小程序 →「业务受限处理 / 风险处理记录」查看管控原因与解脱路径；服务商模式走合作伙伴平台 → 风险处理 → 功能限制记录；或拨 95017。
2. **申诉证据包**：营业执照、真实业务模式说明（指纹浏览器 SaaS 服务）、涉事订单的处置与退款凭证、投诉处理记录，以及**本次风控整改方案**（整改方案本身就是最有力的整改证据）。
3. **预期管理**：部分"风险异常"类管控不可恢复。提前布局备用通道（支付宝当面付/H5、聚合收单），降低单一渠道依赖。

## 四、落地路线图

| 阶段 | 内容 | 目标 |
|------|------|------|
| 第 1~2 周（P0） | 回调 openid 一致性校验 + 异常订单延迟发放/自动退款；二维码 5 分钟失效；支付弹窗警示文案；投诉响应 SOP；基础频次/IP 规则 | 立即止血：代付拿不到权益、纠纷退款有出口 |
| 第 3~6 周（P1） | H5 收银台 + JSAPI 事前拦截；unionid 打通（确认登录 appid 与支付 appid 对齐）；未绑微信账号首充绑定闭环；规则引擎雏形 | 事前拦截：截图转发彻底失效 |
| 第 2~3 月（P2） | 风控规则化运营与名单库、KYC 分级、多商户号隔离、官方代付功能 | 长效治理 + 通道冗余 |

## 五、关键结论

1. **核心抓手是 `payer.openid`**：回调里能拿到实际付款人身份，"账号绑定微信 = 付款微信"的强校验在技术上完全可行，这是行业内（电商、SaaS 充值、游戏点卡）对抗代付/跑分的标准打法。
2. **事后校验先行、事前拦截跟进**：P0 改动小见效快；P1 的 H5 收银台是体验与安全的最终形态。
3. **平台管控靠"整改证据 + 投诉率"逆转**：风控方案本身就是申诉材料，投诉响应速度决定商户评分。
4. 高频小额是你们最大的风险画像，**权益异步发放 + 限额 + KYC** 三件套优先做。
