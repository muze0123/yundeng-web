## 修复：开票管理「常用抬头」是否启用开关（点击无反应 + 双蓝色描边）

### 用户报告
「常用抬头页面是否启用，点击开关没有反应请修复，开关组件出现2个蓝色描边修复」

### 根因（两个问题同源）
开关渲染为 `<button class="toggle-switch is-on" data-title-toggle="T001" role="switch" aria-checked="true">`，
但事件绑定写在 **`onchange`** 上：

```js
q('#invoiceTitleBody').onchange = e => { const toggle = e.target.closest('[data-title-toggle]'); … };
```

**`<button>` 永远不会派发 `change`**（只有 input/select/textarea 会），所以点击完全无反应。
而同文件 `q('#invoiceTitleBody').onclick` 只处理了 `data-title-edit / data-title-default / data-title-delete`，**漏了 toggle**。

「2 个蓝色描边」是它的连带症状：点击无效 → 按钮一直停留在聚焦态 → `.toggle-switch:focus{outline:2px solid #0066FF;outline-offset:2px}`
与 `.toggle-switch.is-on{background:#0066FF}` 同色叠加，视觉上就是「蓝色滑块 + 蓝色外框」两层蓝描边。

### 修复（原型 + 独立版同步）
1. `q('#invoiceTitleBody').onchange = …` → **并入既有的 `.onclick` 委托**（作为第一个分支），并删除失效的 onchange，原地留注释说明原因。
   toggle 分支逻辑：翻转 `enabled`；停用时同时 `default=false`；`renderInvoiceTitles()` + `fillInvoiceTitles()`；
   **重渲染后按 id 找回同一行的开关并 `focus()`**（否则焦点丢失、键盘连击中断）；`toast('常用抬头已启用'/'常用抬头已停用')`。
2. `.toggle-switch:focus` → **`.toggle-switch:focus-visible`**：鼠标点击不再留描边，仅键盘导航显示焦点环（与文件内其他组件
   `.btn:focus-visible` / `.invoice-dialog-btn:focus-visible` / `.order-sort-button:focus-visible` 的既有写法一致）。
   design.md 未定义全局焦点环规范，故按文件内既有约定处理。

改动文件：
- `Prototype/费用管理-开票管理.html`（3 处：1 CSS + 1 委托分支 + 1 删除）
- `exports/开票管理-独立版.html`（同样 3 处）

### 运行验收（agent-browser 驱动真实页面）
- T001 开→关：`aria-checked true→false`、`aria-label 禁用→启用`、`默认` 徽标同时消失、toast「常用抬头已停用」✓
- 再点一次关→开 ✓；关闭态的 T003 点一次变启用 ✓
- 点击后焦点仍停在同一个开关上 ✓
- 描边：未聚焦 `outline: none`；唯一给开关设 outline 的规则是 `.toggle-switch:focus-visible`，**不存在纯 `:focus` 描边规则** ✓
- 原型与独立版内联脚本均 `node --check` 通过 ✓

## 复用经验
- **`<button role="switch">` 一律用 `click` 委托，不要用 `change`**。排查「点了没反应」时，先看绑定的事件类型与元素类型是否匹配。
- 列表重渲染（`innerHTML=…`）后若需保留焦点，按业务 id 找回元素再 `focus()`。
- 同色叠加导致「双重描边」观感：焦点环属于同色系时应只在 `:focus-visible` 生效，避免鼠标点击残留。

## 修复：常用抬头列表「灰色背景」（按 design §5.2 对齐）

## 本轮新挖出的 3 个坑（前两个是真实浏览器才暴露的）

### 1. `getComputedStyle` 读到的是「CSS 过渡的当前帧」，不是终值

`.net-card` 带 `transition: border-color .15s, background-color .15s, box-shadow .15s`。点击后**同步**读 `getComputedStyle` 会拿到**过渡起始值**：
- 卡片明明已 `is-selected`（class = true、标题已转 primary），读到的 `backgroundColor` 却是 `rgb(255,255,255)`、`borderColor` 却是 `rgb(223,225,229)`。
- 错误态同理：读到 `box-shadow: rgba(0,0,0,0) 0 0 0 0`，看起来像「规则没生效」。

**结论**：凡被测样式带 `transition`，断言前必须 `wait`（≥ 过渡时长，本轮用 400–700ms）；否则会把「过渡动画」误判成缺陷。反过来，**没有 transition 的属性（如 `color`、`font-weight`）可以同步读**——这也是判断「到底是没生效还是没过渡完」的快速甄别法：同一元素上有的属性生效、有的不生效，就一定是有过渡的那个没读完。

### 2. 滚动容器内的浮层必须做「向上翻转」（drop-up）

`#formArea` 是 `overflow-auto` 的滚动容器。面板用 `top: calc(100% + 6px)` 向下展开时，实测 **241px 高的日历被容器下沿裁掉 220px**（只露出 20px 高的一条），用户必须先手动滚动才能选日期。

修法（最小、不动视觉 token）：
```css
.date-picker.is-drop-up { top: auto; bottom: calc(100% + 6px); }
```
```js
var areaBottom = area ? area.getBoundingClientRect().bottom : window.innerHeight;
if (areaBottom - trigger.getBoundingClientRect().bottom < picker.offsetHeight + 12) picker.classList.add('is-drop-up');
```
- 顺序要点：先 `remove('is-drop-up')` → 再 `remove('hidden')` → 才能拿到真实 `offsetHeight` 做判定。
- 同类修法：检测结果表格出现在按钮下方，同样会落在滚动容器可视区外 → `renderDetectResult` 末尾加 `if (row.scrollIntoView) row.scrollIntoView({ block: 'nearest', behavior: 'smooth' })`。**`if` 守卫是必须的**：jsdom 未实现 `scrollIntoView`，不加守卫会让交互脚本抛 `TypeError`。
- 判定口径记住是「相对滚动容器的 getBoundingClientRect 下沿」，不是 `window.innerHeight`（有 App Shell 时两者差一层壳的高）。

### 3. 错误态必须压过 `:focus-visible` 焦点环

`.net-card:has(.net-card-input:focus-visible)` 特异度 **(0,3,0)** > `.net-card.is-error` **(0,2,0)**。校验失败时代码会 `first.focus()`，于是**danger 红描边 + primary 蓝焦点环叠加成蓝红混色**，看起来像样式 bug。

修法：把错误态写成组合选择器一起声明，让 danger 环在聚焦时也生效（既解决混色，又保留键盘焦点可见性）：
```css
.net-card.is-error, .net-card.is-error:has(.net-card-input:focus-visible) { border-color:#D9001B; box-shadow:0 0 0 2px rgba(217,0,27,.08); }
```
- 通用原则：**状态色（danger/success）优先于交互色（focus/hover）**。凡页面里同时存在「`:focus-visible` 环」与「错误态环」的组件，都要按此组合声明，否则必然混色。

# 需求 J · 网络属性默认选中「静态」（2026-10-12，`Prototype/添加设备.html`）

## 1. 口径变更：**覆盖**需求 F 的「默认无选择」

需求 F 时用户明确要求网络属性「默认无选择」，已按 `singleNetwork = null` + radio 不带 `checked` 实现。本轮用户改口：「单个添加和批量添加都默认选中'静态'」，**推翻旧口径**。

- 记录这条是因为它影响了 4 处下游断言（见 §3）——**同一字段的默认态口径被改过两次，改断言前先确认用户当前意图**。
- 现状：`singleNetwork = '静态'`、`batchNetwork = '静态'`；`#networkRadio` 与 `#batchNetworkRadio` 的**静态** radio 各带一个 `checked`。

## 2. 实现要点：change 监听改按 `checked` 判定，避免「状态与 DOM 脱节」

旧写法按 `value` 直接赋值（`singleNetwork = event.target.value`），一旦**程序化把 radio 置空**（`radio.checked = false` 后派发 `change`），`event.target.value` 仍是 `'静态'`，状态会错误地停在「已选中」，而 DOM 上其实无选中项。

改为按 `checked` 判定，取消选中（含程序化置空）时回到 `null`，由提交校验兜底拦截：

```js
singleNetwork = event.target.checked ? event.target.value : null;
batchNetwork  = event.target.checked ? event.target.value : null;
```

`syncNetwork()` / `syncDuplicateOption()` / `validateSingle()` / `validateBatch()` 都要能吃下 `null`（`if (!singleNetwork) { …'请选择网络属性' }`），无需额外改动。

# 需求 V · IP查询渠道下拉与其他下拉框同宽（2026-10-12，`Prototype/添加设备.html`）

指令：「单个添加和批量添加页面，调整 ip查询渠道右侧组件宽度与其他下拉框组件宽度保持一致」。

- **实测（agent-browser 1440×900）**：其它普通下拉/输入框都是 **500px**（`.control{width:500px}`），而 4 处 IP查询渠道下拉只有 **474px** —— 差的 26px = 8px gap + 18px 帮助图标，右边缘比上方「设备类型」短 26px。
- **根因**：`.field-inline { width:max-content; max-width:100% }` 的 `max-width:100%` 把容器夹在 `.form-control` 的 500px 里，500px 下拉只能与图标共占同一容器 → `flex:0 1 500px` 被压缩。
- **改法**：`.field-inline` 去掉 `max-width:100%`（容器按内容自然展开 526px）、`.field-inline > .control { flex:none }`（下拉固定 500px 不参与收缩）；帮助图标排在下拉右侧。4 处同构（deviceIpProvider / dynamicIpProvider / staticIpProvider / dynamicBatchIpProvider）一次改 CSS 全生效。
- **实测结果**：4 处下拉全部 500px、与同行其它控件右边缘差 0、gap 8px、图标 18×18；`#formArea` 与页面均无横向溢出（formArea 1188/1188）。
- **视口扫描**（外宽 1440→768，模块内视口 1220→548）：内视口 >767px 的整段桌面区间下拉恒为 500px 且无溢出（内视口 767 时控制列仍有 556px ≥ 526，所以「下拉 500 + 图标 26」永远放得下）；内视口 ≤767px 走移动端布局（`.form-row` 变 block、控件 100%），下拉回退为「行宽−26」——移动端刻意保留图标不挤占下拉（避免横向溢出），未额外改。
