# 产品架构制作规范

> 适用对象：产品经理、业务架构师、解决方案人员和需要说明复杂产品全貌的设计者。目标是产出一张可独立阅读、可评审、可追溯到功能与业务流程的产品架构图，而不是页面目录、技术部署图或营销概念拼图。

## 1. 产品架构的定义

产品架构用于说明：产品面向谁、通过什么触点提供服务、解决哪些业务任务、包含哪些稳定产品域、各域如何协作、依赖哪些基础能力与外部系统。

它关注“用户可使用的能力及其业务关系”。数据库、微服务、容器、消息队列、网络分区等实现细节属于技术架构，除非产品决策必须依赖这些事实，否则不要混入产品架构图。

### 1.1 与相邻图的区别

| 图类型 | 回答的问题 | 主要元素 | 不应代替 |
|---|---|---|---|
| 产品架构图 | 产品由哪些能力域构成，如何分层与协作 | 用户、触点、产品域、能力、支撑、外部生态 | 页面导航图、技术部署图 |
| 产品结构图 | 产品包含哪些模块、页面和入口 | 模块、页面、导航层级 | 跨域关系和技术关系 |
| 产品功能结构图 | 产品能够完成哪些功能 | 功能组、功能点、操作 | 页面布局和信息字段 |
| 产品信息结构图 | 用户如何找到和理解信息 | 导航、对象、字段、内容层级 | 业务流程和系统调用 |
| 业务架构图 | 业务如何创造价值并完成端到端流程 | 参与者、价值链、能力域、流程 | 页面与控件清单 |
| 集成架构图 | 内外系统如何连接和交换信息 | 系统、接口、数据流、事件 | 产品模块分层 |
| 业务时序图 | 一次业务在时间上如何推进 | 参与方、步骤、状态、异常 | 产品全貌 |
| 技术架构图 | 能力如何被工程实现和部署 | 服务、数据库、中间件、网络、基础设施 | 未公开的技术推测 |

## 2. 推荐交付物：“三图两表”

复杂产品不应只依赖一张总图。推荐最小交付组合：

| 交付物 | 作用 | 最低内容要求 |
|---|---|---|
| 业务/产品架构图 | 给出产品全貌与能力边界 | 角色、触点、应用、核心域、支撑、外部边界 |
| 集成架构图 | 解释上下游和跨域关系 | 调用方向、数据/事件类型、外部系统、责任边界 |
| 业务时序图 | 解释一条核心链路如何运行 | 参与方、前置、主流程、状态、异常与结果 |
| 功能清单 | 把架构模块落到可核验功能 | 编号、模块、功能点、规则、状态、证据或来源 |
| 要素清单 | 定义核心对象及关系 | 对象、字段/属性、生命周期、归属、权限、关系 |

当项目只要求一张产品架构图时，也应至少用附表补充模块职责、外部边界和不确定项，避免把所有解释都塞进图中。

## 3. 制作前输入清单

开始画图前，应完成以下输入盘点：

| 输入 | 要回答的问题 | 合格标准 |
|---|---|---|
| 产品目标 | 产品为谁解决什么问题，产生什么价值 | 一句话能说明用户、场景和价值 |
| 用户与角色 | 谁使用、谁管理、谁采购、谁提供外部资源 | 区分使用者、决策者、管理员和合作方 |
| 触点与渠道 | 用户从哪里进入和使用产品 | 区分官网、客户端、浏览器窗口、API 等不同触点 |
| 核心业务链 | 用户从起点到结果经历什么 | 至少识别 1～3 条端到端主链，并含异常或逆向环节 |
| 核心对象 | 哪个对象承载主要配置、状态和关系 | 能画出对象生命周期和对象间关系 |
| 功能清单 | 产品实际提供什么能力 | 功能可追溯，明确已确认/推断/未覆盖 |
| 组织与权限 | 谁能看、谁能操作、资源如何授权 | 权限主体、资源范围、动作权限可区分 |
| 商业模式 | 如何收费、权益如何生效 | 套餐、计费对象、订单、续期和增值服务清楚 |
| 外部依赖 | 哪些平台、资源或服务不在产品边界内 | 能明确自建、集成、跳转、合作供给的区别 |
| 技术公开边界 | 哪些技术事实有正式依据 | 无依据的部署、算法和数据流不进入确认层 |

## 4. 标准制作流程

### 4.1 第一步：确定读者和使用场景

同一产品针对不同读者，架构图重点不同：

- 管理层关注价值链、产品域、商业化和外部依赖；
- 产品团队关注模块职责、核心对象、规则和跨域关系；
- 研发团队还需要集成、数据与技术架构，但不得用技术图替代产品图；
- 销售与客户关注角色、场景、解决方案和交付边界。

在图左上角或文档开头写清楚：图的受众、目的、范围、版本和非范围。

### 4.2 第二步：识别核心对象

判断核心对象可用四个问题：

1. 大多数配置最终附着在哪个对象上？
2. 哪个对象具有清晰的创建、使用、变更、关闭或删除生命周期？
3. 其他资源、用户、订单或任务是否围绕它建立关系？
4. 产品的关键价值是否通过它被交付？

例如 AdsPower 的“浏览器环境”同时关联指纹、代理、账号、数据、应用与自动化任务，因此它比“环境管理页面”更适合作为架构核心。

### 4.3 第三步：提炼业务主链

主链应从业务结果倒推，不从页面点击顺序机械摘录。每条主链至少包含：

- 触发者；
- 前置条件；
- 核心对象；
- 关键步骤；
- 状态变化；
- 正常结果；
- 异常、撤销、恢复或逆向处理。

主链数量通常控制在 1～3 条。超过 3 条时，应判断是否混入了次要流程或把同一价值链拆得过细。

### 4.4 第四步：划分稳定产品域

产品域应满足高内聚、低耦合：

- 同一域内围绕同一类对象或目标；
- 域有明确输入、输出、职责和边界；
- 域名使用业务名词，不使用“其他”“综合”“功能模块”等含混名称；
- 一个功能只设一个主归属，跨域复用通过关系表达，不重复复制；
- 页面可以变化，产品域应相对稳定。

常见划分依据包括：核心对象、生命周期、责任团队、业务规则、数据归属、权限边界、计费边界和外部系统边界。

### 4.5 第五步：建立横向分层

推荐六层模型，可根据产品复杂度增减：

| 层级 | 定义 | 典型内容 |
|---|---|---|
| 触点层 | 用户或系统进入产品的界面与接口 | Web、App、客户端、浏览器窗口、API |
| 用户层 | 使用、管理、采购或协作角色 | 个人用户、管理员、成员、开发者、财务 |
| 应用层 | 面向用户任务组织的工作台或应用 | 运营台、管理台、费用中心、开发平台 |
| 核心域层 | 承载核心对象、规则和业务状态的能力域 | 订单、客户、环境、代理、自动化、组织 |
| 基础能力层 | 被多个核心域复用的公共能力 | 认证、权限、调度、消息、日志、计费 |
| 生态/资源层 | 产品边界外的合作资源与上下游 | 第三方平台、供应商、支付、开放生态 |

若某一支撑能力跨越多个横向层，应使用右侧纵向支撑栏，不应强行塞入单一层。

### 4.6 第六步：增加纵向支撑

适合纵向表达的能力通常具有三项特征：

1. 服务三个或以上产品域；
2. 贯穿多个业务阶段；
3. 具有统一策略、合规或治理要求。

典型纵向支撑包括账号安全、风控、权限、运营、客户服务、任务与消息、日志审计、数据治理、计费权益和恢复能力。

### 4.7 第七步：标明外部边界

使用边界框和图例明确区分：

- 产品自有能力；
- 内部共享能力；
- 第三方集成；
- 外部跳转；
- 资源供应商；
- 客户或合作伙伴自有系统。

边界不明确时，读者很容易把“产品入口”误解为“产品自建能力”。

### 4.8 第八步：补充关系与校验

产品架构图只表达最重要关系。复杂调用、数据流、事件或时序应转移到集成图和时序图。

完成后逐项反查：

- 每个核心模块能否追溯到真实功能或业务规则；
- 每条主链能否从触点贯通到核心域和结果；
- 核心对象生命周期是否闭环；
- 权限、审计、异常、恢复和计费是否遗漏；
- 外部能力是否被误画成内部模块；
- 技术推测是否被错误标为事实。

## 5. 图形语义规范

### 5.1 图形约定

| 图形 | 建议语义 | 使用限制 |
|---|---|---|
| 大型圆角容器 | 层级、产品域或系统边界 | 同级容器尺寸和样式一致 |
| 中型卡片 | 子域、工作台或稳定能力组 | 不直接放页面字段和控件 |
| 小型胶囊/矩形 | 关键能力点 | 每组控制在 3～8 个，过多转附表 |
| 实线边界 | 已确认的产品边界或归属 | 不用于表示“可能属于” |
| 虚线边界 | 逻辑范围、待确认边界或生态边界 | 必须在图例解释 |
| 实线箭头 | 明确的主调用、主流程或依赖方向 | 箭头须有方向，必要时标注动词 |
| 虚线箭头 | 异步、可选、外部跳转或弱依赖 | 不要同时承载多种含义 |
| 双向箭头 | 确认存在双向交互 | 不要为了“看起来有关联”滥用 |

### 5.2 颜色语义

颜色只用于区分信息类别，不用于装饰。推荐一套主色加 3～5 个语义色：

| 用途 | 推荐色 | 示例 |
|---|---|---|
| 品牌与标题 | 品牌蓝 | `#1D39C4`、`#1677FF` |
| 触点/应用 | 浅蓝 | `#E6F4FF`，边框 `#91CAFF` |
| 用户/资源 | 浅绿 | `#F6FFED`，边框 `#B7EB8F` |
| 核心域 | 浅黄 | `#FFFBE6`，边框 `#FFD666` |
| 治理/商业 | 浅粉或浅紫 | `#FFF0F6` / `#F0F5FF` |
| 基础能力 | 浅灰 | `#FAFAFA`，边框 `#D9D9D9` |
| 外部生态 | 浅青 | `#E6FFFB`，边框 `#87E8DE` |

同一颜色在全图中只能表示一种含义。不要用红绿表示普通分类，以免与失败/成功状态冲突。

### 5.3 画布与布局

| 项目 | 推荐规范 |
|---|---|
| 画布比例 | 16:9、16:10 或 A3 横版；复杂架构优先 1920×1200 |
| 安全边距 | 四周 40～64 px |
| 栅格 | 8 px 基础栅格；模块间距 16～24 px；层间距 16～28 px |
| 标题区 | 高 72～96 px；标题居中或左对齐；副标题不超过一行 |
| 主体布局 | 上到下表达层级，左到右表达同级域；右侧放纵向支撑 |
| 层标签 | 左侧固定宽度 64～96 px，避免与模块混排 |
| 圆角 | 大容器 16～20 px；卡片 8～12 px |
| 描边 | 1～2 px；同级保持一致 |
| 阴影 | 仅用于区分主要容器，低透明度，禁止重阴影 |

### 5.4 字体层级

以 1920×1200 画布为例：

| 文本 | 字号 | 字重 | 规则 |
|---|---:|---:|---|
| 主标题 | 32～40 px | 700 | 一行，直接说明图名 |
| 层级标签 | 24～28 px | 700 | 单词或短词组 |
| 产品域标题 | 22～26 px | 700 | 使用业务名词 |
| 子域/卡片标题 | 18～22 px | 600～700 | 不超过 12 个汉字为宜 |
| 能力点 | 15～18 px | 400～600 | 尽量一行，不写长句 |
| 图例与注释 | 13～16 px | 400 | 说明边界、来源和非范围 |

字体优先使用思源黑体、苹方、微软雅黑等无衬线中文字体。正文不要使用低于 14 px 的字号。

## 6. 内容与命名规范

### 6.1 命名原则

- 域和对象使用名词：环境、代理、团队、订单；
- 能力使用“动词 + 名词”或稳定业务名词：环境创建、代理检查、权限分配；
- 同一概念全文同名，不在“浏览器环境/浏览器配置/账号环境”之间来回切换；
- 不用“管理”“中心”“系统”掩盖职责；必须能回答管理什么、服务什么；
- 页面名只在确实代表稳定业务工作台时进入应用层；控件名不进入架构图。

### 6.2 粒度控制

推荐图中最多展示三级：

1. 层级；
2. 产品域；
3. 关键能力。

每个域建议 3～8 个能力点。超过 8 个时，保留对业务链最关键的能力，其余放入功能清单。不同域的粒度必须大致一致，不能一边写“客户系统”，另一边写“手机号输入框”。

### 6.3 事实状态

架构文档必须明确区分：

- **已确认**：有产品页面、正式文档、实际规则或可靠来源支持；
- **架构判断**：根据已确认功能关系进行的合理抽象；
- **建议设计**：面向未来或补全方案的主观设计；
- **待核实**：存在入口或线索，但缺少完整规则；
- **非范围**：明确不属于当前产品或本次研究。

建议在图后附一张状态表，而不是把大量“可能”“推测”塞进节点文字。

## 7. 产品架构图示例：AdsPower

### 7.1 核心判断

- 核心对象：浏览器环境；
- 组织与计费边界：团队；
- 规模化能力：代理、窗口同步、RPA、Local API/MCP；
- 商业化能力：套餐、环境额度、成员额度、钱包、订单、续期、终身环境和代理资源；
- 外部生态：目标网站、代理供应商、DuoPlus、Chrome 扩展和支付渠道。

### 7.2 分层结果

| 层级 | AdsPower 示例 |
|---|---|
| 触点层 | 官网、桌面客户端、隔离浏览器窗口、Local API/MCP |
| 用户层 | 个人运营者、团队管理员、成员、开发者、采购财务 |
| 应用层 | 环境运营台、代理资源台、自动化中心、团队管理台、费用中心 |
| 核心域层 | 环境与指纹、代理与自动化、组织治理与商业化 |
| 基础能力层 | 认证、隔离、内核、代理连通、调度、同步、计费、审计恢复 |
| 外部生态层 | 目标平台、代理供应商、云手机、扩展、支付渠道 |

![AdsPower 产品架构示例](./Adspower产品架构图.png)

### 7.3 为什么这样画

- 采用横向分层，让读者从“谁使用、在哪里使用”逐步进入“产品如何提供能力”；
- 把核心域放在视觉中心，强调环境对象及其与代理、自动化、组织和商业化的关系；
- 把账号安全、运营服务、治理恢复放在右侧，表示其横跨多个业务域；
- 把外部平台和供应商放在产品边界外，避免误解为自建模块；
- 控制每个核心域的能力点数量，详细字段和控件转移到功能清单。

## 8. 常见错误与修正

| 错误 | 表现 | 后果 | 修正方式 |
|---|---|---|---|
| 把菜单树当架构 | 按左侧导航逐项搬运 | 只能说明入口，无法解释业务关系 | 先抽核心对象和业务域，再映射页面 |
| 把功能清单塞进一张图 | 节点过多、字号过小 | 图不可读，重点消失 | 图保留关键能力，细节进入附表 |
| 混入技术部署 | 未经核实写数据库、微服务、加密算法 | 把推测伪装成事实 | 单独制作技术架构，并标注证据和待核实项 |
| 内外边界不清 | 外部跳转、供应商资源画在产品内部 | 误判产品自建范围和责任 | 使用边界框、外部生态层和图例 |
| 模块粒度不一致 | “订单系统”与“确认按钮”同级 | 不能比较或评审 | 统一为域、子域、能力三级 |
| 箭头没有语义 | 线条很多但不标方向或含义 | 关系无法解释 | 只保留主关系，并用动词标注 |
| 颜色只为好看 | 同色多义、颜色过多 | 读者无法建立视觉规则 | 建立颜色语义表，全图复用 |
| 缺少逆向与治理 | 只画正常主流程 | 删除、退款、恢复、审计被遗漏 | 从生命周期补齐异常、恢复和审计 |
| 未标事实状态 | 已确认与建议混在一起 | 决策依据不可信 | 附状态表或在节点使用统一标记 |

## 9. 评审与验收清单

### 9.1 内容完整性

- [ ] 一句话说明产品价值、用户和场景；
- [ ] 识别至少一个核心对象及其生命周期；
- [ ] 识别 1～3 条端到端业务主链；
- [ ] 核心域有明确职责、输入和输出；
- [ ] 用户、触点、应用、核心域、基础能力和外部生态均已覆盖；
- [ ] 权限、计费、日志、异常、恢复和外部依赖已检查；
- [ ] 图中模块可追溯到功能清单或可靠资料。

### 9.2 逻辑一致性

- [ ] 同一能力只有一个主归属；
- [ ] 同级模块粒度一致；
- [ ] 箭头方向和语义明确；
- [ ] 外部系统没有被画入产品自有边界；
- [ ] 产品架构与业务流程、对象关系不存在冲突；
- [ ] 未公开技术没有被写成确定事实。

### 9.3 视觉可读性

- [ ] 缩放到 50% 仍能看清层级和域标题；
- [ ] 100% 查看时能力点无需横向滚动或放大；
- [ ] 颜色含义唯一，图例完整；
- [ ] 节点文字尽量不换行、不截断、不溢出；
- [ ] 画面留白均衡，主次清楚；
- [ ] 图片之外有等价的文字说明，图不是唯一信息来源。

### 9.4 文档交付

- [ ] 图名、版本、日期、负责人、范围和非范围清楚；
- [ ] 同时提供可编辑源文件与发布图片；
- [ ] 附功能清单、要素清单或状态边界表；
- [ ] 引用外部方法或数据时给出来源；
- [ ] 修改记录能说明变更原因和影响范围。
